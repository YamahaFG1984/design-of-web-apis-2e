第 4 章

用 HTTP 表示操作

上一章我们用自然语言找出了资源、动作、输入和输出。这一章把它们逐项翻译成 HTTP： 资源变成路径，动作变成方法，输出类型变成状态码，输入输出数据放进请求和响应里合适的位置。 最后再看看那些不属于增删改查的「做某事」操作怎么处理，以及 REST 到底是什么。

本章目标

  • 设计唯一、有意义、体现层级关系的资源路径
  • 为五种典型操作选择 HTTP 方法（POST / GET / PUT / PATCH / DELETE）
  • 知道输入该放在路径、查询参数、请求头还是请求体里
  • 用 2XX / 4XX / 5XX 状态码表示成功与失败，并借此补全遗漏的错误
  • 用三种方式表示「结账」这类非 CRUD 操作
  • 了解 REST 架构风格的六条约束

目标：一次完整的 HTTP 表示长什么样

用路径表示资源

路径的基本规则

在 https://api.server.com/path 里，/path 就是资源路径。

  • 一条路径唯一标识一个资源，像文件系统里的文件路径（但不同的路径可以通向同一个资源）。
  • 路径不反映底层数据。/something 既不对应服务器上的 /something 文件夹，也不对应 something 数据库表。
  • 路径由斜杠分隔的段组成，可以包含路径参数：文档里写作 /products/{productId}，实际请求时填入值 /products/123456。
💡 别用结尾斜杠

/path/ 这样的结尾斜杠会在代码路由或网络设备上引发诡异的 Bug，让人调试好几个小时。统一用 /path。

让路径有意义

从 REST 的角度，路径只要唯一就行。但我们是给人用的 —— 对「目录」这个资源：

路径思路唯一有意义
/xyz随便起✓✗ 完全看不出是什么
/cat缩写✓✗ 猫？六个月后自己都忘了
/catalog资源名✓✓
/products资源的内容（目录就是商品的集合）✓✓

用路径参数定位具体元素、用层级体现关系

单个「商品」无法只靠名字来唯一标识。上一章发现，所有针对商品的操作都需要「商品引用」这个输入 —— 它就是路径参数的来源。

路径（123456 是商品引用）唯一有意义体现层级问题
/product✗✓—不知道是哪件商品
/123456✓✗—将来的 /{supplierId} 会和它撞车
/product-123456✓✓✗看不出它属于目录
/123456/catalog✓✓✗ 反了子在父之前
/catalog/123456✓✓✓「目录包含商品 123456」
/products/123456✓✓✓「商品 123456 属于商品列表」

HTTP 路径天然是层级的：/parent/child 表示父包含子。最后一段决定了这条路径本质上是什么 （/w/h/a/t/e/v/e/r/products 指的还是商品），前面的段提供上下文： /merchants/{merchantId}/products/{productId} 是「某商家目录里的某件商品」。

集合与元素：最通用的模式

这个模式在 REST API 里被广泛采用。它唯一、有意义、体现关系，而且消费者只要把 ID 拼到集合路径后面就得到元素路径。 （用单数 /product 和 /product/{id} 也是合法的，关键是一致。）

用 HTTP 方法表示动作

REST API 用五个 HTTP 方法。拿不准时查这张表：

方法HTTP 含义CRUD适用的动作（举例）
POST创建；更广义地说是「按资源自身的含义处理这个请求」C，以及非 CRUD创建、添加、开始、保存、发送；执行、做某事
GET读取R读取、获取、搜索、筛选、列出、下载
PUT替换；不存在则创建（upsert）U、C替换、修改、更新、编辑；也可用于创建
PATCH（部分）更新U修改、更新、编辑
DELETE删除D删除、取消、关闭、结束、停止
ⓘ PUT 和 PATCH 的区别

从消费者角度，「只改一部分」用哪个都能做到：用 PUT 时把整个资源（含改动）发回去； 用 PATCH 时只发改动的部分。现阶段推荐默认用 PUT —— 适用面广，实现也更简单。

ⓘ 方法描述的是接口，不是实现

DELETE /something 背后可以是物理删除，也可以只是把一个标记位改掉（软删除）。 但实现必须遵守 HTTP 方法的「安全」「幂等」等特性（第 12 章会讲）。

为五个操作选方法

规则：同一个资源上，每个 HTTP 方法只能定义一次。如果出现冲突（比如同一路径上有两个都想用 GET 的操作）， 通常说明资源或操作识别错了 —— 比如第 2 章如果没把「搜索要买的商品」和「查找相似商品」合并，这里就会撞车。

  • 搜索本质是读 → GET /products
  • 获取 → GET /products/{productId}
  • 移除是删除 → DELETE /products/{productId}
  • 修改是更新 → PUT 或 PATCH /products/{productId}
  • 添加是创建 → POST /products。 能不能用 PUT？PUT /products 会替换整个目录，不是我们要的； 必须是 PUT /products/{productId}，这要求消费者自己提供 ID。当 ID 是事先存在且全球唯一的（如图书的 ISBN）时可行； 如果 ID 是系统生成的随机数，就用 POST 让系统来生成，避免 ID 冲突。

输入数据放在请求的哪里

放哪里，取决于 HTTP 方法和这份数据的性质。输入分三类：

数据性质含义例子位置
资源标识符 帮助确定操作作用于哪个资源 商品引用 路径参数
资源表示 要创建或更新的资源数据本身 商品信息、修改后的商品信息 请求体
资源修饰符 调整返回的数据，但返回的仍是同一种业务实体 筛选条件 查询参数（除非有对应的标准 HTTP 头）

为什么筛选条件不放进路径

假设有「类型」和「描述」两个筛选条件。写成 /products/{type}/{description} 会有两个问题： 路径参数是必填的，消费者就没法只按类型搜、或者不带条件列出全部； 而且类型和描述之间没有层级关系，不适合放进层级化的路径。 所以是 /products?type=book&description=design。

换个角度：GET /products 和 GET /products?type=book 在 HTTP 层面是两个不同的资源（路径 + 查询共同标识资源）， 但它们指向的是同一个 API 资源「目录」。筛选条件改变了返回的内容，却没改变它的性质。

标识符还是修饰符？

同一个东西在不同场合可以是不同的性质。「分类引用」在读取某个分类时是标识符（/categories/{categoryId}）； 在搜索商品时是修饰符（/products?category=…），因为不提供它照样能搜。

⚠ 别因为「能写出这条路径」就多加一个操作

你可能会想：分类是个明确的实体，那 GET /categories/{categoryId}/products 也该有吧？ 先问：「搜索某分类的商品」是之前识别出的能力吗？还是我们在照着「分类页」这个 UI 画 API？ 一个带筛选条件的通用 GET /products 就够了。 GET /suppliers/{supplierId}/products 则可能不同 —— 「供应商的商品」也许是从另一个视角看的不同数据 —— 但同样要有对应的能力才加。

错误，以及借机查漏

需求分析时的关注点在业务上，错误列得不全是正常的。选状态码正是补漏的好时机，三条检查规则：

  1. 凡是有查询参数或请求体输入的操作，都要处理「输入缺失或无效」→ 400 Bad Request。
    补上：「搜索商品」的筛选条件可能写错；「修改商品」的商品信息可能有误。
  2. 凡是路径里有路径参数的操作，都要处理「资源不存在」→ 404 Not Found。
  3. 所有操作都要处理「意外的服务端错误」→ 500 Internal Server Error。
⚠ 两个常见错误

别把 404 和 204 搞混。读取一件不存在的商品返回 204 是错的 —— 那表示「商品存在，但没有内容」。
别自创状态码。用未分配的代码（比如 455）只会带来兼容性问题和困惑。拿不准就用该类别的 X00。

输出数据放在响应的哪里

响应的结构和请求类似，只是第一行换成了状态。放数据的位置只有两个：响应头和响应体。

HTTP 的规范还帮我们发现了几处缺失的输出数据：

  • POST 创建后，应返回被创建的资源（或至少足以再次取回它的信息）。而且 201 Created 要求在 Location 响应头里给出新资源的 URL。
  • 「修改商品」既然选了 200，就该返回更新后的商品。
  • 「没有匹配的商品」返回 200，响应体里放一个空列表。
  • 所有错误都应在响应体里返回错误信息 —— 光有状态码往往不够（第 9 章细讲）。

把这张表实现出来

下面用三种主流框架把上表原样实现一遍（用内存里的字典代替数据库）。 读的时候请把注意力放在设计如何映射到代码上：路径、方法、状态码、Location 头、错误体 —— 每一处都能在表里找到对应的格子。 

from uuid import uuid4
from fastapi import FastAPI, HTTPException, Response, status
from pydantic import BaseModel

app = FastAPI()
db: dict[str, dict] = {}                      # 假装这是数据库

class ProductInfo(BaseModel):                 # 资源表示 → 请求体
    name: str
    type: str
    price: float

# 创建：POST 集合 → 201 + Location 头 + 响应体
@app.post("/products", status_code=status.HTTP_201_CREATED)
def add_product(info: ProductInfo, response: Response):
    product_id = uuid4().hex[:8]              # ID 由系统生成，所以用 POST 而不是 PUT
    db[product_id] = {"id": product_id, **info.model_dump()}
    response.headers["Location"] = f"/products/{product_id}"
    return db[product_id]
    # 商品信息有误时，FastAPI 会根据 ProductInfo 自动返回 4XX

# 搜索：GET 集合，筛选条件 → 查询参数；没找到也是 200 + 空列表
@app.get("/products")
def search_products(type: str | None = None):
    return [p for p in db.values() if type is None or p["type"] == type]

# 读取：GET 元素，资源标识符 → 路径参数
@app.get("/products/{product_id}")
def get_product(product_id: str):
    if product_id not in db:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Product not found")
    return db[product_id]

# 更新：PUT 元素 → 200 + 更新后的资源
@app.put("/products/{product_id}")
def modify_product(product_id: str, info: ProductInfo):
    if product_id not in db:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Product not found")
    db[product_id] = {"id": product_id, **info.model_dump()}
    return db[product_id]

# 删除：DELETE 元素 → 204，无响应体
@app.delete("/products/{product_id}", status_code=status.HTTP_204_NO_CONTENT)
def remove_product(product_id: str):
    if product_id not in db:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Product not found")
    del db[product_id]

import { Hono } from "hono";
import { z } from "zod";
import { zValidator } from "@hono/zod-validator";

const app = new Hono();
const db = new Map<string, Product>();         // 假装这是数据库

const ProductInfo = z.object({                // 资源表示 → 请求体
  name: z.string(),
  type: z.string(),
  price: z.number(),
});
type Product = z.infer<typeof ProductInfo> & { id: string };

const notFound = { message: "Product not found" };

// 创建：POST 集合 → 201 + Location 头 + 响应体
app.post("/products", zValidator("json", ProductInfo), (c) => {
  const id = crypto.randomUUID().slice(0, 8); // ID 由系统生成，所以用 POST 而不是 PUT
  const product = { id, ...c.req.valid("json") };
  db.set(id, product);
  c.header("Location", `/products/${id}`);
  return c.json(product, 201);
  // 商品信息有误时，zValidator 会自动返回 400
});

// 搜索：GET 集合，筛选条件 → 查询参数；没找到也是 200 + 空数组
app.get("/products", (c) => {
  const type = c.req.query("type");
  return c.json([...db.values()].filter((p) => !type || p.type === type));
});

// 读取：GET 元素，资源标识符 → 路径参数
app.get("/products/:productId", (c) => {
  const product = db.get(c.req.param("productId"));
  return product ? c.json(product) : c.json(notFound, 404);
});

// 更新：PUT 元素 → 200 + 更新后的资源
app.put("/products/:productId", zValidator("json", ProductInfo), (c) => {
  const id = c.req.param("productId");
  if (!db.has(id)) return c.json(notFound, 404);
  const product = { id, ...c.req.valid("json") };
  db.set(id, product);
  return c.json(product);
});

// 删除：DELETE 元素 → 204，无响应体
app.delete("/products/:productId", (c) => {
  if (!db.delete(c.req.param("productId"))) return c.json(notFound, 404);
  return c.body(null, 204);
});

export default app;

@RestController
@RequestMapping("/products")
public class ProductController {

    public record ProductInfo(@NotBlank String name, @NotBlank String type, @NotNull Double price) {}
    public record Product(String id, String name, String type, Double price) {}

    private final Map<String, Product> db = new ConcurrentHashMap<>();   // 假装这是数据库

    // 创建：POST 集合 → 201 + Location 头 + 响应体
    @PostMapping
    public ResponseEntity<Product> addProduct(@Valid @RequestBody ProductInfo info) {
        String id = UUID.randomUUID().toString().substring(0, 8);  // ID 由系统生成，所以用 POST
        Product product = new Product(id, info.name(), info.type(), info.price());
        db.put(id, product);
        return ResponseEntity.created(URI.create("/products/" + id)).body(product);
        // 商品信息有误时，@Valid 会让 Spring 自动返回 400
    }

    // 搜索：GET 集合，筛选条件 → 查询参数；没找到也是 200 + 空列表
    @GetMapping
    public List<Product> searchProducts(@RequestParam(required = false) String type) {
        return db.values().stream()
            .filter(p -> type == null || p.type().equals(type))
            .toList();
    }

    // 读取：GET 元素，资源标识符 → 路径参数
    @GetMapping("/{productId}")
    public Product getProduct(@PathVariable String productId) {
        return find(productId);
    }

    // 更新：PUT 元素 → 200 + 更新后的资源
    @PutMapping("/{productId}")
    public Product modifyProduct(@PathVariable String productId, @Valid @RequestBody ProductInfo info) {
        find(productId);
        Product product = new Product(productId, info.name(), info.type(), info.price());
        db.put(productId, product);
        return product;
    }

    // 删除：DELETE 元素 → 204，无响应体
    @DeleteMapping("/{productId}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void removeProduct(@PathVariable String productId) {
        find(productId);
        db.remove(productId);
    }

    private Product find(String id) {
        Product product = db.get(id);
        if (product == null) throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Product not found");
        return product;
    }
}

「做某事」类操作怎么表示

不是所有操作都能归入增删改查。「结账」是个动词，它作用于哪个资源？该用哪个方法？有三种处理方式：

  • ① 动作资源。POST /check-out（如果有多个购物车则是 POST /carts/{cartId}/check-out）。 它返回 201 Created、订单信息和订单的 Location。动作资源也适合不产生任何东西的临时计算，比如 POST /sum 返回 200 和结果。
  • ② 名词化。如果「结账」在业务上本身就是个值得记录的概念，就把动词变名词。 想不出名词时，试试加后缀：-ing、-ment、-tion……「execute」→「executions」。这种方式特别适合耗时长的操作（第 14 章）。
  • ③ 聚焦结果。如果真正重要的是结账产生的「订单」，直接 POST /orders。

REST 架构风格

到目前为止我们把 REST API 简化成了「把能力映射到 HTTP」。其实 REST（Representational State Transfer，表述性状态转移） 是 Roy Fielding 在 2000 年的博士论文里提出的一种架构风格（他当时正在参与 HTTP 1.1 的制定）， 目标是构建高效、可伸缩、可靠、简单、可移植、可修改的分布式系统。它由六条约束定义：

💬 关于「这算不算 RESTful」的争论

这类争论往往激烈而没有结果，而且常常源于对 REST 和 HTTP 的误解：

  • 「POST /do 不 RESTful，因为 /do 是动作不是资源。」—— HTTP 规范（RFC 9110）明确说它不限制资源的性质，动作资源是合法的。
  • 「REST API 里集合必须用复数。」—— 命名约定并不决定一个 API 是否 RESTful。

与其争论标签，不如理解原则、知道何时做取舍、评估只遵守部分原则的后果。 面对那些自称 RESTful 却连 HTTP 都没用对的老 API，重点不是指责过去，而是别再继续加深问题。

本章小结

  • 资源路径要唯一（必要时用路径参数）、表意清楚、体现父子关系（/parent/child）。
  • 集合用 /elements，元素用 /elements/{id}。
  • 五种典型操作：搜索 GET /elements；创建 POST /elements（或 PUT /elements/{id}）；读取 GET /elements/{id}；更新 PUT/PATCH /elements/{id}；删除 DELETE /elements/{id}。
  • 资源表示 → 请求体；资源标识符 → 路径参数；资源修饰符 → 查询参数（除非有对应的标准头）。
  • 成功 2XX，消费者的错 4XX，提供者的错 5XX。
  • 创建成功 201；有数据返回的成功 200；无数据返回的成功 204。
  • 有输入就要有 400；有路径参数就要有 404；所有操作都要有 500。
  • 输出数据放响应体，除非它对应一个标准头（如 Location）。
  • 非 CRUD 操作可以映射为 POST /do、POST /doings（名词化）或 POST /results（结果资源），优先后两者。
  • REST 架构风格的约束：客户端/服务端分离、无状态、可缓存、分层系统、统一接口，以及可选的按需代码。

动手练习

  1. 修正下面这些图书馆 API 的调用：
    a) 读取某本书的一条书评：GET /books/12345/reviews?reviewId=678
    b) 列出某借阅者借的书：GET /books/borrowers/7890
    c) 搜索可借的英文书：GET /books/available/en
    d) 获取图书信息：GET /book/12345
    e) 搜索科幻作者：GET /genres/science-fiction/author
    参考答案 a) 书评 ID 是标识符 → GET /books/12345/reviews/678。
    b) 层级反了 → GET /borrowers/7890/books（或 GET /books?borrowerId=7890）。
    c) 「可借」「英文」是筛选条件 → GET /books?available=true&language=en。
    d) 路径本身合法，但要与其他路径保持一致用复数 → GET /books/12345。
    e) 体裁是筛选条件，且集合名应统一 → GET /authors?genre=science-fiction。
  2. 活动订票 API。为每个操作写出 HTTP 方法和每个输入的位置：搜索活动（类型、日期范围）；订票（活动、座位数、参加者信息）；修改预订（预订、新座位数、参加者信息）；取消预订（预订）；获取某用户的预订（用户、活动类型、日期范围）。
    参考答案 GET /events?type=…&from=…&to=…（全是查询参数）；
    POST /bookings（活动引用、座位数、参加者信息都在请求体）；
    PUT 或 PATCH /bookings/{bookingId}（预订在路径，其余在请求体）；
    DELETE /bookings/{bookingId}（路径）；
    GET /users/{userId}/bookings?eventType=…&from=…&to=…（用户在路径，其余在查询参数）。
  3. 餐厅预订系统，修正这些状态码：404 搜索空桌但没有匹配的；200 成功创建了预订；500 客户端用无效的预订 ID 更新预订；204 成功取消预订；455 提交了不可能的日期或负数人数。
    参考答案 搜索无结果 → 200 + 空列表；创建成功 → 201；无效 ID 是客户端的错 → 404；取消成功 204 没问题（若返回数据则 200）； 455 是未分配的代码，不能自创 → 400。
  4. 杂志订阅 API 创建订阅时返回 200 OK 和订阅数据。怎么改？
    参考答案 状态码改为 201 Created，并加上 Location: /subscriptions/{subscriptionId} 响应头。
