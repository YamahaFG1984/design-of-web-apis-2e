第 5 章

数据建模

上一章结束时，我们只知道「读取商品」的响应体里有一坨叫「商品信息」的东西。 这一章把它打开：商品是一个对象，有整数类型的编号、字符串类型的名称、浮点数类型的价格…… 关键技巧是：先为资源设计一个完整模型，再从它派生出每个操作的输入和输出。

本章目标

  • 知道要建模的是哪些数据，以及 JSON 的六种可移植类型
  • 会设计资源的「完整（理论）模型」：选属性、起名、定类型、标必填
  • 会从完整模型派生出七种典型模型，并知道它们各用在哪个操作上
  • 会用数据反查遗漏的能力和业务错误
  • 能检查数据是否通用、是否混入了提供者或某个消费者的视角

我们在为哪些数据建模

上一章为输入输出选了位置，现在要给这些位置里的东西定形：

⚠ 从业务角度建模，而不是从存储角度

API 数据长得像数据库没什么不对，但那应该是「恰好一样」，而不是「照抄」。 别忘了第 2 章：不要不假思索地暴露提供者的数据结构。

JSON：可移植的数据格式

HTTP 的请求体和响应体可以装任何格式。Web API 最常用的是 JSON（JavaScript Object Notation）： 人能读、浏览器能直接处理，而且与编程语言无关 —— Python、Java、TypeScript 都能轻松解析。 

{
  "productReference": 12345,              // 数字（整数）
  "name": "Cowboy Bebop",                 // 字符串
  "keywords": ["anime", "space"],         // 数组（可以装任何类型）
  "price": 49.99,                         // 数字（浮点数）
  "isProductUnavailable": false,          // 布尔值
  "supplier": {                           // 对象
    "supplierCode": "SUNR",
    "name": "Sunrise"
  },
  "description": null                     // null：表示「没有值」
}

JSON 只有这几种类型：字符串、数字、布尔值、数组、对象，外加 null。 即使将来用别的格式（XML、CSV……），也请以 JSON 的类型为准来建模，这样任何消费者都能理解。路径参数、查询参数和头字段通常对应其中的原子类型。

ⓘ 注释只是为了讲解

标准 JSON 不支持注释。本教程的 JSON 示例里出现的 // 只是给你看的，真实数据里不能有。

数据建模的三步

设计资源的完整模型

REST API 的一切都围绕资源。除了 HTTP 头里的元数据，所有输入输出都与资源数据有关： 请求体和响应体是资源的表示；路径参数通常是资源的 ID；查询参数（如筛选条件）也源自资源的属性。 所以第一件事是设计完整模型（也叫理论模型）：先不管具体操作，把这个业务概念可能有的数据全部列出来。

结构

现阶段的简单约定：单个资源是对象，集合资源是数组。 「商品」→ Product（对象）；「目录」→ Product 的数组。 （第 9 章和第 15 章会说明为什么集合最好也包在一个对象里。）

商品的完整模型

与领域专家讨论「商品里有什么」之后：

　supplier.supplierCodestring✱唯一标识符，可用来读取完整的供应商
　supplier.namestring✱专家认为供应商名称对商品很重要
  • 选属性：包含资源标识符和描述这个概念的数据。与其他资源有关系时，可以带上对方的部分数据（这里带了供应商的代码和名称）。信息来源是领域专家，也可以参考现有界面、代码或数据库 —— 但要小心被它们带偏。
  • 起名：先用讨论中冒出来的第一个有意义的名字，写成变量名的形式。productReference 还是 product_reference 随你，但整个 API（乃至所有 API）要统一。
  • 定类型：从 JSON 的可移植类型里选。JSON 没有日期类型，所以 dateAdded 是字符串，格式写在说明里。
  • 写说明：当「资源名 + 属性名 + 类型」还说不清时才需要，比如「以美元计价」。
  • 标必填：在完整模型里，必填表示「没有它这个概念就不成立」。商品不能没有编号、名称、价格，但可以没有描述。 嵌套对象里也要标：supplier 必填，不代表它里面的每个属性都必填。
💡 高效建模：别同时操心所有事

现在不是争论 isAvailable 还是 isProductAvailable 的时候。重要的是识别出「商品需要一个表示是否可售的属性」。建议按这个顺序来：

  1. 用最先想到的名字把元素全列出来，不管细节；
  2. 把属于同一个子概念的归到一起，形成子对象；
  3. 逐个定类型、把名字整理成变量名、判断是否必填；
  4. 对更深层的对象重复上面的步骤；
  5. 最后逐个审视，删掉没有意义的。

从完整模型派生输入和输出

💡 先建输出，再建输入

大多数情况下，每个输入数据都与输出的某一部分相同。先把输出定下来，输入就水到渠成。

读取：GET /products/{productReference}

输出就是完整的 Product。在输出的语境下，「必填」意味着「总是会返回」：name 每个商品都有，description 可能没有。 路径参数标识的正是 Product 的 productReference，所以类型取 integer，并且把路径参数也命名为 {productReference} —— 文档里同一个东西用同一个名字，消费者才容易把各处对上。

搜索：GET /products

可以返回 Product 的数组，但列表里通常不需要全部细节。这里返回 ProductSummary 的数组： 保留 productReference、name、category、keywords、price，去掉 dateAdded 等。 消费者想看更多，拿着编号去读单个商品即可。没找到时返回空数组 []。

「筛选条件」拆成查询参数，筛选项应与返回的模型里的属性对应：GET /products?keywords=anime,fantasy&category=BD。 想按「是否可售」筛选？那得先把这个属性加进返回的模型。想按「原产国」筛选？模型里没有这个属性，要先加上。

⚠ 列表里放多少数据

放得太少，消费者得为每个元素再调一次接口；放得太多，数据量又太大。这是个效率问题，第 13 章细讲。

创建：POST /products

输出：被创建的商品，用 Product（如果出于性能考虑想少返回点，可以用只含 productReference 的 ProductMinimal）； 另有标准头 Location（string，形如 /products/12345）。

输入：虽然同样叫「商品信息」，但它和输出不一样 —— 要去掉由服务端管理的数据：

更新：PUT / PATCH /products/{productReference}

输出是商品的新状态：Product。路径参数同读取。输入因方法而异：

PUT：发送整个资源（替换）
PUT /products/12345

{
  "name": "Cowboy Bebop",
  "description": "A fantastic ...",
  "keywords": ["anime"],
  "category": "BD",
  "price": 59.99,
  "isProductUnavailable": false,
  "supplier": { "supplierCode": "SUNR" }
}
PATCH：只发送改动的部分
PATCH /products/12345

{
  "description": "A fantastic ...",
  "price": 59.99
}
  • PUT 的输入是「重新创建这个资源」所需的一切 → 与创建模型相同，可以合并成一个 ProductCreationOrReplacement。
  • PATCH 的输入 ProductModification → 创建模型的副本，但所有属性都变成可选。（这种做法叫 JSON Merge Patch，RFC 7396，是最常见的方案。）
  • 如果某些属性创建后不允许修改（比如商品的供应商），替换和修改模型就是创建模型的子集。

删除与错误

DELETE /products/{productReference}：路径参数同上，无输出。 错误输出先用一个临时的简单模型 Error：一个对象，带必填的字符串 message，例如 {"message": "The product type is missing"}。第 9 章会把它做得更好。

七种典型模型

回顾刚才做的事，可以提炼出七种反复出现的模型。以后遇到 CRUD 操作，直接套用：

在代码里表达这些模型

这七种模型在实现时就是一组彼此派生的类型。三种语言各有惯用写法：Python 用 Pydantic 的继承，TypeScript 用 Zod 的 pick / omit / partial， Java 没有内建的派生语法，通常用 record 组合。 

from datetime import date
from pydantic import BaseModel

class SupplierRef(BaseModel):                 # 创建时只需要供应商代码
    supplierCode: str

class Supplier(SupplierRef):                  # 输出时带上服务端查出的名称
    name: str

# ---- 创建模型：只有消费者提供的数据 ----
class ProductCreation(BaseModel):
    name: str
    description: str | None = None            # 可选
    keywords: list[str] = []
    category: str
    price: float
    isProductUnavailable: bool = False
    supplier: SupplierRef

ProductReplacement = ProductCreation          # 替换模型 = 创建模型

# ---- 修改模型：同样的属性，全部可选 ----
class ProductModification(BaseModel):
    name: str | None = None
    description: str | None = None
    keywords: list[str] | None = None
    category: str | None = None
    price: float | None = None
    isProductUnavailable: bool | None = None

# ---- 最小模型：只有标识符 ----
class ProductMinimal(BaseModel):
    productReference: int                     # 它的类型 int 就是「标识符模型」

# ---- 摘要模型：标识符 + 主要属性 ----
class ProductSummary(ProductMinimal):
    name: str
    category: str
    keywords: list[str] = []
    price: float

# ---- 完整模型：摘要 + 其余属性 + 服务端管理的属性 ----
class Product(ProductSummary):
    description: str | None = None
    dateAdded: date
    isProductUnavailable: bool = False
    supplier: Supplier


class Error(BaseModel):                       # 临时的错误模型
    message: str

import { z } from "zod";

// ---- 完整模型：先设计它，其余都从它派生 ----
export const Product = z.object({
  productReference: z.number().int(),          // 服务端生成；它的类型就是「标识符模型」
  name: z.string(),
  description: z.string().optional(),          // 可选
  keywords: z.array(z.string()).default([]),
  category: z.string(),
  price: z.number(),
  dateAdded: z.string().date(),                // 服务端生成，YYYY-MM-DD
  isProductUnavailable: z.boolean().default(false),
  supplier: z.object({
    supplierCode: z.string(),
    name: z.string(),                          // 服务端按代码查出
  }),
});

// ---- 摘要模型：标识符 + 主要属性 ----
export const ProductSummary = Product.pick({
  productReference: true, name: true, category: true, keywords: true, price: true,
});

// ---- 最小模型：只有标识符 ----
export const ProductMinimal = Product.pick({ productReference: true });

// ---- 创建模型：去掉服务端管理的数据 ----
export const ProductCreation = Product
  .omit({ productReference: true, dateAdded: true })
  .extend({ supplier: Product.shape.supplier.pick({ supplierCode: true }) });

export const ProductReplacement = ProductCreation;       // 替换模型 = 创建模型

// ---- 修改模型：同样的属性，全部可选；且供应商创建后不可改 ----
export const ProductModification = ProductCreation.omit({ supplier: true }).partial();

export const ErrorModel = z.object({ message: z.string() });   // 临时的错误模型

export type Product = z.infer<typeof Product>;
export type ProductSummary = z.infer<typeof ProductSummary>;
export type ProductCreation = z.infer<typeof ProductCreation>;
export type ProductModification = z.infer<typeof ProductModification>;

import jakarta.validation.constraints.*;
import java.time.LocalDate;
import java.util.List;

// ---- 完整模型：读取、创建、更新的输出 ----
public record Product(
    int productReference,            // 服务端生成；它的类型 int 就是「标识符模型」
    String name,
    String description,              // 可空 = 可选
    List<String> keywords,
    String category,
    double price,
    LocalDate dateAdded,             // 服务端生成
    boolean isProductUnavailable,
    Supplier supplier
) {
    public record Supplier(String supplierCode, String name) {}   // name 由服务端按代码查出
}

// ---- 摘要模型：标识符 + 主要属性，用于列表 ----
record ProductSummary(int productReference, String name, String category,
                      List<String> keywords, double price) {
    static ProductSummary of(Product p) {
        return new ProductSummary(p.productReference(), p.name(), p.category(), p.keywords(), p.price());
    }
}

// ---- 最小模型：只有标识符 ----
record ProductMinimal(int productReference) {}

// ---- 创建 / 替换模型：只有消费者提供的数据；注解表达「必须提供」 ----
record ProductCreationOrReplacement(
    @NotBlank String name,
    String description,
    List<String> keywords,
    @NotBlank String category,
    @NotNull @Positive Double price,
    Boolean isProductUnavailable,
    @NotNull SupplierRef supplier
) {
    record SupplierRef(@NotBlank String supplierCode) {}
}

// ---- 修改模型：同样的属性，全部可选（用包装类型，null 表示「不改」）----
record ProductModification(
    String name, String description, List<String> keywords,
    String category, Double price, Boolean isProductUnavailable
) {}

record Error(String message) {}      // 临时的错误模型

「做某事」操作的数据

  • 名词化或结果资源（POST /executions、POST /results）：按普通的创建操作处理。「执行」资源的完整模型包含动作的全部输入和输出，再加一个标识符；输入是其创建模型。
  • 动作资源（POST /sum）：像函数一样，请求体放输入，响应体放结果。建议让输出同时带上输入（像不带 ID 的「执行」资源），这样消费者能看出结果是怎么来的。

名字相同，未必是同一个东西

「商品信息」作为创建的输入和输出，模型就不同。更隐蔽的是跨场景的同名概念： 目录里的「商品」和购物车里的「商品」并不是一回事 —— 往购物车加东西只需要 productReference 和 quantity。 应把它们区分为「目录商品（Catalog Product）」和「购物车条目（Cart Item）」并分别建模； 需要时再组合，比如 CartItemSummary 里嵌一个 CatalogProductSummary。

★ 记住

看似唯一的业务概念，往往是在不同场景下的好几个概念。拿不准时一定要问领域专家；如果把模型细化之后出现了彼此不相干的数据，那就是没区分开的信号。

用数据检查完整性与聚焦

1. 输入从哪来、输出给谁用（第二次）

第 2 章在步骤层面问过这两个问题，现在在字段层面再问一遍，会有新发现。

输出也再过一遍：最终用户会拿商品里的「供应商信息」做什么？也许可以把它做成搜索的筛选项；也可能它对最终用户根本无关 —— 那就去掉。 但目录管理员需要它，这可能意味着最终用户和管理员的操作需要分开（第 12 章）。

2. 补全业务错误

有了细粒度的输入，和领域专家再核对一遍可能的业务错误，尤其是创建和修改操作。 它们大多是已有错误的细化：「商品价格不能为负数，也不能超过 100,000」细化了「商品信息有误」，可以写进 400 的说明里。

3. 聚焦在正确的元素上

检查项例子
满足消费者需求：他们要的数据给全了吗？商品缺了「尺寸」，而这对消费者很关键 → 补上
通用：换个场景还适用吗？第一个 App 的线框图里没显示「描述」，但从业务上看它是商品的基本信息 → 保留，迟早有人要用
不暴露提供者视角价格的说明写着「周五下午 4 点到 7 点要加 10%」→ 这是内部业务逻辑，别让消费者自己算
不过度贴合某个消费者因为现有网站把描述和关键词放在同一块区域，就把它们包进一个 summary 对象 → 从纯数据的角度看这毫无道理
ⓘ 这只是初稿

当前只关心「做对的事、足够通用」。得到的数据可能还不够好用、不够高效、不够安全，这对老手也是正常的 —— 后面几层会逐一修正：好用性（第 8 章）、安全（第 12 章）、性能（第 13 章）、实现约束（第 14 章）。

本章小结

  • 用 JSON 的可移植类型（字符串、数字、布尔、数组、对象）为所有数据建模，以保证兼容。
  • 先为资源（业务概念）设计模型，再派生出每个操作的输入和输出。
  • 建模时先列属性不管细节，再重组和筛选，最后定名字、类型和是否必填。
  • 七种典型模型：完整、摘要、最小、标识符、创建、替换、修改。
  • 完整模型包含全部属性和标识符，先设计它；用于创建、读取、搜索、更新的输出。
  • 摘要模型用于搜索列表；最小模型用于创建的输出；标识符模型用于路径参数。
  • 创建模型去掉服务端管理的数据；替换模型通常与它相同（PUT）；修改模型是它的全可选版本（PATCH）。
  • 检查数据的来源和用途以发现遗漏的用例或步骤；借助输入数据找全业务错误。
  • 确保数据通用、贴合消费者需求，不受提供者或某个特定消费者的影响。

动手练习

  1. 电影流媒体 API。「读取电影」返回 {"id":"ZFqoFq","title":"Ghost In The Shell","releaseYear":"1995","duration":"83","director":"Mamoru Oshii","music":"Kenji Kawai","language":"ja"}； 「搜索电影」返回 [{"title":"Ghost In The Shell","language":"ja","stars":5,"music":"Kenji Kawai"}]。指出问题。
    参考答案 ① 类型不对：releaseYear 和 duration 应是数字而不是字符串。 ② 摘要里缺少标识符 id，消费者没法接着去读某一部电影。 ③ 摘要里的 stars 在完整模型里不存在 —— 摘要应是完整模型的子集，要么把 stars 加进完整模型，要么去掉。 ④ music 对列表来说多半不是「主要属性」，而 releaseYear、director 可能更合适。
  2. 菜谱平台的 POST /recipes 请求体里包含 id、title、description、creationDate、ingredients（每项有 id 和 quantity）、instructions。有什么问题？
    参考答案 id 和 creationDate 应由服务端生成，不该出现在创建模型里。 另外每种食材的 id（如 shortcrust_pastry）从哪来？消费者无法凭空给出，说明缺少一个「搜索/列出食材」的操作。 quantity 把数值和单位混在一个字符串里（"200g"）也不便于使用。
  3. 智能手表上的健身 App 只展示一次训练的时长和类型。GET /workouts/{workoutId} 返回 id、type、duration、distance、date、lastDbSync。哪些该保留？
    参考答案 id、type、duration 保留。distance 和 date 也保留：虽然这个 App 现在不用，但它们是「训练」这个概念的基本信息，别的消费者会需要（通用性）。 lastDbSync 删除：它暴露的是提供者的内部运作。
  4. 租车 API 的 GET /cars/{carId} 同时服务「顾客租车」和「技师检修」，返回的数据里既有日租金、可载人数，也有车架号、轮胎状况、上次检修日期。合适吗？
    参考答案 不合适。这是「名字相同但概念不同」：顾客眼里的「可租车辆」和技师眼里的「待维护车辆」是两个概念，而且把车架号、检修记录给顾客还有安全问题。 应拆成两个资源/模型（例如 /rental-cars/{carId} 和 /fleet-vehicles/{carId}，或同一路径按权限返回不同模型），各自只含本场景相关的数据。
  5. 把本章的模型代码挑一种语言抄下来，为「购物车条目（Cart Item）」设计完整、摘要和创建三个模型。
