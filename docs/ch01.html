第 1 章

什么是 API 设计

你一定用过让人抓狂的 API：字段名像密码、报错只有一句「Bad Request」、升级之后程序莫名其妙崩溃。 这些问题的根源往往是同一个 —— 设计没做好。这一章先把「Web API」和「API 设计」这两个词说清楚， 再给出整本教程要走的路线图。

本章目标

  • 说得清什么是 Web API：它是给程序用的、走 HTTP 的、隐藏实现的、给别人用的接口
  • 理解糟糕的设计会伤害谁：开发者、基础设施、最终用户，最后是公司的收入
  • 知道设计发生在 API 生命周期的哪个位置、由哪些角色完成
  • 记住本教程的方法：四个步骤 × 四个层次

Web API 是什么

API 是 Application Programming Interface（应用程序编程接口）的缩写。 Web API 让一个程序可以通过网络调用另一个程序的功能：读取客户地址、发一条短信、叫一辆出租车、开关一盏智能灯…… 调用方不需要知道对方的代码怎么写，只要被授权，几行代码就能用上。

整本教程用一个虚构的社交网络 SOCNET 做例子。我们从四个角度来认识 Web API。

① 它是给「程序」用的远程接口

提供 API 的一方叫提供者（provider），也叫服务端、后端； 调用 API 的一方叫消费者（consumer），也叫客户端。 一个 API 可以提供很多操作（operation），也可以被很多不同的程序同时使用。

② 它使用 HTTP 协议

Web API 里的「Web」来自 HTTP —— 就是浏览器打开网页用的那个协议。 消费者发出一个 HTTP 请求，说明「要做什么」以及「需要的数据」； 服务端处理完后回一个 HTTP 响应，说明「做得怎么样」以及「结果数据」。

任何主流语言都能发 HTTP 请求。下面用三种语言调用 SOCNET 的「分享」操作 —— 注意它们做的是同一件事， 这正是 Web API 的价值：消费者用什么语言、什么平台都无所谓。 

# pip install httpx
import httpx

response = httpx.post(
    "https://api.soc.net/statuses",
    json={"message": "Hello!"},                 # 请求体：需要的数据
    headers={"Authorization": "Bearer <token>"},
)

print(response.status_code)   # 201 —— 处理得怎么样
print(response.json()["id"])  # "12345" —— 结果数据

// Node 18+ / 浏览器 / Deno / Bun 都内置 fetch
const response = await fetch("https://api.soc.net/statuses", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: "Bearer <token>",
  },
  body: JSON.stringify({ message: "Hello!" }),  // 请求体：需要的数据
});

console.log(response.status);                   // 201 —— 处理得怎么样
const status: { id: string } = await response.json();
console.log(status.id);                         // "12345" —— 结果数据

// Java 11+ 自带 java.net.http
import java.net.URI;
import java.net.http.*;

HttpClient client = HttpClient.newHttpClient();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.soc.net/statuses"))
    .header("Content-Type", "application/json")
    .header("Authorization", "Bearer <token>")
    .POST(HttpRequest.BodyPublishers.ofString("""
        { "message": "Hello!" }
        """))                                    // 请求体：需要的数据
    .build();

HttpResponse<String> response =
    client.send(request, HttpResponse.BodyHandlers.ofString());

System.out.println(response.statusCode());      // 201 —— 处理得怎么样
System.out.println(response.body());            // {"id":"12345",...} —— 结果数据
ⓘ 为什么本教程只讲 REST

Web API 有好几种风格：REST、SOAP、GraphQL、gRPC……它们使用 HTTP 的方式各不相同。 本教程聚焦 REST API：它最常用，背后的架构原则也最扎实（第 4 章会讲）。 书里的大多数设计原则换到其他类型的 API 上同样成立；第 14 章会简单讨论什么时候该选别的。

③ 它是「实现」的接口，隐藏幕后细节

人们常把「提供 API 的那个程序」直接叫作 API，但严格说，API 只是那个程序露在外面的那一层。 可以把它想成餐厅：

SOCNET 的 App 开发者不需要知道后端用了几个微服务、什么数据库、人脸识别怎么做的。 他们只需要发一个 HTTP 请求，把消息和照片交过去，剩下的由实现处理。

下面这段服务端代码把「接口」和「实现」分开写了。请注意哪部分是消费者看得到的（路径、请求体、响应）， 哪部分是他们永远不该知道的（FriendDetector、MessageStore）。 

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

# ---------- 接口：消费者能看到的全部 ----------
class StatusCreate(BaseModel):
    message: str

class Status(BaseModel):
    id: str
    message: str

@app.post("/statuses", status_code=201, response_model=Status)
def share_status(body: StatusCreate) -> Status:
    # ---------- 实现：幕后细节，随时可以换 ----------
    friends = friend_detector.detect(body.message)   # 今天是自研，明天可能换成第三方
    saved = message_store.save(body.message, friends) # 今天是 Postgres，明天可能是别的
    return Status(id=saved.id, message=saved.message)

import { Hono } from "hono";

const app = new Hono();

// ---------- 接口：消费者能看到的全部 ----------
type StatusCreate = { message: string };
type Status = { id: string; message: string };

app.post("/statuses", async (c) => {
  const body = await c.req.json<StatusCreate>();

  // ---------- 实现：幕后细节，随时可以换 ----------
  const friends = await friendDetector.detect(body.message);   // 今天是自研，明天可能换成第三方
  const saved = await messageStore.save(body.message, friends); // 今天是 Postgres，明天可能是别的

  const status: Status = { id: saved.id, message: saved.message };
  return c.json(status, 201);
});

@RestController
public class StatusController {

    // ---------- 接口：消费者能看到的全部 ----------
    public record StatusCreate(String message) {}
    public record Status(String id, String message) {}

    @PostMapping("/statuses")
    @ResponseStatus(HttpStatus.CREATED)
    public Status shareStatus(@RequestBody StatusCreate body) {
        // ---------- 实现：幕后细节，随时可以换 ----------
        var friends = friendDetector.detect(body.message());   // 今天是自研，明天可能换成第三方
        var saved = messageStore.save(body.message(), friends); // 今天是 Postgres，明天可能是别的
        return new Status(saved.id(), saved.message());
    }
}
★ 本教程只讲「接口」的设计

后面所有章节讨论的都是消费者看得见的那一层长什么样，不讨论实现怎么写。 上面这样的代码只是为了让你把设计和日常编码对上号。这些设计原则与你用什么语言、什么架构无关 （不过实现上的限制有时会反过来影响设计，第 14 章会讲）。

④ 它是给「别人」用的

API 的使用者几乎从来不只是作者自己。按「谁能用」可以分三类；另外 internal / external 这两个词有时指「谁能用」， 有时指「暴露在哪个网络上」，和别人沟通时最好先对齐含义。

为什么设计很重要

如果糟糕的 API 是一台厨房电器

想象一台叫「厨房雷达（Kitchen Radar）」的电器：面板上只有一个写着 MAG. 的按钮，按住才工作，松手就停。 翻说明书才知道它其实是用来加热食物的 —— MAG. 是磁控管（magnetron）。想用中火？按住 7 秒、松开 7 秒，自己掐表循环。

这台机器的根本问题是：它没有回应用户的需求。人们想要的是「加热食物」，不是「打开磁控管」。 说明书救不了它。很荒谬对吧？可现实中长得像厨房雷达的 API 比比皆是 —— 私有的、给伙伴的、公开的都有。

糟糕的设计会伤害谁

受害者他们会说……背后的设计问题
开发者与架构 「sts 这个字段是什么？」
「为什么 createdAt 和 fromDate 的日期格式不一样？」
「HTTP 说成功了，可返回的数据里是个错误！」
「只给一句 Invalid request，我怎么知道哪里错了？」 		命名晦涩、不一致、HTTP 用错、缺数据缺操作、暴露内部逻辑导致客户端重复造轮子
安全与基础设施 「用户 A 能读到用户 B 的私信，这正常吗？」
「时间线接口有时要转很久，还会吐出一段 Java 内存溢出的堆栈。」 		设计时没定义清楚「谁能看什么」；没有分页，一次返回整张表；泄露内部信息
最终用户与第三方 「上次更新之后 App 一打开时间线就崩！」
「我给朋友转了 10 块，他收到了 1000 块！」
「受够了，我要取消订阅。」 		不向后兼容的修改（sts 改名为 status）、悄悄改变含义（元变成分）、流程复杂

错过里程碑、功能缩水、Bug 频发、技术债累积、客户流失 —— 这些最终都会变成组织的真金白银损失。

好设计带来的回报

🎯

正好满足需求

「这个 API 提供的操作和数据正是我要的。」

🔮

不看文档也能猜对

一致、直观，用过一个操作就会用下一个。

🧩

可互操作

不同 API 之间的数据能直接对上，代码可以复用。

🔄

解耦、易演进

把自研人脸识别换成第三方服务，现有 App 毫无感知。

💡 别担心

如果你现有的 API 长得像厨房雷达，也不必绝望。修正永远不晚，这套教程就是为此准备的。

什么时候需要设计

  • 任何新 API 都要设计，包括私有 API。 你写的私有 API 远多于公开 API，它们是练手的最佳机会；而且公开 API 往往建在私有 API 之上，底层一团糟，上层也救不回来。 Amazon 在 2002 年就要求所有团队通过「服务接口」沟通，并按「随时可以对外开放」的标准来设计 —— 这是它后来成功的关键之一。
  • 任何修改都要设计。 随手把 sts 改名成 status，没更新的客户端就会崩溃。要么避免破坏性修改，要么在充分评估后有意为之（第 15 章）。
  • 设计发生在「决定做一个 API」之后、「写代码实现」之前。

谁来设计

设计一个 API 需要三种角色坐在一起（可以是同一个人，也可以是三个人）：

✏️

API 设计者

把模糊的需求、复杂的业务和晦涩的系统，转化成一个可实现、好用的 HTTP 接口。开发、架构师、产品经理、测试、技术写作者都可以胜任。

📚

领域专家（SME）

懂这块业务：银行、物流、CRM……你不必是专家，但要会向专家提问。

🔧

IT 系统专家

知道系统的真实限制。比如 SOCNET 识别一段 10 秒视频里的人脸要 1 分钟 —— 这会直接影响设计。

此外还有一圈利益相关者会影响设计：提出需求的人、消费者、安全专家、同行评审者。 经验法则：安全方面的意见通常直接采纳；消费者的要求要仔细掂量 —— 照单全收可能会得到一个只有他一家能用的 API。

怎么设计：四个步骤 × 四个层次

这是整本教程的地图。步骤回答「先做什么后做什么」，层次回答「每次只关注一类问题」。 两者都不是严格线性的，实际工作中会来回跳。

四个步骤

  1. 识别 API 能力：分析用户需求，用自然语言列出用例、步骤和所需的操作。例如用例「分享一条状态」包含步骤「上传照片」「发送状态」。同一个操作可以服务多个用例。
  2. 设计编程接口：找出关键业务概念（用户、状态），把「分享一条消息」翻译成 POST /statuses，再为输入输出建模（Status 有一个字符串类型的 message）。
  3. 描述编程接口：用标准的 API 描述格式（OpenAPI）把设计写成蓝图。它既方便和各方讨论，也能直接生成代码和文档。
  4. 丰富设计产物：往蓝图里补充细节（message 最长 140 字符），或增加新产物（模拟尚未开发的 API 的 Mock）。

四个层次

  1. 做对的事、且足够通用。同一个 SOCNET 后端 API 要能同时服务网站和 App，以后做「智能冰箱版」也不用改。
  2. 好用、可互操作。字段叫 status 而不是 sts；错误信息要能指导修复；两个 API 用同一种用户 ID。
  3. 纳入约束。只追求好用，可能得到一个无法实现、容易出故障甚至危险的设计：
    • 安全：设计时就要明确「谁能看什么」。
    • 效率：时间线别一次返回全部数据。
    • 上下文：人脸识别要一分钟，就不能设计成一次调用立即返回，而要设计成「发起任务 → 查询进度 → 取结果」。
    • 修改：评估改名的影响，并让设计本身便于扩展。
  4. 有章法、持续改进的流程。设计中的大量决定会反复出现（用 fromDate 还是 from_date？用哪种分页？）。把它们沉淀成设计指南、可复用组件和自动化检查，组成你的「API 设计工具箱」。
🤖 关于 AI

AI 很可能成为设计工具箱里的重要一员，但它会给出错误、不准确或不完整的答案。 先掌握设计原则，你才知道什么时候该用 AI、该喂给它什么信息、以及怎么判断它的产出是否真的「做对了事、好用、安全、高效」。

本章小结

  • Web API 是程序之间通过网络、使用 HTTP 协议通信的软件接口；本教程聚焦 REST API。
  • API 是实现的接口，理想情况下应隐藏实现细节。
  • API 按开放程度分为私有、合作伙伴、公开三类；三类都需要认真设计。
  • 设计的好坏会影响开发效率、安全、基础设施成本、用户体验，最终影响收入。
  • 新建 API 要设计，修改 API 也要设计；设计发生在决定做 API 之后、编码之前，并且是迭代的。
  • 设计需要 API 设计者、领域专家、IT 系统专家三种角色协作，并听取（但不盲从）各方意见。
  • 四个步骤：识别能力 → 设计接口 → 描述接口 → 丰富产物。
  • 四个层次：做对的事 → 好用可互操作 → 纳入约束 → 持续改进的流程。

  2. 挑一台你家里的电器，想象把它的面板设计成「厨房雷达」风格：它会暴露哪些内部零件？用户原本的需求是什么？
