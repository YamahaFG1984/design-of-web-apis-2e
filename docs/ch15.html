第 15 章

修改 API

购物公司想让商品支持多个分类，于是打算把字符串属性 category 换成数组 categories。 这意味着所有调用方都得改代码；没改的会因为找不到 category 而崩溃。内部应用好说，要求所有合作方配合就难了。 更糟的是悄悄上线、谁都没通知。API 一旦被使用就很少一成不变 —— 这一章讲如何改得不伤人，以及如何从一开始就设计得经得起改。

本章目标

  • 分清破坏性修改和向后兼容的修改：输出、输入、路径、方法、状态码、流程
  • 知道「看不见的契约」，以及如何防止意外的修改
  • 识别安全方面的破坏性修改
  • 为 API 选择版本号方案和它在请求中的表示方式
  • 权衡破坏性修改的影响与收益
  • 掌握可扩展的设计模式
  • 用 OpenAPI 记录版本、弃用和变更日志

修改 API 时会发生什么

修改 API 就是「照常设计」：识别新的或变化的能力，设计接口，保证好用、安全、高效、适配上下文。 但多了一层约束：修改可能破坏已有的消费者。

假设要给购物 API 加上多币种支持。漂亮的做法是把数字类型的 price 换成带 value 和 currency 的对象。 草率上线的后果：读商品的消费者崩溃（期望数字，拿到对象）；加商品的消费者被拒绝（服务端期望对象，收到数字）。应对的选择有三个：

同步发布

只有一个内部消费者时，让它的更新和新 API 一起上线。合作方一多就行不通。

新旧版本并行

同时暴露两个版本，让消费者按自己的节奏迁移。代价是要维护两套。

改成向后兼容的设计

保留 price 不动，新增一个带默认值的 priceCurrency。没那么优雅，但谁都不受影响。

更好的初始设计本可以避免这次取舍。这很让人沮丧，但要学会接受：用的人越多、场景越多，就会发现越多问题。

⚠ 适用于任何 API

无论它是公开的还是私有的，是庞大的单体还是小小的微服务，是 REST 还是别的类型 —— 修改都必须谨慎。

破坏性修改 vs 向后兼容的修改

破坏性修改（breaking change）是指消费者必须改代码才能继续使用 API 的修改。它可能导致明显的报错，也可能导致更可怕的静默错误 —— 没改的代码照样能处理变了的数据，只是结果不对。

修改输出

消费者的代码要读这些数据。规则：只能增加，或者在原有范围之内调整。对成功响应和错误响应、响应头和响应体都适用。

破坏性向后兼容
重命名数据（amt → amount）新增数据
移动数据（merchantName 挪进 merchant 对象）把可选数据变成必返
删除必返的数据删除可选数据（消费者本来就得处理它不存在的情况）
把必返的数据变成可选缩短字符串的最大长度
改变类型（数字 → 字符串）
改变格式（时间戳 → ISO 8601）
改变含义（分 → 元）
给枚举增加取值
增大字符串的最大长度（消费者的数据库列可能就是按原长度建的）

错误响应同理：把错误列表从 items 改名为 errors，消费者可能崩溃，也可能看不到错误； 把具体的类型 MISSING_SOURCE 换成通用的 REQUIRED，依赖旧值的代码会失效。响应头也一样：一直返回的 Location 突然不返回了，就是破坏。

修改输入

没更新的消费者会按旧版的定义发数据。规则：只能放宽。把必填变可选、新增可选项、扩大允许的范围。 对请求体、请求头、查询参数、路径参数都适用。

破坏性向后兼容
新增必填数据新增可选数据（它内部可以有必填项 —— 旧消费者根本不会发它）
把可选数据变成必填把必填数据变成可选
重命名、移动数据删除数据（旧消费者还会发，服务端忽略即可 —— 第 9 章的「宽进」）
改变类型、格式、含义
收紧数值范围（提高下限、降低上限）放宽数值范围
收紧字符串长度放宽字符串长度
从枚举里删除取值给枚举增加取值
⚠ 最危险的是「不报错」的破坏
  • 改变输入值的含义。服务端把金额从「分」改成「元」，没更新的消费者发来 1000（分），服务端按 1000 元转了出去。
  • 改参数名。把 pageIndex 改名为 page：调用 ?pageIndex=2 的消费者不会报错，只是永远拿到第一页。
  • 加分页或减小页大小。消费者拿到的数据变少了，却可能毫无察觉。
  • 把 If-Match 设为必填（第 12 章）：所有没更新的消费者都无法再做任何修改。

修改路径、操作、状态码、流程

修改破坏性向后兼容
路径 /transaction → /transactions；改变层级结构 → 404。（可以用 308 Permanent Redirect 缓解，但消费者常常没配置跟随重定向） 改路径参数的名字（它不出现在请求里）；让路径参数接受更多种值（账号或 IBAN 都行）
枚举型路径参数 删除或改名（office → professional）→ 404 新增取值（vacation）
操作 / HTTP 方法 删除操作；把 PATCH 换成 PUT → 405 Method Not Allowed 或 404 新增操作（旧消费者不会调它）
状态码 把一个状态码换成同类的另一个（200 → 201、400 → 422）；新增状态码 不再返回某个状态码（比如消除了夜间维护，就不再有 503）
操作流 在流程里加一步（转账后新增「用短信验证码确认」）—— 旧消费者以为转完了，其实没有，而且没有任何报错

为什么 200 改成 201 也算破坏？HTTP 规范说客户端应该按类别处理不认识的状态码，但现实中消费者的代码常常写成 if (response.status !== 200)。

看不见的契约

📚 海勒姆定律（Hyrum's Law）

「当一个 API 有足够多的用户时，你在契约里承诺了什么已经不重要：系统所有可被观察到的行为，都会有人依赖。」

  • 有消费者靠数组里的位置而不是地址类型来取户主的家庭住址。哪天数组顺序变了，他就拿到了错的地址。我们从未承诺过顺序，按类型查才是对的 —— 这次是他的问题。
  • 限流由 API 网关处理，所以银行 API 的文档里没写 429（「网关不归我们管」）。但 429 响应的格式一变，消费者照样崩溃 —— 这次是我们的问题。合作方和公众不关心它在你们组织里归哪个团队。
  • 响应时间也是契约的一部分：新加的业务逻辑让某个操作变慢，可能触发消费者的超时。

防止意外的修改

每次修改都对比新旧两版 OpenAPI 文档，确保所有改动都被列出并评估过。普通的文本 diff 不够用（文档结构重排了但接口没变，它也会报一大堆差异）， 要用专门的 OpenAPI diff 工具 —— 它们能指出哪些是安全的、哪些是破坏性的，还能接入 CI/CD，发现意外的破坏就阻止部署。 （在 tools.openapis.org 搜「diff」。）

但这类工具看不到文档之外的东西：响应的行为、看不见的契约。所以还要以 OpenAPI 文档为准绳，对实现做充分的测试。

在消费者一侧：宽容的读取

理解了上面这些，也就知道怎么写出不容易被破坏的客户端代码。提供者无法强求消费者这样写，但如果你自己就是消费者，值得这么做： 

import httpx

r = httpx.post(f"{base}/transfers", json=transfer)

# ✗ 脆弱：只认 200。提供者把它改成更准确的 201，这里就炸了
if r.status_code != 200:
    raise RuntimeError("Transfer failed")

# ✓ 宽容：按类别判断
if not r.is_success:                      # 任何 2XX 都算成功
    handle_error(r)


data = r.json()

# ✗ 脆弱：未知的枚举值直接崩溃
LABELS = {"executed": "已执行", "delayed": "已预约"}

# ✓ 宽容：未知值有兜底
label = LABELS.get(data["status"], "处理中")

# ✗ 脆弱：依赖没人承诺过的顺序
home = owner["addresses"][0]

# ✓ 宽容：按契约里明确的属性去找

# ✓ 用 Pydantic 解析时：忽略不认识的属性（默认行为），而不是 extra="forbid"

const response = await fetch(`${base}/transfers`, { method: "POST", body: JSON.stringify(transfer) });

// ✗ 脆弱：依赖没人承诺过的顺序

// ✓ 宽容：让 Jackson 忽略不认识的属性 —— 提供者新增字段不会让反序列化失败

安全方面的修改

修改后果怎么办
替换或移除安全方案（把 API Key 换成双向 TLS）破坏性，但为了安全往往无法避免过渡期内两种方式并存，让消费者切换
把操作从一个作用域挪到另一个（「列出转账」从 account:all 挪到 transfer:read）破坏性：消费者认证时要声明用哪些作用域先加到新作用域，等消费者都更新了再从旧的里移除
往现有作用域里加操作（把「删除账户」加进 user:account:all）不破坏消费者，但可能制造安全漏洞：面向户主的应用突然能调用管理员操作了按第 12 章的原则重新审视

给 API 一个版本号

版本控制不只是挑一个名字或数字。它是一套策略：什么时候、怎样做修改；如何处理破坏性修改；同时支持几个旧版本、各支持多久。 这些由产品负责人和架构师决定，但会约束我们的设计。

接口的版本 ≠ 实现的版本

我们版本化的是消费者看得到的东西 —— 接口契约，而不是实现代码。

修改API 版本实现版本
初始版本：账户信息相关的操作v1v1
修复了一个访问控制的 Bugv1（接口没变）v2
新增转账相关的操作v2v3
重构转账的内部实现（改用消息队列）v2（接口没变）v4
新增开户申请相关的操作v3v5

版本标识符：语义化版本 vs 日期

修改类型语义化版本日期版本
初始版本：列出账户、读取账户1.02023-10-02
新增「列出交易」兼容1.12023-11-06
交易里新增商户名称和地址兼容1.22024-01-08
路径里的账号换成 IBAN破坏2.02024-02-05
读取账户不再返回银行卡列表破坏3.02024-03-04
  • 语义化版本的完整形式是 主版本.次版本.补丁。破坏性修改递增主版本，兼容的修改递增次版本。 API 的版本不用补丁号 —— 那是给 Bug 修复用的，而 Bug 修复只发生在实现里。所以 API 版本是 1.0、1.2 这样的两段。
  • 日期版本能看出哪个更新，但看不出改动的性质，必须去查文档。

默认推荐语义化版本：它直接说明了改动的类型，也最通行。如果发布频繁或有固定节奏（比如每季度），可以考虑日期版本。

版本在请求里怎么表示

位置示例评价
路径GET /v2/accounts、/banking/v2/accounts默认推荐 实现和使用都最简单，所以也最常见。只放主版本（2.1 对 2.0 是兼容的，不需要区分）
自定义请求头Version: 2可以考虑。但开发者经常忘了带，然后花很久排查为什么结果不对
自定义媒体类型Accept: application/vnd.bnk.v2+json可以，但限制了内容协商（想要 PDF 格式的 v2 怎么办？），实现也更复杂
媒体类型参数Accept: application/json;version=2罕见
域名api-v2.bnk.com罕见
查询参数GET /accounts?type=current&version=2不推荐 把业务数据（筛选条件）和元数据（版本）混在了一起
消费者配置（带外）请求里不带版本，由提供者按消费者的配置决定适合承诺长期支持很多旧版本的公开 API；应同时允许在请求里显式指定
💡 从第一天就定下来

不要等到第一次破坏性修改才决定版本方案。一开始就定好，消费者知道将来会怎样，过渡也更顺。 这不意味着你一定会改版本号 —— 路径里的 /v1 可能永远是 /v1。而且这通常不是每个 API 各自决定的，而是整个团队或组织共用的策略。

不要对 API 的局部做版本控制

技术上可以只给某个资源或某个操作升版本（/v2/transfers、/v3/transfers、/v1/sources、/v2/sources/{id}/destinations……）。 别这么做。完成一次转账要依次调用付款方、收款方、转账三个资源上的操作 —— 消费者（和你自己）怎么知道各资源的哪个版本能搭配使用？ 这种想法通常源于把「资源」和「API」混为一谈，或者 API 太大、该拆分了（第 11 章）。

谨慎地做破坏性修改

从 1.1 升到 1.2 没有后果；升到 2.0 则必须权衡。用五个问题来评估：

  1. 有多少消费者受影响？他们是谁？ 只有自己团队的一个应用：好办。几十个内部应用：要花组织很多钱和时间。只有两个合作方：数量不多，但他们是客户。
  2. 消费者真的在用我们要破坏的东西吗？ 看作用域（没有相关作用域的肯定不受影响）；看日志（有作用域不代表真的在调 —— 但注意日志保留期：只在 12 月被大量使用的年度统计操作，在 11 月的六个月日志里看不到）； 实在不行只能请消费者查代码（日志不会告诉你消费者怎么使用响应体里的数据）—— 这对合作伙伴和公开 API 基本不可能。
  3. 能同时暴露多个版本吗？ 两种方式：每个版本一套实例（成本高，而且 v2 改了数据库结构后 v1 的实例可能根本跑不了）；或者一套实例支持多个版本（推荐）—— 用适配器把 v1 的请求转成 v2 的、处理完再把 v2 的响应转回 v1 的。但版本多了、改动大了，适配器也会变复杂，有些转换甚至做不到。
  4. 版本策略有什么约束？ 比如「支持最近两个主版本；破坏性修改每年一次；季度发布只能含兼容的修改」。
  5. 破坏性修改的目的是什么？ 合作方强烈要求多币种支持 → 值得：让现有客户满意，吸引新客户，带来收入。 只是想把「读取本年度看板」换成设计更好的「读取年度看板」→ 不值得：保留旧操作，新增一个更好的。

一套实例支持多个版本

下面演示「适配器」的思路：实现只有一份（按 v2 的模型工作），v1 的路由在入口和出口各做一次转换。同时给 v1 的响应加上 Sunset 头（RFC 8594），预告它将在何时下线： 

from fastapi import APIRouter, FastAPI, Response

app = FastAPI()
v1 = APIRouter(prefix="/banking/v1")
v2 = APIRouter(prefix="/banking/v2")

# ---- v2：当前的模型。price 是带币种的对象 ----
@v2.get("/products/{product_id}")
def read_product_v2(product_id: str) -> dict:
    return products.get(product_id)
    # {"id": "p1", "name": "...", "price": {"value": 49.99, "currency": "USD"}, "categories": ["BD"]}

# ---- v1：适配器。复用 v2 的实现，把结果转换成旧的形状 ----
def to_v1(product: dict) -> dict:
    return {
        "id": product["id"],
        "name": product["name"],
        "price": product["price"]["value"],          # v1 里 price 是数字
        "category": product["categories"][0],        # v1 里只有一个分类
    }
    # 注意：非 USD 的商品没法无损地表达成 v1 —— 有些转换是做不到的

@v1.get("/products/{product_id}")
def read_product_v1(product_id: str, response: Response) -> dict:
    # 预告旧版本的下线时间；也可以加 Link 头指向迁移指南
    response.headers["Sunset"] = "Sat, 31 Aug 2024 23:59:59 GMT"
    response.headers["Link"] = '<https://developer.shopp.ing/migrate-to-v2>;rel="sunset"'
    return to_v1(read_product_v2(product_id))

app.include_router(v1)
app.include_router(v2)

import { Hono } from "hono";

type ProductV2 = {
  id: string; name: string;
  price: { value: number; currency: string };     // v2：带币种的对象
  categories: string[];                           // v2：多个分类
};
type ProductV1 = { id: string; name: string; price: number; category: string };

// ---- v2：当前的模型 ----
const v2 = new Hono();
v2.get("/products/:productId", (c) => c.json(products.get(c.req.param("productId"))));

// ---- v1：适配器。复用同一份实现，把结果转换成旧的形状 ----
const toV1 = (p: ProductV2): ProductV1 => ({
  id: p.id,
  name: p.name,
  price: p.price.value,                           // v1 里 price 是数字
  category: p.categories[0],                      // v1 里只有一个分类
});
// 注意：非 USD 的商品没法无损地表达成 v1 —— 有些转换是做不到的

const v1 = new Hono();
v1.use("*", async (c, next) => {
  await next();
  // 预告旧版本的下线时间；也可以加 Link 头指向迁移指南
  c.header("Sunset", "Sat, 31 Aug 2024 23:59:59 GMT");
  c.header("Link", '<https://developer.shopp.ing/migrate-to-v2>;rel="sunset"');
});
v1.get("/products/:productId", (c) => c.json(toV1(products.get(c.req.param("productId")))));

const app = new Hono();
app.route("/banking/v1", v1);
app.route("/banking/v2", v2);
export default app;

record Price(BigDecimal value, String currency) {}
record ProductV2(String id, String name, Price price, List<String> categories) {}   // 当前的模型
record ProductV1(String id, String name, BigDecimal price, String category) {       // 旧的形状
    static ProductV1 from(ProductV2 p) {
        // 注意：非 USD 的商品没法无损地表达成 v1 —— 有些转换是做不到的
        return new ProductV1(p.id(), p.name(), p.price().value(), p.categories().get(0));
    }
}

// ---- v2 ----
@RestController
@RequestMapping("/banking/v2/products")
class ProductControllerV2 {
    @GetMapping("/{productId}")
    ProductV2 read(@PathVariable String productId) {
        return products.get(productId);
    }
}

// ---- v1：适配器。复用同一份实现，把结果转换成旧的形状 ----
@RestController
@RequestMapping("/banking/v1/products")
class ProductControllerV1 {
    @GetMapping("/{productId}")
    ResponseEntity<ProductV1> read(@PathVariable String productId) {
        return ResponseEntity.ok()
            // 预告旧版本的下线时间；也可以加 Link 头指向迁移指南
            .header("Sunset", "Sat, 31 Aug 2024 23:59:59 GMT")
            .header("Link", "<https://developer.shopp.ing/migrate-to-v2>;rel=\"sunset\"")
            .body(ProductV1.from(products.get(productId)));
    }
}

Sunset 头只有在消费者或其基础设施真的去检查它时才有用。提供者自己出的 SDK 通常会据此在日志里打警告。

攒着取舍，还是定期破坏

尽量停留在 v1

作者通常建议：尽可能长久地留在版本 1，把领域覆盖全、收集反馈、弄清什么有效。 只有当期待已久的新功能足以抵消成本时才迁移到版本 2。版本 2 常常永远不会来 —— 那就与一个不完美但够用的 API 共存。

但要看到长期代价

消费者越多，修正越难。取舍越攒越多，API 越来越复杂，新的消费者集成起来越来越慢、越来越没吸引力。 严格的版本策略能强制迁移，但频繁的破坏性更新会让合作方和公众用户厌烦，转投更稳定的竞品。

💡 务实一点

对私有 API：如果确定某个破坏性修改影响不到任何人，可以只升次版本号，免得所有消费者都要改基础 URL（/v1 → /v2）。这在合作伙伴或公开 API 上有风险。 另一个选择是保留想删的元素，但在 OpenAPI 里标记为已弃用（见本章末尾）。

可扩展的设计

破坏性修改和别扭的取舍并非宿命。好的初始设计能让将来的修改影响更小，甚至根本不需要修改。

之前学的已经在帮我们了

  • REST 的统一接口（第 4 章）：建立在粒度合适的业务概念上的 API 不容易需要破坏性修改；有了内容协商，新增 CSV、PDF 等格式毫无影响。
  • 拿来即用的数据（第 8 章）：金额带着币种，消费者就不会把「默认是欧元」硬编码进代码。
  • 接受多余的输入（第 9 章）：操作不因多余的数据报错，将来删除某个输入项就是兼容的。
  • 灵活的流程（第 10 章）：不绑定 UI、可以任意顺序收集数据的流程，以后很少需要改。
  • 大小合适的 API（第 11 章）：范围小、消费者少的 API 各自演进，远比一个无所不包的大 API 容易。

从过去的决定里学习

「转账」操作最初只处理立即转账，返回一个布尔值 executed。后来加了预约转账，一个布尔值不够用了：现在有「已执行」「用户预约的」「因系统维护而推迟的」三种状态。 不能把 executed 换成 status（破坏性），只能保留它并新增 status。不够漂亮，但能用。教训是：下次想用布尔值时，先多想一步。

💡 建一份「已知设计问题」清单

发现问题就记下来。它能防止重蹈覆辙、提示哪些地方需要更明确的指南（第 16 章）；如果 v2 真的到来，也能立刻知道要修什么。

六个可扩展的设计模式

⚠ 别为了想象中的未来过度设计

可扩展不等于「超级通用但超级复杂、覆盖一切永远不会发生的可能」。不要因此忽略设计的其他方面，尤其是满足需求和好用。

用 OpenAPI 记录修改

清晰、完整的修改记录，是相关方评估影响、实现者更新代码、消费者决定是否要改的依据。

版本号

openapi: 3.1.0
info:
  title: Banking API
  version: "1.2"          # API 的版本；加引号，否则会被解析成数字
servers:
  - url: /banking/v1      # 如果版本在路径里，主版本变化时记得更新这里

想同时追踪文档本身的修订（只是澄清了描述、重组了 schema，接口没变），可以借用补丁号：version: 1.2.1。私有 API 通常不需要这么细。

⚠ 从代码生成的文档

代码优先生成的 OpenAPI 文档，info.version 里可能是实现的版本（甚至是构建号），而不是 API 的版本。查一下生成器的文档，把它覆盖掉。

标记弃用

info:
  title: Banking API
  version: "1.2"                    # 只升次版本：弃用不是破坏性修改
paths:
  /current-year-dashboard:
    get:
      deprecated: true              # 不应再使用，但为向后兼容而保留
      ...
components:
  schemas:
    Account:
      properties:
        cards:
          deprecated: true
          type: array

操作、参数、响应头、属性都可以标 deprecated。 把文档提供给消费者时，甚至可以直接隐去已弃用的元素：老消费者继续用，新消费者在文档里看不到，也就不会开始用（不过输出数据在实际调用时仍然可见）。

变更日志

所有 description 都支持 Markdown，可以直接把变更日志写进去；再用 tags 把本次改动的操作标出来，文档工具会据此分组：

info:
  title: Banking API
  version: "1.2"
  description: |
    # Changelog

    - Version 1.1:
      - Added owners list on Read account.
    - Version 1.2:
      - Added cards list on Read account.
      - Deprecated current year dashboard; use Get dashboard instead.
paths:
  /current-year-dashboard:
    get:
      tags:
        - All
        - Modified by v1.2          # 方便快速找到这个版本改动的操作
      deprecated: true
      description: |
        # Changelog

        - Version 1.2
          - Deprecated; use Get dashboard instead.
💡 让工具帮忙

用 OpenAPI diff 工具列出改动，再让 AI 把它们写成通顺的文字。但文档里看不到的改动 —— 响应行为的变化、看不见的契约 —— 仍需要手工补充。

本章小结

  • 修改 API 时照常设计：满足需求、好用、可互操作、安全、高效、适配上下文。
  • 向后兼容地修改输出：只新增数据，或在原数据的范围之内调整。
  • 向后兼容地修改输入：只把必填变可选、新增可选数据、放宽现有数据的范围。
  • 删除操作、替换状态码、修改流程步骤、修改安全方案都是破坏性的。修改作用域既可能破坏消费者，也可能造成安全漏洞。
  • 消费者会依赖一切可观察到的行为（海勒姆定律）。用 OpenAPI diff 工具和测试来防止意外的修改。
  • 接口契约的版本与实现的版本分开管理。
  • 首选最通行的语义化版本（它说明了改动的类型）；发布频繁或有固定节奏时可以考虑日期版本。
  • 首选最通行的路径级版本；也可以考虑自定义请求头；媒体类型版本会限制内容协商。不要对 API 的局部做版本控制。
  • 从一开始就确定版本方案及其表示方式。
  • 评估破坏性修改的影响：多少消费者、是谁、是否真的在用、有哪些技术或合约上的约束；再与它给消费者和组织带来的收益相权衡。
  • 接受设计上的取舍，尽可能长久地停留在版本 N；新功能足够有价值时再迁移到 N+1。
  • 可扩展的设计：拿来即用的数据、接受多余的输入、灵活的流程、避免无所不包的 API；体里用对象、同类数据归入数组、使用可解释的格式，并考虑对象数组优于原子数组、枚举优于布尔值、操作优于枚举。
  • 在 OpenAPI 文档里更新版本、标记弃用元素、在描述里写变更日志。
