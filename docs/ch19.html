第 19 章

丰富 API 设计产物

一路走来，我们积累了一批产物：填好的能力画布、OpenAPI 文档、设计指南（连同组件库和 lint 规则）。 它们合在一起，就是这个 API 的设计参考套件 —— 既是设计过程的支撑，也是交付给后续环节的成果。 最后一章讨论如何把它打磨得更有用：加概览、让模型更精确、配上示例、照顾实现者，以及要不要做 Mock 和测试。

本章目标

  • 知道设计参考套件里有什么，以及它在 API 生命周期各阶段怎么被使用
  • 用 info、externalDocs 和 tags 给 OpenAPI 文档加上概览
  • 用 JSON Schema 的约束关键字让数据模型更精确
  • 用 JSON Schema 和 OpenAPI 的示例机制说明数据和操作
  • 为实现者补充备注，并让文档更适合代码生成
  • 判断什么时候值得做 Mock、原型和功能测试

API 设计参考套件

设计参考套件（API design reference kit）是一组能够完整描述一个 API（接口）的产物和信息。 虽然「丰富设计产物」在流程图里排在最后一步，但它其实与前面几步并行：套件从设计的第一天就开始积累，随时可以补充。

各阶段怎么用它

  • 设计：需求、画布和 OpenAPI 文档让大家能讨论和评估设计；指南帮助我们做出好用、可互操作、可演进、高效的设计；Mock 或原型让人能「摸到」设计，尽早发现缺什么。
  • 开发：实现者据此准确地写代码和安全控制；可以从 OpenAPI 文档生成代码或用 JSON Schema 校验输入 —— 但记住实现应该返回完整的错误，而不只是基本的校验失败（第 9 章）。
  • 测试：开发、QA 和安全专家据此编写测试；OpenAPI 和 JSON Schema 的机器可读性可以自动生成一部分，但覆盖不了所有情况。
  • 部署：API 网关可以直接使用文档里的安全作用域和 schema。 但要留意：如果让网关在转发前就按 schema 把请求挡回去，实现精心准备的「一次报全、信息友好」的错误就没机会返回了。
  • 提供与消费：对公开或合作伙伴 API，它是技术写作者制作开发者门户的输入之一； 对私有 API，消费方的开发者多半只能直接用这份「毛坯」套件 —— 它远不如公开门户精致，但要么是它，要么什么都没有。
★ 量力而行

我们已有的画布、OpenAPI 文档和指南已经构成了一套扎实的套件，可以到此为止。下面的每一项增强都要问一句：在我们的情况下值得吗？ 套件不是公开 API 的最终文档（那是另一份工作），不要把它做过头。

用 OpenAPI 提供概览

描述 API，并链接到其他产物

openapi: 3.1.0
info:
  title: Banking API
  version: "1.0"
  summary: Manage accounts, transactions, and money transfers     # 名字说不清时加一句话
  description: |
    更长的说明可以写在这里（支持 Markdown）。

    # Links
    - [Needs](https://needs.url)
    - [API capabilities canvas](https://canvas.url)
    - [API design guidelines](https://guidelines.url)
externalDocs:                         # 如果 OpenAPI 文档不是所有产物的入口，就指向那个入口
  url: https://docs.url
  description: All documentation

这样 OpenAPI 文档就成了一个中心枢纽。大多数 OpenAPI 对象都支持 description 和 externalDocs —— 组件库里的每个组件都可以链接到指南的对应章节。

用标签按概念和用例组织操作

工具默认把操作显示成一长串扁平的列表，看不出 API 涉及哪些概念、能完成什么事。标签（tags）可以把操作分组；一个操作可以有多个标签： 

tags:                                 # 根级的 tags 列表决定各组的显示顺序
  - name: Concept - Owner
  - name: Concept - Transfer
  - name: Use Case - Transfer Money
    externalDocs:                     # 可以直接链接到画布里这个用例所在的行
      description: API capabilities canvas
      url: https://canvas.url?sheet=1&line=12
    description: |                    # 或者用 Markdown 描述用例的步骤
      1. List sources
      1. List source destinations
      1. Create transfer

paths:
  /transfers:
    get:
      summary: Search transfers
      tags:
        - Concept - Transfer
    post:
      summary: Create transfer
      tags:
        - Concept - Transfer
        - Use Case - Transfer Money   # 同一个操作出现在两个分组里
  /sources:
    get:
      summary: List sources
      tags:
        - Concept - Transfer          # 「转账」这个概念下不止 /transfers 一个资源
        - Use Case - Transfer Money
ⓘ 别在 OpenAPI 里硬写用例

在标签的描述里详细写用例的步骤是可以的，但工作量不小 —— OpenAPI 本来不是干这个的。 更省事的做法是只打标签，然后从带标签的 OpenAPI 文档生成一份 Postman Collection：它支持完整的请求/响应示例，API 上线后还能直接拿来调用。 或者使用 OpenAPI 组织推出的 Arazzo 格式来正式描述操作流（如果你的工具支持）。

让数据模型更精确

第 7 章只给属性定了类型，其余的约束（「金额大于 0」「币种是 USD 或 EUR」）都写在文字描述里 —— 只有人（和 AI）读得懂。 JSON Schema 有一批关键字可以把这些约束变成机器可读的，文档、代码生成、测试、Mock 工具都能用上。

要表达的约束关键字例子
数值范围minimum（≥）、exclusiveMinimum（>）
maximum（≤）、exclusiveMaximum（<）		年龄 12 ≤ age < 100：minimum: 12、exclusiveMaximum: 100
金额 > 0：exclusiveMinimum: 0（范围可以只有一端）
数组长度minItems、maxItems每页最多 100 条：maxItems: 100
1 到 3 个地址：minItems: 1、maxItems: 3
字符串长度minLength、maxLength姓氏 1–200 个字符
字符串格式pattern（正则表达式）账户 ID 形如 acc-12345：pattern: "^acc-[0-9]+$"
取值集合enumenum: [USD, EUR]
默认值default分页大小不传时为 100：default: 100
components:
  schemas:
    AccountId:
      type: string
      pattern: "^acc-[0-9]+$"         # acc- 后面至少一位数字
    Amount:
      required: [value]
      properties:
        value:
          type: number
          exclusiveMinimum: 0         # 必须大于 0
        currency:
          type: string
          enum: [USD, EUR]            # 只能是这两个值
          default: USD
    Owner:
      properties:
        lastName:
          type: string
          minLength: 1
          maxLength: 200
        age:
          type: integer
          minimum: 12
          exclusiveMaximum: 100
        addresses:
          type: array
          minItems: 1
          maxItems: 3
          items:
            $ref: "#/components/schemas/Address"
  parameters:
    PaginationLimit:
      name: limit
      in: query
      schema:
        type: integer
        minimum: 1
        maximum: 100
        default: 100
⚠ 三点提醒
  • 给 ID 加类型前缀（acc-、trf-）能让人一眼看出它标识的是什么。但只对新造的自定义 ID 这么做 —— 改动已有的、被多个系统共用的 ID，或者偏离既有标准，会破坏互操作性。
  • 如果范围或取值取决于业务逻辑或配置（动态的），仍然只能用文字描述；考虑提供一个操作来返回这些动态的值（第 10、15 章）。经常变化的取值集合也不要写成 enum。
  • 第一遍建模时专注于识别数据，用文字描述约束即可。这些 JSON Schema 细节可以留到第二遍。

从 schema 约束到代码里的校验

精确的 schema 可以直接转化成实现里的校验代码 —— 手写或由代码生成器生成。三种语言的对应写法： 

from typing import Literal
from pydantic import BaseModel, Field

class Amount(BaseModel):
    value: float = Field(gt=0)                              # exclusiveMinimum: 0
    currency: Literal["USD", "EUR"] = "USD"                 # enum + default

class Owner(BaseModel):
    lastName: str = Field(min_length=1, max_length=200)     # minLength / maxLength
    age: int = Field(ge=12, lt=100)                         # minimum / exclusiveMaximum
    addresses: list[str] = Field(min_length=1, max_length=3)   # minItems / maxItems

class Transfer(BaseModel):
    source: str = Field(pattern=r"^acc-[0-9]+$")            # pattern
    destination: str = Field(pattern=r"^acc-[0-9]+$")
    amount: Amount

# FastAPI 会据此自动校验请求，并把这些约束写进它生成的 OpenAPI 文档
# 查询参数同理：limit: int = Query(100, ge=1, le=100)

import { z } from "zod";

const Amount = z.object({
  value: z.number().gt(0),                                  // exclusiveMinimum: 0
  currency: z.enum(["USD", "EUR"]).default("USD"),          // enum + default
});

const Owner = z.object({
  lastName: z.string().min(1).max(200),                     // minLength / maxLength
  age: z.number().int().gte(12).lt(100),                    // minimum / exclusiveMaximum
  addresses: z.array(z.string()).min(1).max(3),             // minItems / maxItems
});

const AccountId = z.string().regex(/^acc-[0-9]+$/);         // pattern

const Transfer = z.object({
  source: AccountId,
  destination: AccountId,
  amount: Amount,
});

// 查询参数：limit 不传时为 100
const Pagination = z.object({
  limit: z.coerce.number().int().min(1).max(100).default(100),
});

import jakarta.validation.Valid;
import jakarta.validation.constraints.*;

enum Currency { USD, EUR }                                   // enum

record Amount(
    @NotNull @Positive BigDecimal value,                     // exclusiveMinimum: 0
    Currency currency                                        // default 在构造时处理（见下）
) {
    Amount {
        if (currency == null) currency = Currency.USD;       // default: USD
    }
}

record Owner(
    @NotNull @Size(min = 1, max = 200) String lastName,      // minLength / maxLength
    @Min(12) @Max(99) int age,                               // minimum / exclusiveMaximum（整数）
    @NotNull @Size(min = 1, max = 3) List<String> addresses  // minItems / maxItems
) {}

record Transfer(
    @NotNull @Pattern(regexp = "^acc-[0-9]+$") String source,        // pattern
    @NotNull @Pattern(regexp = "^acc-[0-9]+$") String destination,
    @NotNull @Valid Amount amount
) {}

// 查询参数：
// @RequestParam(defaultValue = "100") @Min(1) @Max(100) int limit

用示例说明数据和操作

文档工具能根据 schema 自动生成示例数据，但结果往往是 "string" 和 "lorem ipsum" 这类毫无帮助的占位符。 必要的时候，可以自己提供示例。

属性级：JSON Schema 的 examples

    Transaction:
      properties:
        label:
          type: string
          maxLength: 200
          examples:                   # JSON Schema 标准的写法：一个列表
            - Monthly saving
            - Seven Eleven, Tokyo

文档工具会把它们显示在属性的说明里，并用第一个值替换生成的示例数据里的 "lorem …"。

⚠ example 还是 examples

单数的 example 是 OpenAPI 特有的写法，从 3.1 起已弃用，规范建议用 JSON Schema 标准的 examples（复数）。 但有些工具对 examples 的支持还不稳定、对 example 反而更好 —— 先确认你的工具支持哪个。

参数、请求体、响应体、响应头：OpenAPI 的 examples

在这些元素的 schema 旁边，可以放一个 OpenAPI 的 examples 映射（注意：是映射不是列表）。每个示例有一个键、摘要、描述和值，工具支持得很好： 

paths:
  /transactions:
    get:
      responses:
        "200":
          description: Found transactions
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Transactions"
              examples:                       # 与 schema 同级
                NoTransaction:                # 示例的键
                  summary: No data found      # 文档工具常把它显示成标签页的名字
                  description: Not a 404!
                  value:                      # 值可以用 YAML 写，工具会转成 JSON
                    data: []
                Transactions:
                  summary: Data found
                  value:
                    data:
                      - id: trx-57645
                        amount: 123.4
                        label: Monthly saving
💡 写示例的省力办法
  • 把文档工具根据 schema 生成的示例复制出来，贴进 OpenAPI 文档，再改成真实的样子。
  • 把 schema 贴给 AI，让它生成几个示例。
  • 在 Spectral 规则集里启用内建规则 oas3-valid-media-example 和 oas3-valid-schema-example（第 18 章），自动检查示例是否符合它所说明的 schema。

共享示例

指南规定所有搜索操作在没有结果时返回 200 和空的 data。每个搜索操作的 data 元素类型不同，所以没法共享整个响应 —— 但「空结果」这个示例是一样的，可以定义在组件库的 components.examples 里： 

# ---------- library.openapi.yaml ----------
components:
  examples:
    SearchNoData:
      summary: No data found
      description: Not a 404!
      value:
        data: []

# ---------- banking.openapi.yaml ----------
              examples:
                NoTransaction:
                  $ref: "https://guidelines.intra/library.openapi.yaml#/components/examples/SearchNoData"

再配一条 lint 规则，要求所有搜索操作的 200 响应都引用这个示例 —— 它会时刻提醒大家：搜索不到东西不是 404。

把请求和响应的示例对应起来

让同一场景下的请求示例和响应示例使用相同的键和摘要，读文档的人就能把它们对上：

  /transfers:
    post:
      requestBody:
        content:
          application/json:
            examples:
              Success:                        # ← 相同的键
                summary: Success              # ← 相同的摘要
                value:
                  amount: 12
                  source: acc-12345
                  destination: acc-54321
      responses:
        "201":
          description: Money transfer done.
          content:
            application/json:
              examples:
                Success:
                  summary: Success
                  value:
                    id: trf-56789
                    amount: 12
                    source: acc-12345
                    destination: acc-54321
⚠ 设计阶段别在示例上投入过多

OpenAPI 里请求和响应的示例是分开存放的，数量一多就难以维护。需要大量完整的「请求 + 响应」示例时，Postman Collection 是更合适的格式。 但更重要的是：我们现在是在帮助人们理解设计，不是在写公开门户的文档。成套的真实示例，等实现完成后从实际的请求和响应里取，要容易得多。

💡 以示例为中心的设计流程

有些团队会采用另一种流程：分析完需求后，直接起草各个操作的请求和响应示例（比如用 Postman Collection）来支撑讨论。 它牺牲了一份独立而正式的事实来源，也会漏掉一些细节（哪些必填、哪些可选要到实现时才明确）；OpenAPI 文档改由代码生成，可能不如手写的完整，也用不上共享组件库。 但 linter 照样可以用，在实现过程中继续引导设计。是否采用取决于你的环境。

照顾实现者

把实现备注放进产物里

设计过程中会收集到一些只和实现有关的信息。与其另存一份文档，不如放在 OpenAPI 文档里对应的位置：

    Transaction:
      properties:
        label:
          type: string
          description: |
            A human-readable description of the transaction.

            ##### Implementation notes
            Use `label` instead of the `description` column in the TRA02 table.
    Account:
      properties:
        owners:
          type: array
          x-implementation-notes: Sort the owners list alphabetically.   # 或者用扩展属性
  • 写在 description 里，用一个小标题（如五级标题）与契约信息隔开，免得在文档界面里喧宾夺主；
  • 或者用 OpenAPI 的扩展机制：以 x- 开头的属性几乎可以加在文档的任何位置，普通的解析器会忽略它们；
  • 通用的实现提示（比如怎样实现游标分页）应该放在设计指南的相关章节，并在组件库的对应组件上加链接。
⚠ 对外发布前要清除

这些信息出现在私有 API 的文档里问题不大，但绝不能出现在给合作方或公众的文档里。如果套件是最终文档的基础，负责的人必须记得把它们删掉 —— 用 jq、yq 或几行脚本就能批量清理。

让文档更适合代码生成

如果代码生成是你们流程的一部分，有三件事可以做：

  • 标签：生成器通常按标签把操作分到不同的类、模块或文件里（可以指定用哪些标签、忽略哪些，比如前面的概念和用例标签）。
  • operationId：生成器默认根据方法和路径推断函数名，结果不一定好看，不同生成器之间也不一致。 给每个操作设一个 operationId（如 searchTransfers），生成器就会用它当函数名。可以启用 Spectral 内建的 operation-operationId 和 operation-operationId-unique 规则来保证它总是存在且唯一。
  • 克制地使用 JSON Schema：allOf 这类组合关键字（第 17 章）有些生成器处理不好，要么报错要么生成很别扭的代码。必要时避开它们 —— 代价是文档的精确性或组织性。

Mock 与原型

设计阶段让人能「调用」一下尚未开发的 API，常常能暴露出纸面上看不出的问题。

基础 Mock：从 OpenAPI 文档一键生成

用静态数据模拟 API。Microcks、Postman、Prism 等工具可以直接读取 OpenAPI 文档，根据 schema（越精确越好）或示例返回数据，几乎不需要配置。 有些工具还能按 schema 校验输入，不过返回的错误未必符合你的设计。

复杂 Mock：设计阶段慎做

模板、脚本、在请求之间保存数据……这些能让 Mock 表现得很逼真。完整的 Mock 以后很有用（消费方可以独立开发，公开 API 可以有演示环境）， 但我们现在的重点是设计，不是把生命周期里可能用到的所有产物都做出来。 

# 例：用 Prism 把 OpenAPI 文档变成一个 Mock 服务器
npx @stoplight/prism-cli mock banking.openapi.yaml

curl http://localhost:4010/transactions
# → 根据文档里的示例或 schema 返回数据
★ 需要逼真的行为时：做原型，而不是复杂的 Mock

让实现者（也许就是你）搭一个早期的实现原型：先是一个返回静态数据的骨架（可以从 OpenAPI 文档生成），随着设计的细化逐步加上逻辑。 设计定稿后，在这个原型上继续开发即可，一点不浪费。

功能测试

测试在生命周期里是独立的阶段，涵盖数据、行为、性能、安全等很多方面，由不同的人在不同的时间完成。 但在设计阶段，由最了解预期的人 —— API 设计者 —— 写一些功能测试放进套件，有时很有价值：

🧩

澄清复杂的逻辑

接口设计得很简单，背后的逻辑却不容易实现对。OpenAPI 加文字说明仍然说不清时，几个测试胜过千言万语。

🤝

让协作更顺畅

设计和开发由不同的团队甚至第三方完成时，随套件交付功能测试能减少后期才暴露的错误。这时最好用与实现代码无关的可移植格式（如 Postman Collection）。

📏

设计标准 API

由多个团队各自实现的标准 API（文件上传、健康检查）：提供现成的测试和一个参考实现，避免每个实现都重新发明一个有缺陷的版本。

这些早期测试只覆盖实现的一部分，开发、QA 和安全人员还要补充各自的测试。下面是一组针对「搜索交易」和「转账」的功能测试，它们把前面各章的设计决定变成了可执行的断言： 

import httpx, pytest

@pytest.fixture
def api():
    # 可以指向 Mock、原型，或正在开发的实现
    return httpx.Client(base_url="http://localhost:8080", headers={"Authorization": "Bearer test"})

def test_search_without_result_returns_200_and_empty_list(api):
    """指南：搜索不到东西不是 404"""
    r = api.get("/accounts/acc-12345/transactions", params={"date": "1900-01-01"})
    assert r.status_code == 200
    assert r.json()["data"] == []

def test_search_returns_default_pagination_metadata(api):
    """不传分页参数时，元数据要说明实际使用的默认值"""
    r = api.get("/accounts/acc-12345/transactions")
    pagination = r.json()["metadata"]["pagination"]
    assert pagination["size"] == 100
    assert len(r.json()["data"]) <= 100

def test_transfer_creation_returns_201_location_and_complete_resource(api):
    r = api.post("/transfers", headers={"Idempotency-Key": "t-001"},
                 json={"source": "acc-12345", "destination": "acc-54321", "amount": {"value": 12}})
    assert r.status_code == 201
    body = r.json()
    assert r.headers["Location"] == f"/transfers/{body['id']}"
    assert body["amount"]["currency"] == "USD"          # 没传币种时使用默认值

def test_invalid_transfer_returns_all_errors_at_once(api):
    """复杂逻辑：结构检查和业务规则检查要一次做完，报全所有错误"""
    r = api.post("/transfers", headers={"Idempotency-Key": "t-002"},
                 json={"source": "acc-12345", "amount": {"value": 999999999, "currency": "JPY"}})
    assert r.status_code == 422

💡 如果只带走几句话
  • 先弄清用户要做什么，再想接口长什么样 —— 形式追随功能。
  • API 是给别人用的。从外向内看，别把自己的内部暴露出去，也别为某一个消费者量身定做。
  • 一致是好用和可互操作的共同基础：尊重 HTTP，采用标准，和自己保持一致。
  • 安全、效率和可演进性是设计出来的，不是事后补上的。
  • 把决定记下来、沉淀成指南、交给工具检查 —— 把脑子留给真正需要判断的事。

本章小结

  • API 设计参考套件包含完整描述一个 API 的产物和信息，在设计、开发、测试、部署、提供与消费的整个生命周期里都有用。
  • 完整的套件覆盖：初始需求、用户、用例、操作、操作流、概念、操作的 HTTP 表示（路径、方法、数据、行为）、安全，以及实现方面的考虑。
  • 它包括需求描述、能力画布、OpenAPI 文档、设计指南（含组件库和 linter），以及可选的 API 模拟（Mock 或原型）和功能测试。
  • 画布、OpenAPI 文档和指南已经构成扎实的套件；可以增强，但要衡量投入。套件不是公开 API 的最终文档，却往往是私有 API 消费者唯一的资料。
  • 在 info.description 里加一组链接，让 OpenAPI 文档成为中心枢纽；或用 externalDocs 指向资料的入口。
  • 给操作打标签、用根级的 tags 列表排序，为概念和用例提供概览。
  • 用范围、长度、正则、枚举、默认值让 JSON Schema 更精确，这对理解、代码生成、测试和 Mock 都有帮助。
  • 用 JSON Schema 的 examples 说明单个数据；用 OpenAPI 带说明的 examples 映射说明参数、请求体、响应体和响应头；把共享的示例放进组件库。
  • 用 description 或自定义的 x- 扩展在需要的地方添加实现备注；对外发布前清除。
  • 如果代码生成是流程的一部分，相应地调整 OpenAPI 和 JSON Schema 的用法（标签、operationId、慎用组合关键字）。
  • 可以用 OpenAPI 文档生成一个基础的 Mock，帮助思考和讨论设计；需要更逼真的行为时，考虑做早期的实现原型。
  • 当需要向实现者澄清特定的逻辑，或者实现由另一个团队或第三方完成时，考虑在设计阶段创建功能测试。
