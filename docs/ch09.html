第 9 章

好用、可互操作的操作

想象一个购物 API：不管是属性名打错了、商品编号不存在还是商品缺货，「创建订单」一律只回一个光秃秃的 400 Bad Request。 开发者要花很久才能找到问题，最终用户则只能看到「无法提交订单」。 这一章把上一章的原则从数据扩展到整个操作：路径、输入、输出、列表功能、多种格式，以及最重要的 —— 错误处理。

本章目标

  • 设计一看就懂、甚至不看也猜得到的路径
  • 让输入容易提供：位置合适、与输出对应、尽量少
  • 返回拿来即用的成功响应
  • 为列表加上筛选、排序、分页，并返回元数据
  • 用内容协商支持多种格式和语言
  • 优雅地处理错误：少出错、状态码恰当、信息有用、机器可读、一次报全、采用标准
  • 避免把多个能力藏在一个操作里；全程保持一致

一致且标准

知道 GET /shops，就能猜出 POST /shops 和 GET /shops/{shopId}。GET 绝不会删东西。

和数据一样，这些是第二遍设计时处理的。第一遍别纠结 GET /shops/{shopId}/cars 能不能简化成 GET /cars。 本章继续用银行 API 做例子。

一看就懂、猜得到的路径

有意义的路径 + 遵守 HTTP

/accounts 一看就是账户列表，/act 则让人困惑。 配合标准方法，知道 /customers 是客户，就能猜到 GET /customers 是搜索、POST /customers 是新增。 POST /add-customer 虽然读得懂，却猜不到。

⚠ 只用这五个方法

HTTP 还定义了别的方法，但请只用 POST、GET、PUT、PATCH、DELETE（第 11 章会再加一个 OPTIONS），免得让开发者、他们的库和中间的 HTTP 设备措手不及。并且要尊重方法的含义：不要用 GET 修改数据。

可预测：每一段都有明确用途

路径应该像文件系统路径一样严格分层。访问文件夹里的文件时，文件夹的名字不会变：

不可预测问题可预测
/accounts 和 /account/{accountId}单复数不一，没法从前者拼出后者/accounts 和 /accounts/{accountId}
/savings/accounts/{accountId}
/checking/accounts/{accountId}		savings 这一段是资源？是标识符？说不清/savings-accounts/{accountId}
或者干脆 /accounts/{accountId}

统一使用这个模式：

/resources
/resources/{identifier}
/resources/{identifier}/sub-resources
/resources/{identifier}/sub-resources/{sub-identifier}

短，但要准确

短路径更易读，也意味着要提供的输入更少。办法是利用全局唯一的 ID，从路径末尾往前逐段审视：

让输入容易提供

1. 放在常规的、符合 HTTP 的位置

第 4 章讲过规则。这里看看不遵守会怎样。创建一笔转账需要付款账户、收款账户和金额：

做法样子问题
合适 资源表示放请求体POST /transfers + JSON 体—
随意 东一块西一块POST /transfers?source=12345
Destination: 54321
体里只有 amount		难懂、猜不到、不符合 HTTP
全放路径POST /transfers/12345/54321/100/EUR非层级数据塞进路径；参数堆叠后无法辨认；可选值怎么办？
全放查询参数POST /transfers?source=12345&destination=…资源不在请求体里，不符合 HTTP；看不出数据结构
全放请求头Source: 12345
Amount-Value: 100		非标准头；在日志和 API 客户端里常被隐藏

搜索同理。GET /accounts/12345/transactions?from=2024-01-01&minAmount=100 让标识符（路径）和修饰符（查询）一目了然。 如果全用查询参数（GET /transactions?accountId=12345），层级信息就丢了；还容易出现 GET /transactions?accountId=… 返回列表、GET /transactions?transactionId=… 却返回单个元素这种不一致。 如果全放请求体，就只能用 POST /search-transactions —— 资源没了，HTTP 统一接口带来的可预测性也没了。

2. 让输入与输出对应

第 5 章从完整模型派生输入，就是为了这个：开发者读过一次账户，就能猜出创建账户要提供什么； 看到搜索交易的结果里有 currency，就会去试 GET /transactions?currency=USD。

3. 要众所周知或标准的数据

/accounts/{iban}；货币筛选用 ISO 代码；转账请求体里的收付款账户用 IBAN。 标识符也不一定是不透明的随机串：一位客户每种类型的地址只有一个，那么地址的标识符就可以是固定的代码 —— /customers/1234/addresses/home。

4. 用默认值和服务端推断来减少输入

转账可以立即执行、指定日期执行，或者周期执行。最初的设计要求消费者填一大堆：

一笔立即转账：填 7 项
{
  "source": "FR123",
  "destination": "FR543",
  "amount": { "value": 100, "currency": "EUR" },
  "type": "immediate",
  "frequency": "none",
  "date": "2024-01-01",
  "endDate": "2024-01-01"
}
精简后：填 3 项
{
  "source": "FR123",
  "destination": "FR543",
  "amount": { "value": 100 }
}

// 延期转账：再加 "date": "2024-06-01"
// 周期转账：再加 "frequency": "monthly"
  • type 可以由服务端推断：只有三要素是立即转账；多了 date 是延期；有 frequency 是周期。
  • currency 可选，默认用付款账户的币种。
  • 周期转账的起止日期可选：默认从今天开始，没有 endDate 就一直执行到用户终止。
⚠ 不是什么都能让服务端代填

银行卡交易的发生时间不能由服务端用「收到请求的时间」来填 —— 这笔交易可能在几分钟甚至几小时后才传到服务端。把不该可选的数据设为可选，会得到不准确的数据。

返回拿来即用的成功响应

  • 用恰当的状态码和符合 HTTP 的位置。技术上可以自定义一个 299 Money Transfer Created，别人看到 2 开头也知道是成功 —— 但它会让开发者意外，还可能在他们的代码或中间设备上出问题。老老实实用 201 Created，数据放响应体。
  • 返回信息量足够的数据。

创建和更新时，返回完整的资源，而不是只有 ID。服务端总会生成或修改一些消费者没发过来的数据： 一笔「立即」转账的执行日期可能因为节假日而不是今天。

列表的筛选、排序与分页

一个账户可能有成千上万笔交易，而消费者通常只要特定的一小部分：「2024 年 3 月 6 日在餐厅或酒吧、金额在 100（含）到 400（不含）之间、从大到小排的前 10 笔」。 如果接口一次返回全部，这件事就很难做。

筛选

  • 筛选项对应返回的数据。交易有 date、category、amount，查询参数就叫同样的名字、用同样的类型： ?date=2024-03-06&category=restaurant&amount=100。嵌套属性用点号：amount.value。 不要按返回数据里没有的东西筛选 —— 消费者既猜不到这个筛选项存在，也无从核对结果。
  • 筛选要灵活。不只是等于某个值：
类型写法示例说明
枚举category=restaurant,bar或 category=restaurant&category=bar（第 7 章）
范围amount=gte:100&amount=lt:400
或 amount.gte=100&amount.lt=400		gt/gte/lt/lte 明确表达了含不含边界；minAmount/fromDate 这类写法则不明确
宽松的值date=2024-03、date=2024省去写月/年范围的麻烦
模糊匹配description=good匹配「包含 good」而不是「等于 good」
自由搜索q=nice restaurant last week跨多个属性的文本搜索
查询语法q=date:2024-03-06 AND (category:"restaurant" OR category:"bar")不要自创语法，借用现成的（如 Lucene）
  • 筛选项要节制，且必须可选。按需求挑选，不必每个属性都能筛；没人需要就不提供。 GET /accounts/1234/transactions 不带任何筛选应返回全部（的第一页）。 如果某个筛选项是必填的，多半是路径里少了一个标识符：GET /transactions?accountId=12345（必填）应该写成 GET /accounts/12345/transactions。

排序

sort=date:desc,amount:asc：先按日期降序，再按金额升序。sort 可选，并提供有用的默认顺序 —— 大多数人想先看最近的交易，所以默认就是 date:desc。方向也可选，默认 asc。

分页

方式写法含义
基于页码（索引）?page=3&size=10第 3 页，每页 10 条 → 第 21–30 条
基于游标?after=2501&size=25游标 2501 之后的 25 条

分页参数可选，并给出合理的默认值：一个月的交易适用于多数场景，而普通账户一个月大约 40 笔，所以默认返回前 40 条。 两种分页方式的取舍和页大小的优化见第 13 章。

ⓘ 标准不总是好选择

HTTP 有个 Range 头，理论上可以用来分页。但不建议：它本是为分段获取二进制数据设计的，中间设备可能把它去掉；分页参数和筛选排序参数分处两地也更难用；而且根本没人这么做。跟随通行做法。

返回元数据

消费者没传参数时，用了什么默认值？后面还有没有数据？把这些列表的元数据一并返回。 它不是业务数据，所以响应不再是一个裸数组，而是一个把两者分开的对象： 

HTTP/1.1 200 OK
Content-Type: application/json

{
  "data": [ ... ],
  "metadata": {
    "pagination": { "page": 1, "size": 40, "last": 10, "elements": 398 },
    "sort": [
      { "name": "date", "direction": "desc" }
    ],
    "filters": [
      { "name": "amount",   "range": { "min": 100, "exclusiveMax": 400 } },
      { "name": "date",     "value": "2024-03-06" },
      { "name": "category", "enum": ["restaurant", "bar"] }
    ]
  }
}

请求里没给 page、size、sort，元数据如实告知了实际使用的默认值，还附带了最后一页的页码和总条数。

实现一个带筛选、排序、分页的列表操作

from fastapi import FastAPI, HTTPException, Query

app = FastAPI()
SORTABLE = {"date", "amount"}

@app.get("/accounts/{account_id}/transactions")
def search_transactions(
    account_id: str,
    category: str | None = Query(None, description="逗号分隔，如 restaurant,bar"),
    date: str | None = Query(None, description="2024-03-06、2024-03 或 2024"),
    sort: str = "date:desc",                 # 有用的默认顺序
    page: int = Query(1, ge=1),              # 分页参数可选，带默认值
    size: int = Query(40, ge=1, le=200),
):
    items = repository.transactions_of(account_id)

    # ---- 筛选：参数名与返回数据的属性名一致 ----
    categories = category.split(",") if category else None
    if categories:
        items = [t for t in items if t["category"] in categories]
    if date:
        items = [t for t in items if t["date"].startswith(date)]   # 宽松匹配：前缀即可

    # ---- 排序：sort=date:desc,amount（方向默认 asc）----
    criteria = []
    for part in sort.split(","):
        name, _, direction = part.partition(":")
        direction = direction or "asc"
        if name not in SORTABLE or direction not in ("asc", "desc"):
            raise HTTPException(400, f"Unsupported sort '{part}'; sortable: {sorted(SORTABLE)}")
        criteria.append({"name": name, "direction": direction})
    for c in reversed(criteria):             # 从次要条件排到主要条件（稳定排序）
        items.sort(key=lambda t: t[c["name"]], reverse=c["direction"] == "desc")

    # ---- 分页 ----
    total = len(items)
    start = (page - 1) * size

    return {
        "data": items[start:start + size],
        "metadata": {                        # 告诉消费者实际用了什么（含默认值）
            "pagination": {"page": page, "size": size,
                           "last": max(1, -(-total // size)), "elements": total},
            "sort": criteria,
            "filters": [f for f in (
                {"name": "category", "enum": categories} if categories else None,
                {"name": "date", "value": date} if date else None,
            ) if f],
        },
    }

import { Hono } from "hono";

const app = new Hono();
const SORTABLE = ["date", "amount"] as const;
type Transaction = { id: string; date: string; amount: number; category: string };

app.get("/accounts/:accountId/transactions", (c) => {
  let items: Transaction[] = repository.transactionsOf(c.req.param("accountId"));

  // ---- 筛选：参数名与返回数据的属性名一致 ----
  const categories = c.req.query("category")?.split(",");
  const date = c.req.query("date");
  if (categories) items = items.filter((t) => categories.includes(t.category));
  if (date) items = items.filter((t) => t.date.startsWith(date));    // 宽松匹配：前缀即可

  // ---- 排序：sort=date:desc,amount（方向默认 asc）----
  const criteria = (c.req.query("sort") ?? "date:desc").split(",").map((part) => {
    const [name, direction = "asc"] = part.split(":");
    return { name, direction };
  });
  for (const { name, direction } of criteria) {
    if (!SORTABLE.includes(name as never) || !["asc", "desc"].includes(direction)) {
      return c.json({ message: `Unsupported sort '${name}:${direction}'; sortable: ${SORTABLE}` }, 400);
    }
  }
  items.sort((a, b) => {
    for (const { name, direction } of criteria) {
      const [x, y] = [a[name as keyof Transaction], b[name as keyof Transaction]];
      if (x !== y) return (x < y ? -1 : 1) * (direction === "desc" ? -1 : 1);
    }
    return 0;
  });

  // ---- 分页：参数可选，带默认值 ----
  const page = Number(c.req.query("page") ?? 1);
  const size = Number(c.req.query("size") ?? 40);
  const total = items.length;

  return c.json({
    data: items.slice((page - 1) * size, page * size),
    metadata: {                              // 告诉消费者实际用了什么（含默认值）
      pagination: { page, size, last: Math.max(1, Math.ceil(total / size)), elements: total },
      sort: criteria,
      filters: [
        ...(categories ? [{ name: "category", enum: categories }] : []),
        ...(date ? [{ name: "date", value: date }] : []),
      ],
    },
  });
});

@RestController
public class TransactionController {

    record Pagination(int page, int size, int last, int elements) {}
    record SortCriterion(String name, String direction) {}
    record Metadata(Pagination pagination, List<SortCriterion> sort, List<Map<String, Object>> filters) {}
    record TransactionList(List<Transaction> data, Metadata metadata) {}

    private static final Map<String, Comparator<Transaction>> SORTABLE = Map.of(
        "date", Comparator.comparing(Transaction::date),
        "amount", Comparator.comparing(Transaction::amount));

    @GetMapping("/accounts/{accountId}/transactions")
    public TransactionList search(
            @PathVariable String accountId,
            @RequestParam(required = false) List<String> category,     // restaurant,bar
            @RequestParam(required = false) String date,               // 2024-03-06、2024-03 或 2024
            @RequestParam(defaultValue = "date:desc") String sort,     // 有用的默认顺序
            @RequestParam(defaultValue = "1") int page,                // 分页参数可选，带默认值
            @RequestParam(defaultValue = "40") int size) {

        // ---- 筛选：参数名与返回数据的属性名一致 ----
        Stream<Transaction> stream = repository.transactionsOf(accountId).stream();
        if (category != null) stream = stream.filter(t -> category.contains(t.category()));
        if (date != null) stream = stream.filter(t -> t.date().toString().startsWith(date));

        // ---- 排序：sort=date:desc,amount（方向默认 asc）----
        List<SortCriterion> criteria = new ArrayList<>();
        Comparator<Transaction> comparator = null;
        for (String part : sort.split(",")) {
            String[] p = part.split(":");
            String direction = p.length > 1 ? p[1] : "asc";
            Comparator<Transaction> byField = SORTABLE.get(p[0]);
            if (byField == null || !List.of("asc", "desc").contains(direction)) {
                throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
                    "Unsupported sort '" + part + "'; sortable: " + SORTABLE.keySet());
            }
            if (direction.equals("desc")) byField = byField.reversed();
            comparator = comparator == null ? byField : comparator.thenComparing(byField);
            criteria.add(new SortCriterion(p[0], direction));
        }
        List<Transaction> items = stream.sorted(comparator).toList();

        // ---- 分页 ----
        int total = items.size();
        int from = Math.min((page - 1) * size, total);
        int last = Math.max(1, (int) Math.ceil((double) total / size));

        List<Map<String, Object>> filters = new ArrayList<>();
        if (category != null) filters.add(Map.of("name", "category", "enum", category));
        if (date != null) filters.add(Map.of("name", "date", "value", date));

        return new TransactionList(
            items.subList(from, Math.min(from + size, total)),
            new Metadata(new Pagination(page, size, last, total), criteria, filters));   // 实际使用的值
    }
}

适配请求与响应数据

多种数据格式：内容协商

HTTP 天生支持多种格式，靠的是内容协商。同一个资源可以有不同的表示： 很多人喜欢把交易导进电子表格分析，对他们来说 CSV 比 JSON 方便得多。

请求也可以用不同格式：有些银行系统天生产出 XML，让它们发 Content-Type: application/xml 的请求体即可。 请求和响应的格式不必相同 —— 发 JSON、收 XML 完全可以。只支持对需求有意义的格式。 

import httpx

url = "https://api.bank.com/accounts/12345/transactions"

as_json = httpx.get(url)                                  # 默认：JSON
as_csv = httpx.get(url, headers={"Accept": "text/csv"})   # 同一个 URL，要 CSV

print(as_csv.headers["Content-Type"])    # text/csv
open("transactions.csv", "w").write(as_csv.text)

# 标签要法语的（属性名和代码不会被翻译）
fr = httpx.get(url, headers={"Accept-Language": "fr"}).json()
print(fr["data"][0]["category"])         # {"code": "travel_agency", "label": "Agence de voyage"}

const url = "https://api.bank.com/accounts/12345/transactions";

const asJson = await fetch(url);                                   // 默认：JSON
const asCsv = await fetch(url, { headers: { Accept: "text/csv" } }); // 同一个 URL，要 CSV

console.log(asCsv.headers.get("Content-Type"));   // text/csv
const csv = await asCsv.text();

// 标签要法语的（属性名和代码不会被翻译）
const fr = await (await fetch(url, { headers: { "Accept-Language": "fr" } })).json();
console.log(fr.data[0].category);   // { code: "travel_agency", label: "Agence de voyage" }

RestClient api = RestClient.create("https://api.bank.com");
String path = "/accounts/12345/transactions";

TransactionList asJson = api.get().uri(path)                 // 默认：JSON
    .retrieve().body(TransactionList.class);

String asCsv = api.get().uri(path)                           // 同一个 URL，要 CSV
    .accept(MediaType.parseMediaType("text/csv"))
    .retrieve().body(String.class);

// 标签要法语的（属性名和代码不会被翻译）
TransactionList fr = api.get().uri(path)
    .header(HttpHeaders.ACCEPT_LANGUAGE, "fr")
    .retrieve().body(TransactionList.class);
System.out.println(fr.data().get(0).category());   // Category[code=travel_agency, label=Agence de voyage]

翻译与区域设置

同样的机制可以用来翻译：消费者发 Accept-Language: fr，交易分类的标签就返回 Agence de voyage 而不是 Travel agency。 这个头可选，默认英语。它还支持变体（fr-CA）和带权重的优先级（fr;q=0.9, it;q=0.8, *;q=0.5）。

⚠ 只翻译给人看的值

属性名和代码不能翻译。如果 category 在法语下变成 categorie，travel_agency 变成 agence_de_voyage，想根据分类显示图标的开发者就没法写代码了。

用查询参数微调返回数据

GET /accounts/1234?currency=EUR：把余额换算成欧元返回（默认是美元）。查询参数用在「读取单个资源」上不常见，但完全合法。 注意别用这招大幅改变数据结构，或者返回完全不同的资源。

优雅地处理消费者的错误

① 少出错：宽进严出

软件界有条著名的波斯特尔法则（健壮性原则）：对接收的东西宽容，对发出的东西严格。

  • 消费者 GET 到一笔转账，改了点东西再 PUT 回去。如果因为请求体里多了不可修改的 id 就报 400，他们就得先手工剔除这些字段 —— 很烦。 更好的做法：忽略多余的数据，只在可修改的数据有问题时才报错。
  • 时间只接受 UTC（…T14:10:00Z）对我们最省事，但带时区偏移的写法（…T05:10:00+09:00）也是合法的 ISO 8601。 都接受，返回时统一成 UTC。只给日期（2024-03-10）也接受更好。
  • 搜索没有结果时返回 200 加空列表，而不是 404。两者在 HTTP 上都说得通，但空列表让消费者的代码更简单、Bug 更少，也是通行做法。

② 用恰当的状态码

状态码何时使用
400 Bad Request请求有问题：JSON 无法解析、缺少必填项、违反业务规则……
422 Unprocessable Content请求体能解析，但数据或业务规则校验没通过。比 400「更合乎 HTTP」，但作者偏好只用 400 统一处理请求体和查询参数的问题 —— 自己选，选了就一致
404 Not Found路径标识的资源不存在。POST /transfers 的请求体里付款账户不存在时不能返回 404（那表示 /transfers 不存在），应返回 400/422
406 Not Acceptable消费者用 Accept 或 Accept-Language 要了不支持的格式或语言
415 Unsupported Media Type消费者发来的请求体是不支持的格式（Content-Type）

③ 信息要有用，能指导修复

没用的反馈有用的反馈
400（空）「缺少必填的付款账户 source」
「不支持 JPY」「不支持 JPY；金额币种必须是 EUR 或 USD」
404（空），路径是 /customers/54321/addresses/home「客户 54321 不存在」—— 说清楚是哪个路径参数没找到
415（空）带上 Accept: application/json, application/xml 响应头，并在响应体里再说一遍

④ 机器可读

光有一句人话不够。消费者的程序也需要理解错误 —— 比如在界面上把出错的输入框标红。加上：

  • source：问题在哪。位置（header / path / query / body）、元素名，以及指向请求体内具体位置的 JSON Pointer；
  • type：一个人能读的通用错误类型，如 INVALID_FORMAT、INVALID_VALUE。不要搞出几百个神秘的数字代码；
  • values：（如果有）允许的取值。

⑤ 一次报全

消费者发来一笔缺少收款账户、金额又超过余额的转账。如果只报第一个问题，他改完重试又撞上第二个 —— 想象一下这种体验出现在手机 App 的表单里。 实现应该一次做完所有可能的检查（包括结构校验和业务规则），把错误全部列出来。

⑥ 采用标准：Problem Details

IETF 专门定义了一个错误格式的标准：Problem Details for HTTP APIs（RFC 9457），目的就是「让大家不必再各自发明错误响应格式」。它可以用自定义属性扩展。 把上面几点合在一起： 

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "status": 422,
  "type": "https://api.bank.com/validation-error",
  "title": "The request is not valid",
  "detail": "Missing destination account and unsupported amount currency",
  "errors": [
    {
      "type": "https://api.bank.com/validation-error/required",
      "title": "Missing required property",
      "detail": "Destination account is missing",
      "source": { "location": "body", "name": "destination", "pointer": "#/destination" }
    },
    {
      "type": "https://api.bank.com/validation-error/invalid-value",
      "title": "Invalid value",
      "detail": "Unsupported JPY currency, the amount currency must be EUR or USD",
      "source": { "location": "body", "name": "currency", "pointer": "#/amount/currency" },
      "values": ["EUR", "USD"]
    }
  ]
}
属性来源含义
Content-Type: application/problem+json标准让消费者确切知道这是哪种错误格式
status标准HTTP 状态码
type标准问题的类型；如果是 URL，可以打开它查看说明文档
title标准对类型的简短描述；同一类型每次都相同
detail标准对这一次问题的具体描述
errors自定义扩展详细的错误列表；每一项沿用标准的属性名，再加上 source 和 values

实现：一次校验，报全所有错误

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()
BASE = "https://api.bank.com/validation-error"
CURRENCIES = ["EUR", "USD"]

def error(kind: str, title: str, detail: str, name: str, pointer: str, **extra) -> dict:
    return {"type": f"{BASE}/{kind}", "title": title, "detail": detail,
            "source": {"location": "body", "name": name, "pointer": pointer}, **extra}

@app.post("/transfers", status_code=201)
async def create_transfer(request: Request):
    body = await request.json()
    errors = []

    # ---- 结构检查：不要遇到第一个错误就返回 ----
    for name in ("source", "destination"):
        if not body.get(name):
            errors.append(error("required", "Missing required property",
                                f"{name.capitalize()} account is missing", name, f"#/{name}"))

    amount = body.get("amount") or {}
    currency = amount.get("currency", "EUR")           # 可选，有默认值
    if currency not in CURRENCIES:
        errors.append(error("invalid-value", "Invalid value",
                            f"Unsupported {currency} currency, the amount currency must be EUR or USD",
                            "currency", "#/amount/currency", values=CURRENCIES))

    # ---- 业务规则检查：和结构检查一起做 ----

                            f"Amount exceeds the {source.balance} available on the source account",
                            "value", "#/amount/value"))

    if errors:
        return JSONResponse(
            status_code=422,
            media_type="application/problem+json",
            content={"status": 422, "type": BASE, "title": "The request is not valid",

                     "errors": errors})

    return transfers.create(body)      # 多余的属性（如 id）被忽略：宽进

import { Hono } from "hono";

const app = new Hono();
const BASE = "https://api.bank.com/validation-error";
const CURRENCIES = ["EUR", "USD"];

type ApiError = {
  type: string; title: string; detail: string;
  source: { location: "body" | "query" | "path" | "header"; name: string; pointer?: string };
  values?: string[];
};

app.post("/transfers", async (c) => {
  const body = await c.req.json();
  const errors: ApiError[] = [];

  // ---- 结构检查：不要遇到第一个错误就返回 ----
  for (const name of ["source", "destination"]) {
    if (!body[name]) {
      errors.push({
        type: `${BASE}/required`, title: "Missing required property",
        detail: `${name[0].toUpperCase()}${name.slice(1)} account is missing`,
        source: { location: "body", name, pointer: `#/${name}` },
      });
    }
  }

  const currency: string = body.amount?.currency ?? "EUR";       // 可选，有默认值
  if (!CURRENCIES.includes(currency)) {
    errors.push({
      type: `${BASE}/invalid-value`, title: "Invalid value",
      detail: `Unsupported ${currency} currency, the amount currency must be EUR or USD`,
      source: { location: "body", name: "currency", pointer: "#/amount/currency" },
      values: CURRENCIES,
    });
  }

  // ---- 业务规则检查：和结构检查一起做 ----
  const source = await accounts.find(body.source);
  if (source && (body.amount?.value ?? 0) > source.balance) {
    errors.push({
      type: `${BASE}/insufficient-balance`, title: "Insufficient balance",
      detail: `Amount exceeds the ${source.balance} available on the source account`,
      source: { location: "body", name: "value", pointer: "#/amount/value" },
    });
  }

  if (errors.length > 0) {
    return c.body(
      JSON.stringify({
        status: 422, type: BASE, title: "The request is not valid",
        detail: `${errors.length} problem(s) found in the request`, errors,
      }),
      422,
      { "Content-Type": "application/problem+json" },
    );
  }

  return c.json(await transfers.create(body), 201);   // 多余的属性（如 id）被忽略：宽进
});

// Spring 6 内建了 RFC 9457 的 ProblemDetail 类型，会自动使用 application/problem+json
@RestController
public class TransferController {

    private static final String BASE = "https://api.bank.com/validation-error";
    private static final List<String> CURRENCIES = List.of("EUR", "USD");

    record Source(String location, String name, String pointer) {}
    record ApiError(String type, String title, String detail, Source source, List<String> values) {}

    @PostMapping("/transfers")
    public ResponseEntity<?> createTransfer(@RequestBody TransferCreation body) {
        List<ApiError> errors = new ArrayList<>();

        // ---- 结构检查：不要遇到第一个错误就返回 ----
        if (body.source() == null) errors.add(required("source", "Source account is missing"));
        if (body.destination() == null) errors.add(required("destination", "Destination account is missing"));

        String currency = Optional.ofNullable(body.amount().currency()).orElse("EUR");  // 可选，有默认值
        if (!CURRENCIES.contains(currency)) {
            errors.add(new ApiError(BASE + "/invalid-value", "Invalid value",
                "Unsupported " + currency + " currency, the amount currency must be EUR or USD",
                new Source("body", "currency", "#/amount/currency"), CURRENCIES));
        }

        // ---- 业务规则检查：和结构检查一起做 ----
        accounts.find(body.source()).ifPresent(source -> {
            if (body.amount().value().compareTo(source.balance()) > 0) {
                errors.add(new ApiError(BASE + "/insufficient-balance", "Insufficient balance",
                    "Amount exceeds the " + source.balance() + " available on the source account",
                    new Source("body", "value", "#/amount/value"), null));
            }
        });

        if (!errors.isEmpty()) {
            ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.UNPROCESSABLE_ENTITY, errors.size() + " problem(s) found in the request");
            problem.setType(URI.create(BASE));
            problem.setTitle("The request is not valid");
            problem.setProperty("errors", errors);            // 自定义扩展属性
            return ResponseEntity.of(problem).build();
        }

        Transfer created = transfers.create(body);
        return ResponseEntity.created(URI.create("/transfers/" + created.id())).body(created);
    }

    private ApiError required(String name, String detail) {
        return new ApiError(BASE + "/required", "Missing required property", detail,
            new Source("body", name, "#/" + name), null);
    }
}

别把多个能力藏在一个操作里

第 2 章的能力识别已经降低了这种风险，但仍要警惕「全能型」操作。两个检查角度：

检查数据的粒度

  • GET /accounts/{accountId} 的响应里带着需要筛选、排序、分页的交易列表？ → 应该有独立的「搜索账户的交易」。（但一个明确叫「获取看板」、返回账户摘要和最近几笔交易的操作，是合理的。）
  • 读取账户时会返回户主的地址，不代表「更新账户」（PUT /accounts/{accountId}）就该能改地址。账户和客户是两个概念 → PUT /customers/{customerId}/addresses/{addressId}。

检查操作的目的

一致与标准化

和数据一样：至少在 API 内部一致，最好和组织内其他 API、行业乃至全世界一致。操作层面要看三样东西。

数据

GET /customers 返回「客户 ID」，创建账户却要求「客户引用」，后者要调 GET /customers/{customerId} 才拿得到 —— 两者都标识客户，却不是同一个值。 开发者会为此排查好几个小时。API 应该隐藏内部的复杂性，包括同一个东西有多个标识符这件事。

列表放在哪个属性里也要统一。可以用具体的名字（transactions、accounts），也可以用通用的名字（data、items）。 作者偏好通用的 —— 所有列表的访问方式完全相同，内容是什么看路径就知道。无论选哪种，所有列表操作都照此办理。

行为

一旦这个操作这样做了…………其他同类操作就必须一样
创建转账返回 201 + Location + 完整资源创建客户不能返回 200 + 只有 ID；创建账户不能返回 204
搜索账户没结果时返回 200 + 空列表搜索交易没结果时不能返回 404
转账失败返回 422 + Problem Details + 错误列表创建账户失败不能返回 400 + 一句话
PUT /transfers/{id} 接受完整模型（忽略多余属性）PUT /owners/{id} 不能因此报错

功能

「搜索账户交易」能分页，「搜索账户」和「搜索客户」也得能。参数的设计也要相同： 交易用 amount=gt:400&sort=amount:desc，账户就该是 balance=gt:2000&sort=balance:asc，而不是 minBalance=2000&order=balance,up。 支持 XML 就所有操作都支持；搜索交易能返回 CSV，就考虑让其他搜索操作也能。

💡 三样东西自带标准化

尊重 HTTP 语义（方法、状态码、标准头）、使用第 5 章的典型模型、设计可预测的路径 —— 做到这三点，操作层面的大部分一致性就自动有了。

本章小结

  • 好用的操作满足需求、能力清晰、数据好用、乐于助人，并且一致、标准。
  • 路径要有意义、分层，每一段都有明确用途；利用全局唯一 ID 让路径短而准确。
  • 输入要容易提供：位置符合 HTTP 惯例、与输出对应、使用众所周知或标准的数据、尽量少。能推断的就不要求，能给默认值的就设为可选。
  • 创建和修改时返回完整资源；列表里不要吝啬有用的信息。
  • 为列表和搜索操作提供筛选、排序、分页；所有查询参数都应可选（必填的往往意味着缺了路径参数）；返回相应的元数据；列表放在通用命名的属性里。
  • 用内容协商（Accept、Content-Type）支持多种格式，用 Accept-Language 翻译 —— 只翻译给人看的值。
  • 对输入宽容以减少错误：更新时接受完整模型、接受格式变体但返回统一格式、搜索无结果返回 200 和空列表。
  • 错误反馈要描述问题并帮助修复，人和机器都能读，并且一次列出全部错误（结构检查和业务规则检查一起做）。
  • 使用标准的错误格式，如 Problem Details for HTTP APIs。
  • 确保每个操作粒度合适、没有隐藏别的能力。
  • 输入输出数据、功能、行为，在操作内部和操作之间都要一致。

动手练习

  1. 健身追踪 API 搜索用户 5678 在 12 月 20–23 日的步行记录。用户 ID 和日期必填，运动类型可选。请改进它： 
    POST /fitness/tracking/summary/exercises?user=5678

{ "exerciseType": "walking", "fromStartDate": "2024-12-20", "endDate": "2024-12-23" }

200 OK
[ { "id": 123, "type": "walking", "startTime": 1734699900, "end": 1734702300,
    "duration": "45 minutes", "distance": "3.5 kilometers" } ]
    参考答案 ① 搜索应该用 GET，筛选条件放查询参数。② user 是必填的 → 它是标识符，应进路径：GET /users/5678/exercises?type=walking&startTime=gte:2024-12-20&startTime=lte:2024-12-23；路径也短得多。 ③ 日期最好设为可选并给默认值（如最近 30 天）。④ 筛选项的名字应对应返回的属性（type 而非 exerciseType）。 ⑤ 响应：时间戳 → ISO 8601；startTime/end 命名不一致；"45 minutes"、"3.5 kilometers" 是格式化的字符串 → ISO 8601 时长 "PT45M"、{"value": 3.5, "unit": "km"}； ⑥ 用 {data, metadata} 包起来并支持分页。
  2. 桌游资料 API 提供 GET /games/{name}/classes.json、.xml、.csv，以及 GET /games/{name}/spells?format={format}（必填）。怎么改进？
    参考答案 两种做法彼此不一致，而且都没用 HTTP 的标准机制。统一成 GET /games/{name}/classes 和 GET /games/{name}/spells，用 Accept 请求头做内容协商，不带时默认 JSON。
  3. PATCH /events/12345 + {"date": "2024-12-26", "reason": "Venue conflict"} 用来给活动改期。问题在哪？
    参考答案 「改期」是一个重要的业务动作（要通知参加者、可能触发退票），却被藏在通用的更新里；reason 也不是活动本身的属性，而是这次改期的属性。 应提供独立的操作，如 POST /events/12345/reschedulings（请求体是新日期和原因）。
  4. IAM API 的 POST /users 收到一个把 lastName 错写成 lastNam、角色给了无效值 administrator（应为 admin）的请求，返回 432 Missing And Invalid Data，没有响应体。怎么修？
    参考答案 432 是自创的状态码 → 用 400（或 422）。响应体用 application/problem+json，在 errors 里同时列出两个问题： 缺少必填属性 lastName（pointer #/lastName）；#/permissions/0/role 的值无效，并在 values 里给出允许的角色。
  5. 医疗 API 记录血压时，设计者允许消费者不发测量时间（由服务端生成）和单位（固定 mmHg）。会有什么问题？
    参考答案 测量时间不该由服务端代填：设备可能离线，数据几小时后才上传，服务端生成的时间就是错的（和银行卡交易时间同理）—— 它应该必填，或至少可以提供。 另外输入（"systolic": 120）和输出（{"value": 120, "unit": "mmHg"}）结构不对应，消费者没法把读到的数据直接发回去；应该让输入也接受同样的结构，其中 unit 可选并有默认值。
