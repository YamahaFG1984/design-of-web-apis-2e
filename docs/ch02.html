第 2 章

识别 API 能力

设计 API 的第一步不是想 URL 长什么样，而是搞清楚用户到底要用它做什么。 这一章介绍一张表格 —— API 能力画布（API Capabilities Canvas）—— 用它把一张写着「在线购物」的便利贴， 拆解成一组清晰、通用的操作。

本章目标

  • 理解「能力 = 用例 + 操作」，以及为什么此时要用自然语言而不是 POST /xxx
  • 会用 API 能力画布：先走主路径，再走备选路径和失败路径
  • 会用「输入从哪来 / 结果给谁用」发现遗漏的步骤、用例和用户
  • 会把具体的步骤提炼成唯一、与场景无关的操作
  • 能识别两类陷阱：过于贴合某个消费者，和暴露提供者内部

什么是「API 能力」

形式追随功能（form follows function） —— 建筑、电器、App 和 API 都适用这条原则。 在决定接口长什么样之前，必须先知道它要完成什么。API 的能力由两样东西组成：

  • 用例（use case）：用户想达成的事，像一份菜谱。例如「给朋友发消息」。
  • 操作（operation）：完成用例所需的通用食材。例如「列出好友」「发送消息」。API 最终暴露给消费者的就是操作。

五个要点

  1. 输入是「定义阶段」的产出。它常常短到只够写一张便利贴：「社交网络」「在线购物」。 公开 API 的输入可能更完整（用户调研、画像），但通常仍需深挖。
  2. 分析用户要达成什么，而不是系统内部怎么运作。 微波炉的用户想「加热冷冻餐」，不想「开关磁控管」。当然，用户是谁很关键：造微波炉的工程师确实需要开关磁控管； 数据库 API 的用户确实需要访问表。
  3. 操作要通用。 「以给定火力加热给定时长」能同时服务「加热冷冻餐」和「烤蛋糕」，还支持以后才想到的「冲热可可」。 如果为每个步骤造一个专用操作（「加热巧克力、黄油和牛奶」），接口会迅速膨胀，新用例还是做不了。
  4. 接口长相留到后面。 此刻争论 POST /status 还是 POST /messages 只会分散注意力， 而且业务专家未必看得懂。用大家都懂的自然语言写：「发送一条消息」。
  5. 澄清概念。 如果大家一会儿说「分享状态」一会儿说「发送消息」，就要问：状态是消息吗？是私信吗？ 用自然语言反复对齐，会逐步形成一套共同词汇（领域驱动设计里叫「通用语言」）。

API 能力画布

画布就是一张七列的表格。它没有发明什么新东西，只是把分析需求时该问的问题固定下来，保证不遗漏。 用白板、便利贴都行，但最顺手的工具其实是电子表格：增删方便、能筛选，还能做透视表。 本仓库 2. Identifying API capabilities/ 目录下就有一份示例（.xlsx / .ods）。

第一遍：走主路径

我们手上只有一张便利贴：「在线购物」。

1. 谁是用户

用户包括消费者（调用 API 的应用及其开发者）和应用背后的最终用户。 最终用户不直接调 API，但他们的需求决定了 API 要有什么能力。 用二八法则挑重点：找出贡献 80% 用例的那 20% 用户。这里显然是「在网站或 App 上购物的人」；管理员、企业客户留到第二遍。

2. 他们做什么（用例）

购物者不想 select * from product，他们想「购买商品」，也可能想「管理配送偏好」。 同样用二八法则，先挑最主要的。

3. 怎么做的（步骤）

停在用例层会漏掉能力，必须拆成步骤。用户怎么买东西？反复「把商品加入购物车」，然后「结账」。 先别急着提炼通用操作，照人们说的原话记下来就好 —— 哪怕有人说的是「往圣诞老人的篮子里放礼物」。

4. 输入与成功结果

为每一步写下需要什么、成功后发生什么。保持粗粒度，从用户视角描述，不用列出商品有哪些字段（那是第 5 章的事）。

5. 用「来源」和「去向」找遗漏

这是画布最有价值的一招。对每个输入问「它从哪来？」，对每个成功结果问「它被谁用？」。

输入的来源只有三种：用户自己知道的、API 管理的、前面某一步得到的。 如果三种都不是，说明漏了东西。对新发现的元素重复同样的分析。

ⓘ 发现新领域要先确认

挖出来的新东西（比如「管理商品目录」）不一定在原始需求范围内。先找定义阶段的相关方确认，再继续深挖。

第二遍：备选路径与失败路径

只看主路径会得到一个残缺的 API。第二遍做三件事。

1. 分析每一步的失败

从用户视角列出每一步可能出什么问题、为什么、怎么修复。 失败通常源于：输入缺失或无效、数据状态不对、违反业务规则。「怎么修复」常常会指向一个新步骤。

步骤输入失败（→ 修复方法）
搜索要买的商品目录、筛选条件没有匹配的商品（→ 换条件重试）
目录是空的（→ 管理员填充目录）
查看商品详情选中的商品商品不存在（→ 搜索商品）
把商品加入购物车商品、购物车商品不存在（→ 搜索商品）

某件商品缺货（→ ＋ 新步骤 从购物车移除缺货商品）
新 从购物车移除缺货商品商品、购物车商品不在购物车里（无需修复）

2. 在用例里加备选分支

问「如果……怎么办？」。如果用户结账时反悔了某件商品？他需要「从购物车移除不想要的商品」； 而要移除，得先知道车里有什么 —— 于是又多了一步「核对购物车内容」。 类似的问题还有：如果用户没填收货地址？如果购物车里商品的价格变了？

3. 回头处理备选用户和用例

第一遍搁置的「管理配送偏好」「目录管理员」「企业客户」现在要补上；还有处理异常的用例，比如「反馈订单问题」「到货提醒」。

⚠ 次要不等于可以忽略

管理员不如普通用户显眼，但如果没有人能往目录里加商品，整个系统就转不起来。

把步骤提炼成操作

如果把每个步骤原样变成一个 API 操作，会得到一堆大同小异的东西。 步骤是具体的、带场景的；操作是唯一的、与场景无关的。 对每个步骤做两件事：找有没有相似的步骤；借助描述、输入和成功结果，挖出它的真实意图。

为什么「搜索要买的商品」不能直接当操作？因为「要买的」把它绑死在购物场景上。 去掉这个修饰语，「搜索商品」就能在上线很久之后被用来做「生日愿望清单」这样的新功能。

聚焦在正确的需求上

  • 守住需求范围。「查询用户的银行账户余额」和「在线购物」关系很远，高度可疑 —— 但最终由领域专家和需求方决定。 另一个快速判断：某一步的结果既没人用、也不是别的步骤的输入，那多半可以删掉（例如购物流程里的「列出商品供应商」）。
  • 多问几次「为什么」。 「为什么更新地址时用户得先停用旧地址？」——「因为数据库里一个用户只能有一个生效地址。」 这是提供者的事，不是消费者的事。连续追问能挖到问题的根，分辨出哪些是真正的能力、哪些是多余的。
  • 警惕两种错误视角，下面两节分别展开。

陷阱一：过于贴合某个消费者

照着 UI 画 API

参考已有界面或线框图来设计没问题，但要小心把界面流程当成了业务流程。 假设注册页面分四屏，于是 API 也做了四个操作：

替消费者做它自己的业务

某个 App 想根据用户地址显示天气图标，于是提出「获取用户所在地的天气预报」。 这和「在线购物」无关，是这个 App 自己的事，不该进我们的 API。 但换个角度，天气相关的能力可能有意义：给「搜索商品」加一个「适用天气」筛选（冬季、夏季、雨天），由消费者决定传什么值。

⚠ 信号

某个元素（用户、用例、步骤、输入、结果、操作）牵扯到与本领域无关或关系很远的逻辑。拿不准就问领域专家；关系较远的领域也可能意味着需要拆成多个 API（第 11 章）。

陷阱二：暴露提供者的内部

反映提供者视角的 API 难懂、难用，还可能危及底层系统。三种常见形式：

1. 暴露数据组织方式

客户数据在数据库里分成 CUSD（客户数据）和 CUSA（客户地址）两张表， 于是 API 提供了「读取 CUSD」和「读取 CUSA」。把名字换成「读取客户数据」「读取客户地址」也没好多少 —— 消费者依然要自己拼。 正确做法是一个「读取客户信息」，由实现去聚合。

2. 暴露业务逻辑

系统出于安全考虑保留旧地址，只有状态为「生效」的才是当前地址。于是「修改地址」变成了三步：

代码对比更直观。上半段是「被迫编排三次调用」的客户端，下半段是好设计下的客户端：

import httpx

api = httpx.Client(base_url="https://api.shopp.ing")

# ✗ 提供者视角：消费者必须知道「一个客户只能有一个生效地址」这条内部规则
def change_address_bad(customer_id: str, new_address: dict) -> None:
    addresses = api.get(f"/customers/{customer_id}/addresses").json()
    active = next(a for a in addresses if a["status"] == "active")
    api.patch(f"/addresses/{active['id']}", json={"status": "inactive"})
    # 如果程序在这里崩溃，客户就没有生效地址了
    api.post(f"/customers/{customer_id}/addresses",
             json={**new_address, "status": "active"})

# ✓ 消费者视角：只表达意图，规则由服务端实现保证
def change_address_good(customer_id: str, new_address: dict) -> None:
    api.put(f"/customers/{customer_id}/address", json=new_address)

const base = "https://api.shopp.ing";
type Address = { id: string; street: string; city: string; status: "active" | "inactive" };
const json = { "Content-Type": "application/json" };

// ✗ 提供者视角：消费者必须知道「一个客户只能有一个生效地址」这条内部规则
async function changeAddressBad(customerId: string, newAddress: Omit<Address, "id" | "status">) {
  const addresses: Address[] = await (await fetch(`${base}/customers/${customerId}/addresses`)).json();
  const active = addresses.find((a) => a.status === "active")!;
  await fetch(`${base}/addresses/${active.id}`, {
    method: "PATCH", headers: json, body: JSON.stringify({ status: "inactive" }),
  });
  // 如果页面在这里被关掉，客户就没有生效地址了
  await fetch(`${base}/customers/${customerId}/addresses`, {
    method: "POST", headers: json, body: JSON.stringify({ ...newAddress, status: "active" }),
  });
}

// ✓ 消费者视角：只表达意图，规则由服务端实现保证
async function changeAddressGood(customerId: string, newAddress: Omit<Address, "id" | "status">) {
  await fetch(`${base}/customers/${customerId}/address`, {
    method: "PUT", headers: json, body: JSON.stringify(newAddress),
  });
}

// 用 Spring 6 的 RestClient 做客户端
RestClient api = RestClient.create("https://api.shopp.ing");

record Address(String id, String street, String city, String status) {}
record NewAddress(String street, String city) {}

// ✗ 提供者视角：消费者必须知道「一个客户只能有一个生效地址」这条内部规则
void changeAddressBad(String customerId, NewAddress newAddress) {
    Address[] addresses = api.get()
        .uri("/customers/{id}/addresses", customerId)
        .retrieve().body(Address[].class);
    Address active = Arrays.stream(addresses)
        .filter(a -> a.status().equals("active")).findFirst().orElseThrow();

    api.patch().uri("/addresses/{id}", active.id())
        .body(Map.of("status", "inactive")).retrieve().toBodilessEntity();
    // 如果进程在这里崩溃，客户就没有生效地址了
    api.post().uri("/customers/{id}/addresses", customerId)
        .body(Map.of("street", newAddress.street(), "city", newAddress.city(), "status", "active"))
        .retrieve().toBodilessEntity();
}

// ✓ 消费者视角：只表达意图，规则由服务端实现保证
void changeAddressGood(String customerId, NewAddress newAddress) {
    api.put().uri("/customers/{id}/address", customerId)
        .body(newAddress).retrieve().toBodilessEntity();
}

3. 暴露软件架构

系统由两个微服务组成：一个管商品信息，一个管价格。如果 API 照搬这个结构，消费者就得先「搜索商品（不含价格）」， 再对每一件商品调用「获取商品价格」。对购物来说，没有价格的商品毫无意义，所以这个别扭的序列每次都要走一遍， 而且有性能问题（第 13 章）。

📚 康威定律

「设计系统的组织，其产出的设计必然是该组织沟通结构的翻版。」（1968 年） API 同样受此影响：组织怎么划分团队、系统之间怎么交换数据，都会悄悄渗进 API 的形状里。意识到这一点，才能有意识地抵抗它。

陷阱典型信号
照着 UI 画 API流程里出现细碎字段；界面流程一改 API 就得改
替消费者做业务出现与本领域无关或关系很远的逻辑
暴露数据组织步骤或操作名里出现表名；步骤在描述数据怎么拆分存储
暴露业务逻辑调错顺序或漏调一步会破坏数据完整性
暴露软件架构步骤或操作名里出现系统名；取一份数据需要复杂的调用序列

本章小结

  • API 能力 = API 要覆盖的用例 + 完成它们所需的操作。
  • 用自然语言（「发送一条消息」）而不是接口语言（POST /status）描述能力，便于所有人讨论和确认。
  • 列出所有用户及其用例；先走最常见、顺利的主路径，再补备选路径和失败。
  • 把用例拆成步骤；追问输入的来源和结果的去向，找出遗漏的步骤、用例、用户。
  • 从用户视角列出每步的失败、原因和修复方法；用「如果……怎么办」发现备选分支。
  • 借助描述、输入和成功结果找出相似步骤，提炼成唯一、与场景无关的操作。
  • 质疑与领域关系很远、或结果没人用的元素；多问「为什么」。
  • 不要照搬 UI 流程，不要替某个消费者实现它自己的业务逻辑。
  • 不要暴露数据组织、业务逻辑、软件架构。

动手练习

  1. 你在为一个管理请假的 HR 工具设计 API。列出至少三类用户，选一类优先分析，并说出你会最先分析的用例和理由。
    参考答案 员工、经理、HR 管理员（还可以有薪资系统这类程序用户）。优先分析员工：他们人数最多、产生最多用例。 最先分析「申请休假」—— 它是整个系统存在的原因，其他用例（审批、统计）都以它的结果为输入。
  2. 你在为销售团队的 CRM 设计 API。「销售代表」的用例清单是：准备客户会议、跟进销售线索、核查数据同步流程、识别并联系有流失风险的客户、跟踪进行中的交易。哪一条有问题？为什么？
    参考答案 「核查数据同步流程」。它是系统内部运维的事（提供者视角），不是销售代表要达成的业务目标。 多问一句「为什么销售需要这个？」—— 很可能背后是「担心看到的客户数据不是最新的」，那可以考虑的是让数据带上「最后更新时间」，或者把这个用例归给另一类用户（系统管理员），并向需求方确认是否在范围内。
  3. 外卖 API，「顾客」的「下单」用例有三步：搜索餐厅、把菜品加入订单、支付订单。用输入来源和结果去向找出缺失的步骤。
    参考答案 「把菜品加入订单」需要菜品作为输入，它从哪来？「搜索餐厅」的结果是餐厅，不是菜品。 所以中间缺了一步「查看餐厅菜单」（列出某家餐厅的菜品）。
  4. 活动管理 API 的步骤：核实活动是否已存在、创建活动、搜索可订的活动、把门票加入订单、支付订单、把门票加入礼物、确认礼物。请提炼出唯一、通用的操作。
    参考答案 「核实活动是否已存在」和「搜索可订的活动」→ 搜索活动；「创建活动」→ 创建活动； 「把门票加入订单」和「把门票加入礼物」→ 把门票加入订单（礼物只是带了收礼人的订单）； 「支付订单」和「确认礼物」→ 支付订单。7 个步骤归并为 4 个操作。
  5. 把本章三种语言的「透视」脚本挑一个跑起来，再往里加上「管理订单」用例的步骤，看看哪些操作被复用了。
