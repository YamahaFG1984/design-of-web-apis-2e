第 13 章

设计高效的 API

购物公司上线了重新设计的 API，结果销量下滑。监控显示用户搜索商品时要等 500 毫秒以上。 问题不在数据库缺索引，也不在服务器不够 —— 而在 API 的设计：每搜到一件商品，前端都得再发好几个请求才能凑齐要显示的数据。 效率是继安全之后第二重要的约束。

本章目标

  • 理解低效的 API 如何同时伤害消费者和提供者
  • 知道优化设计之前先检查什么（HTTP 配置、限流、真正的根因）
  • 用「聚焦用户需求」这把老钥匙优化调用流程
  • 启用缓存和条件读取：Cache-Control、ETag、If-None-Match、304
  • 优化数据量：模型选择、字段选择、PATCH、分页
  • 设计批量操作及其错误策略（207 Multi-Status）
  • 知道什么时候该另建一层专门优化的 API

低效的 API 是什么样的

高效的 API 让消费者用最少的能耗和处理、哪怕在糟糕的网络下也能快速达成目标，同时让提供者的基础设施得到有效利用。反过来：

设计如何贡献效率

目标很简单：完成一个用例所需的调用次数最少（尤其是串行调用），处理的数据最少。手段有四类：

  1. 优化输入和输出数据；
  2. 优化调用流程；
  3. 启用缓存和条件请求；
  4. 必要时建一层专门为效率优化的 API。

和安全一样，效率是在做对了事、打磨好用之后才集中处理的约束。好消息是：那样的 API 本身就已经相当高效了。

优化设计之前先检查这些

下面这些与设计无关，但能避免你为了想象中的（或被误判的）性能问题给设计增加不必要的复杂度。

HTTP 配置

HTTP 1.1HTTP 2 及以上
压缩只能压缩请求体/响应体，而且可能默认没开体和头都压缩，传输用更高效的二进制格式
连接可复用（keep-alive），但同一连接上不能并行请求；浏览器和手机系统还限制到同一服务器的并发连接数同一连接上可以并行发送请求

换版本并不改变我们使用 HTTP 的方式（请求、响应、方法、状态码都一样）。平均而言，HTTP 压缩能把 JSON 这类文本数据压到原来的 25% 左右。 所以在怀疑设计之前，先确认 HTTP 2 已启用，或者 HTTP 1.1 的压缩和长连接已打开。

限流

限流（rate limiting）控制消费者在一段时间内能发多少请求，既防恶意攻击（DoS）和无心之失（死循环 Bug），也保证资源在消费者之间公平分配。 制定限流策略不是设计者的事，但要确保它存在，并且以好用、可互操作的方式呈现。 

HTTP/1.1 429 Too Many Requests
Retry-After: Tue, 02 Jan 2024 14:12:00 GMT

更好的做法是在所有响应里都带上限流信息，让消费者能主动调整，而不是等到撞墙：

写法示例说明
事实标准（自定义头） X-RateLimit-Limit: 100
X-RateLimit-Remaining: 90
X-RateLimit-Reset: Tue, 02 Jan 2024 14:12:00 GMT		 没有 RFC 定义，但被广泛使用（命名略有差异）
IETF 草案（推荐关注） RateLimit: "default";r=90;t=20
RateLimit-Policy: "default";q=100;w=60		 还剩 90 次，20 秒后重置；策略是每 60 秒 100 次
ⓘ 关于 X- 前缀

X- 原本表示「实验性的」或「扩展的」，用来区分自定义头和标准头。这个做法在 2012 年被 RFC 6648 废弃了 —— 因为实验性的名字一旦被广泛采用就改不掉了。这个教训适用于 API 里的一切数据（第 15 章）。

找到真正的根因

⚠ 别急着怪设计

运行时出现性能问题，人们常常匆忙归咎于 API 设计。但据作者多年的经验，大多数效率问题出在（广义的）实现上： 服务器规格太小、负载均衡配错了把流量全打到一个实例、网络带宽不足、实现有 Bug……而最常见的元凶是数据库 —— 数不清有多少次，解决办法只是补上一个缺失的索引。 动手解决任何问题之前，先确认找到的是真正的根因。

聚焦用户需求，本身就是在做优化

前面学的很多东西已经在不知不觉中提升了效率：只返回必要的数据（第 5 章）、把创建转账所需的输入砍掉一半（第 9 章）、把三步串行的选择流程变成一步（第 10 章）。局部看是小优化，放到每小时成千上万次调用的规模上，差别巨大。

案例：手机银行的首页

首页要显示用户及关联人名下账户的总余额、近三个月交易的分类饼图，以及境外交易提醒。看看三个版本：

★ 低效常常是一个信号：你解决的不是正确的问题

一个操作或流程很低效时，先问「消费者为什么需要这么复杂的流程？」。 这里的答案是：我们把业务逻辑（汇总余额、分类统计）推给了应用。这不仅容易出错、不好用（第 2 章），现在还发现它很低效。

⚠ 两个提醒
  • 版本 3 高效的前提是实现也高效。如果实现内部照搬版本 1 的做法逐条读交易，只是省掉了互联网上的往返，数据库照样被压垮。
  • 这种专用操作可能离核心领域较远、灵活性较低。可以考虑把它放进一个专门的 API（见本章最后一节）。

缓存与条件读取

最高效的 API 调用是根本没发生的调用，其次是只在必要时才取数据的调用。对应两个机制：

  • 缓存：消费者把数据存起来复用。少了调用和下载，但有用到过期数据的风险。
  • 条件请求：「数据变了才给我」。仍然要调用，但数据没变时不用下载。

不能让消费者自己决定怎么缓存

缓存策略必须由提供者规定。过期的缓存轻则惹恼用户，重则引发法律纠纷：App 显示了错误的余额，用户据此消费，账户透支、产生费用，接下来就是投诉、诉讼和信任的丧失。

按数据和场景制定缓存策略

要考虑数据的组成（不同部分寿命不同）、什么事件会改变它、易变性，以及使用场景（有时用旧数据也无妨）：

数据特点策略
开户时展示的银行卡种类和价格种类不变；价格每月 15 日可能调整可以缓存到下一个 15 日
账户（类型、户主名、余额）类型和户主名几乎不变，但余额随交易实时变化允许缓存，但使用前必须校验
首页的交易分类饼图每笔新交易都会影响它，但它本身是粗粒度的、模糊的可以缓存几小时甚至一天；在数据里标明计算时间
ⓘ 别一个人决定

和领域专家、架构师一起讨论，确认没有安全、业务或法规方面的理由禁止客户端缓存。把定下来的策略写进 OpenAPI 文档里操作或 2XX 响应的描述中 —— 实现者需要它。

返回缓存指令：Cache-Control

响应头含义
Cache-Control: no-store不能缓存
Cache-Control: max-age=600可以缓存 600 秒
Cache-Control: no-cache
ETag: "z567dff"		名字很迷惑：它允许缓存，但每次使用前必须向服务端校验。ETag 是校验时要用的「数据版本」
Vary: Accept, Accept-LanguageHTTP 缓存默认以 URL 为键。如果同一个 URL 因内容协商而有多种表示（JSON/XML、英语/法语），用 Vary 说明哪些请求头也要参与缓存键的计算

这些都是标准的 HTTP 机制（RFC 9111），任何遵循 HTTP 缓存规范的工具都能自动使用。

条件读取：If-None-Match 与 304

第 12 章用 If-Match 做条件更新。条件读取用的是它的反面 If-None-Match：「如果数据不是这个版本了，就给我新的」。

数据没变 → 304，不返回数据
GET /accounts/123
If-None-Match: "z567dff"

HTTP/1.1 304 Not Modified
Cache-Control: no-cache
ETag: "z567dff"
数据变了 → 200 + 新数据 + 新 ETag
GET /accounts/123
If-None-Match: "z567dff"

HTTP/1.1 200 OK
Cache-Control: no-cache
ETag: "890xtdi"

{ "balance": 10.6, ... }

（也可以用基于日期的 Last-Modified / If-Modified-Since。）别忘了把这些头和 304 响应写进 OpenAPI 文档。

# ---------- 服务端 ----------
from fastapi import FastAPI, Header, Response

app = FastAPI()

@app.get("/accounts/{account_id}")
def read_account(account_id: str, response: Response,
                 if_none_match: str | None = Header(None)):
    account = accounts.get(account_id)
    etag = etag_of(account)                        # 如内容的哈希，或版本号

    headers = {"Cache-Control": "no-cache",        # 可以缓存，但用前必须校验
               "ETag": etag,
               "Vary": "Accept"}
    if if_none_match == etag:
        return Response(status_code=304, headers=headers)   # 没变：不返回数据

    response.headers.update(headers)
    return account


# ---------- 客户端：一个最简单的校验式缓存 ----------
import httpx

api = httpx.Client(base_url="https://api.bank.com")
cache: dict[str, tuple[str, dict]] = {}            # url → (etag, data)

def get_with_cache(url: str) -> dict:
    headers = {}
    if url in cache:
        headers["If-None-Match"] = cache[url][0]   # 带上已有的版本
    r = api.get(url, headers=headers)
    if r.status_code == 304:
        return cache[url][1]                       # 没变：直接用缓存，零下载
    cache[url] = (r.headers["ETag"], r.json())     # 变了：更新缓存
    return cache[url][1]

// ---------- 服务端 ----------
import { Hono } from "hono";
const app = new Hono();

app.get("/accounts/:accountId", (c) => {
  const account = accounts.get(c.req.param("accountId"));
  const etag = etagOf(account);                    // 如内容的哈希，或版本号

  c.header("Cache-Control", "no-cache");           // 可以缓存，但用前必须校验
  c.header("ETag", etag);
  c.header("Vary", "Accept");

  if (c.req.header("If-None-Match") === etag) {
    return c.body(null, 304);                      // 没变：不返回数据
  }
  return c.json(account);
});
// Hono 也自带 etag() 中间件，可以自动完成这件事


// ---------- 客户端：一个最简单的校验式缓存 ----------
const cache = new Map<string, { etag: string; data: unknown }>();

async function getWithCache<T>(url: string): Promise<T> {
  const cached = cache.get(url);
  const response = await fetch(url, {
    headers: cached ? { "If-None-Match": cached.etag } : {},   // 带上已有的版本
  });
  if (response.status === 304) return cached!.data as T;       // 没变：直接用缓存，零下载
  const data = await response.json();
  cache.set(url, { etag: response.headers.get("ETag")!, data }); // 变了：更新缓存
  return data as T;
}
// 浏览器里的 fetch 会自动遵循 Cache-Control 和 ETag，通常不需要手写这段

// ---------- 服务端 ----------
@GetMapping("/accounts/{accountId}")
public ResponseEntity<Account> readAccount(@PathVariable String accountId, WebRequest request) {
    Account account = accounts.get(accountId);
    String etag = etagOf(account);                       // 如内容的哈希，或版本号

    // checkNotModified 会比较 If-None-Match；匹配时 Spring 自动返回 304
    if (request.checkNotModified(etag)) {
        return null;
    }
    return ResponseEntity.ok()
        .cacheControl(CacheControl.noCache())            // 可以缓存，但用前必须校验
        .eTag(etag)
        .varyBy("Accept")
        .body(account);
}


// ---------- 客户端：一个最简单的校验式缓存 ----------
record Cached(String etag, Account data) {}
Map<String, Cached> cache = new ConcurrentHashMap<>();

Account getWithCache(String path) {
    Cached cached = cache.get(path);
    ResponseEntity<Account> response = api.get().uri(path)
        .headers(h -> { if (cached != null) h.setIfNoneMatch(cached.etag()); })  // 带上已有的版本
        .retrieve()
        .toEntity(Account.class);

    if (response.getStatusCode() == HttpStatus.NOT_MODIFIED) {
        return cached.data();                            // 没变：直接用缓存，零下载
    }
    cache.put(path, new Cached(response.getHeaders().getETag(), response.getBody()));
    return response.getBody();
}

优化数据量

HTTP 压缩已经能减掉大部分体积。在此之上，可以让消费者按场景多拿或少拿数据：多拿能减少调用次数，少拿能加快响应、降低出站流量成本。

让消费者选择模型

列表返回摘要、读取返回完整模型 —— 这个默认选择一旦定下就改不了，可能对某些场景太多、对另一些又太少。可以让消费者自己选，两种做法：

自定义媒体类型
GET /accounts/123
Accept: application/vnd.bankingapi.summarized+json

HTTP/1.1 200 OK
Content-Type: application/vnd.bankingapi.summarized+json

{ "id": "...", "balance": 45.6 }
Prefer 请求头（RFC 7240）
GET /accounts
Prefer: model=complete

HTTP/1.1 200 OK
Content-Type: application/json
Preference-Applied: model=complete

{ "data": [ { "id": "...", "balance": 45.6,
              "owner": { ... }, ... } ] }

vnd 表示厂商自定义的类型，+json 表示它基于 JSON。不指定时返回默认模型，行为和以前一样。 两种做法都合乎 HTTP 规范，但都不常见，慎用；Prefer 的好处是保留了大家熟悉的 application/json。

同样的 Prefer 头还能控制创建或更新后要不要返回资源：Prefer: model=none 时只返回 201 Created 和 Location，不带响应体（仍用 201 而不是 204，以保留「创建了东西」这个信息）；也可以是 model=minimal 或 model=summarized。

字段选择

更细的粒度：让消费者指明要哪些字段。有些超媒体格式自带这个功能（JSON:API 的 ?fields[account]=balance）； 用普通 JSON 的话可以自己定一个 ?fields=balance。GraphQL 和 OData 也提供字段选择。

把重复出现的数据集中到专门的操作

第 8 章建议给代码配上可读的标签。但一百笔交易里可能有三十笔都带着 "code": 123, "label": "Restaurant"；消费者早就知道 123 是什么了，仍然每次都收到。 可以提供一个专门的操作：通用的 GET /codes/{codeName}/values，或者更具体、内容更丰富（图标、长短标签）的 GET /transaction-categories。 这种数据非常适合缓存。代价是交易数据不那么「拿来即用」了 —— 规模大时才值得。

PATCH 优于 PUT

把一笔交易标记为「已核对」，PATCH 只需发 {"checked": true}，PUT 则要发整笔交易。 单看微不足道，但想想规模：不是一个用户核对一笔交易，而是几十万、上百万用户每周核对十倍于此的交易。

JSON Merge Patch vs JSON Patch

我们一直用的 PATCH 写法叫 JSON Merge Patch（RFC 7396）。修改数组里的元素时，还有另一种格式 JSON Patch（RFC 6902）：

JSON Merge Patch：发送改动后的部分
PATCH /owners/123
Content-Type: application/merge-patch+json
If-Match: "et715"

{
  "addresses": [
    { "type": "home", "city": "Paris", ... },
    { "type": "office", ... }
  ]
}
JSON Patch：描述一系列修改动作
PATCH /owners/123
Content-Type: application/json-patch+json
If-Match: "et715"

[
  {
    "op": "replace",
    "path": "/addresses/0/city",
    "value": "Paris"
  }
]

只改一个城市，Merge Patch 得把整个数组发过去，JSON Patch 只描述那一处修改。尽管如此，作者不推荐 JSON Patch： 它不常用、复杂，而且几乎无法用 OpenAPI 和 JSON Schema 描述「允许哪些操作」。 如果数组真的大到值得这样优化，更好的做法是把它从资源里拆出去，用独立的操作管理。 真有需要时，可以靠内容协商同时支持两种格式。

优化分页

页大小

参数设多少为什么
最大值按业务和用例定（交易：100）设成 10 的话，取 100 笔要调 10 次（版本 1 的教训）。但越大意味着越多的输出数据和越长的下载时间
最小值1设成 50 的话，只要 10 笔的消费者白白多拿 40 笔。设成 1 还能「取最近一笔交易」
默认值偏小但有用（10）大多数调用都会用默认值；设太高会返回大量没人需要的数据。把页大小设成必填能避免浪费，但不够友好

游标还是页码

💡 建议

出于性能考虑优先考虑游标分页，除非需求要求「跳到指定页」，或者数据/数据库不适合游标。和架构师一起决定。

批量操作

把一连串相似的调用合并成一次。把 100 笔交易标记为已核对：调用 100 次「更新交易」，还是调用 1 次「更新多笔交易」？ 我们需要批量操作的理由，和需要「搜索」「列表」操作的理由是一样的。

请求的设计

把操作从单个元素提升到集合层面，最后那个路径参数挪个地方：

单个批量标识符去哪了
创建 POST /account-applications
{ "card": "gold" }		 POST /account-applications
{ "data": [ {…}, {…} ] }		 本来就没有
更新 PATCH /account-applications/123
{ "card": "metal" }		 PATCH /account-applications
{ "data": [ { "id": 123, "card": "metal" }, … ] }		 进入每个元素的数据里（PUT 同理）
删除 DELETE /account-applications/123 DELETE /account-applications?id=123,456 进入查询参数列表
读取 GET /account-applications/123 GET /account-applications?id=123,456 + Prefer: model=complete 同上；配合模型选择

请求体用 data 数组，与列表响应的结构保持一致。

进一步优化

  • 用筛选条件代替 ID 列表。DELETE /account-applications?created=lt:2024-05-04&status=IN_PROGRESS：取消所有 5 月 4 日前创建且仍在进行中的申请。
  • 相同的修改只发一次。PATCH /account-applications?created=lt:…&status=IN_PROGRESS + { "status": "STALLED" }（不常见，但避免了重复数据）。
  • 最好的调用是不需要的调用。消费者为什么要自己清理过期的申请？让系统自动处理（比如发起申请时可以指定有效期）。

错误策略：全有或全无，还是允许部分成功

一个元素出错，整个请求就失败吗？这不是设计者能单独决定的，取决于业务和实现：

场景策略理由
批量提交开户申请部分成功架构师说：第 100 个出错时回滚前 99 个，在现有系统里做不到。业务上也合适 —— 有效的申请越多越好，消费者只需重发有问题的那几个
批量转账全有或全无各笔转账之间可能相互依赖，必须保持整体的完整性

部分成功的响应：207 Multi-Status

207 Multi-Status 来自 HTTP 的扩展 WebDAV。它定义的响应格式是 XML 的、WebDAV 专用的，JSON API 没有对应的标准 —— 但可以借鉴其思路： 为每个元素返回「如果单独调用会得到的东西」：状态、头、体。 

POST /account-applications

{ "data": [ { "card": "gold", ... }, { "card": "bleue", ... } ] }


HTTP/1.1 207 Multi-Status

{
  "data": [
    {
      "status": 201,
      "headers": { "Content-Type": "application/json", "Location": "/account-applications/123" },
      "body": { "id": 123, "card": "gold", ... }
    },
    {
      "status": 400,
      "headers": { "Content-Type": "application/problem+json" },
      "body": { "errors": [ { "source": { "pointer": "#/data/1/card" }, ... } ] }
    }
  ]
}
  • 响应里元素的顺序与请求一致；
  • 错误里的指针以 #/data/{序号} 开头，指明是哪个元素的问题；
  • 如果所有元素的状态都相同（全是 201 或全是 400），就直接返回那个状态，而不是 207。

全有或全无的操作，可以沿用同样的结构以保持一致；如果不关心每个元素各自的状态和头，也可以用更简单的设计： 成功时返回 { "data": [...] }，失败时返回普通的错误格式、把所有元素的所有错误列在一起。 但要想清楚 —— 以后若再出现需要部分成功的批量操作，两种设计就不一致了。 

from fastapi import FastAPI
from fastapi.responses import JSONResponse
from pydantic import BaseModel, ValidationError

app = FastAPI()
MAX_BULK = 100

class ApplicationCreation(BaseModel):
    card: Literal["gold", "metal", "classic"]
    email: EmailStr

@app.post("/account-applications")
async def create_applications(payload: dict):
    items = payload.get("data", [])
    if len(items) > MAX_BULK:
        return JSONResponse({"message": f"At most {MAX_BULK} applications per call"}, 400)

    results = []
    for index, item in enumerate(items):               # 顺序与请求保持一致
        try:
            created = applications.create(ApplicationCreation(**item))
            results.append({
                "status": 201,
                "headers": {"Content-Type": "application/json",
                            "Location": f"/account-applications/{created['id']}"},
                "body": created,
            })
        except ValidationError as e:
            results.append({
                "status": 400,
                "headers": {"Content-Type": "application/problem+json"},
                "body": {"errors": [
                    {"detail": err["msg"],
                     "source": {"location": "body",
                                "pointer": f"#/data/{index}/" + "/".join(map(str, err["loc"]))}}
                    for err in e.errors()]},
            })

    statuses = {r["status"] for r in results}
    # 所有元素状态相同就返回那个状态，否则 207
    return JSONResponse({"data": results}, status_code=statuses.pop() if len(statuses) == 1 else 207)

import { Hono } from "hono";
import { z } from "zod";

const app = new Hono();
const MAX_BULK = 100;

const ApplicationCreation = z.object({
  card: z.enum(["gold", "metal", "classic"]),
  email: z.string().email(),
});

type ItemResult = { status: number; headers: Record<string, string>; body: unknown };

app.post("/account-applications", async (c) => {
  const items: unknown[] = (await c.req.json()).data ?? [];
  if (items.length > MAX_BULK) {
    return c.json({ message: `At most ${MAX_BULK} applications per call` }, 400);
  }

  const results: ItemResult[] = items.map((item, index) => {   // 顺序与请求保持一致
    const parsed = ApplicationCreation.safeParse(item);
    if (!parsed.success) {
      return {
        status: 400,
        headers: { "Content-Type": "application/problem+json" },
        body: {
          errors: parsed.error.issues.map((issue) => ({
            detail: issue.message,
            source: { location: "body", pointer: `#/data/${index}/${issue.path.join("/")}` },
          })),
        },
      };
    }
    const created = applications.create(parsed.data);
    return {
      status: 201,
      headers: { "Content-Type": "application/json", Location: `/account-applications/${created.id}` },
      body: created,
    };
  });

  const statuses = new Set(results.map((r) => r.status));
  // 所有元素状态相同就返回那个状态，否则 207
  const status = statuses.size === 1 ? [...statuses][0] : 207;
  return c.json({ data: results }, status as 201 | 207 | 400);
});

@RestController
public class BulkApplicationController {

    private static final int MAX_BULK = 100;

    record Bulk<T>(List<T> data) {}
    record ItemResult(int status, Map<String, String> headers, Object body) {}

    @PostMapping("/account-applications")
    public ResponseEntity<Bulk<ItemResult>> createApplications(
            @RequestBody Bulk<ApplicationCreation> payload) {
        if (payload.data().size() > MAX_BULK) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
                "At most " + MAX_BULK + " applications per call");
        }

        List<ItemResult> results = new ArrayList<>();
        for (int index = 0; index < payload.data().size(); index++) {     // 顺序与请求保持一致
            ApplicationCreation item = payload.data().get(index);
            var violations = validator.validate(item);
            if (!violations.isEmpty()) {
                final int i = index;
                var errors = violations.stream().map(v -> Map.of(
                    "detail", v.getMessage(),
                    "source", Map.of("location", "body",
                                     "pointer", "#/data/" + i + "/" + v.getPropertyPath()))).toList();
                results.add(new ItemResult(400,
                    Map.of("Content-Type", "application/problem+json"), Map.of("errors", errors)));
            } else {
                Application created = applications.create(item);
                results.add(new ItemResult(201,
                    Map.of("Content-Type", "application/json",
                           "Location", "/account-applications/" + created.id()), created));
            }
        }

        Set<Integer> statuses = results.stream().map(ItemResult::status).collect(Collectors.toSet());
        // 所有元素状态相同就返回那个状态，否则 207
        int status = statuses.size() == 1 ? statuses.iterator().next() : HttpStatus.MULTI_STATUS.value();
        return ResponseEntity.status(status).body(new Bulk<>(results));
    }
}

控制谁能用批量操作

一次提交上百个开户申请对某个合作方有意义，对手机 App 则没有。两种隔离方式： 用一个行为调节型作用域（第 12 章），如 account-application:create:bulk，有它才允许一次提交多个； 或者单独开一个操作 POST /account-applications/bulk，用专门的作用域保护。

ⓘ 批量处理可能很耗时

处理很多元素可能需要很长时间，这时一次同步调用就不合适了。第 14 章讲如何设计耗时长的操作。

另建一层专门优化的 API

如果确实需要大刀阔斧的优化，而优化的结果是一堆只对某个消费者有意义的资源和操作，那就不要动通用的 API，在它上面另建一层。

⚠ 分层需要纪律

是否分层、怎么分，同样要和架构师讨论。层和组件多了之后，必须有章法地管理「什么放在哪一层」，保证调用路径最优、减少重复。 否则这种分布式系统无节制地生长，会变得低效、脆弱、难以维护 —— 与初衷正好相反。

本章小结

  • 高效的 API 让消费者、最终用户和提供者都受益：更快、更省电、数据量小、基础设施负载轻、成本低。
  • 完成用例所需的调用（尤其是串行调用）要尽量少，处理的数据要尽量少。
  • 先设计一个做对事、好用的 API，再提升效率。局部的小优化在规模上很可观。
  • 因性能问题动设计之前，先确认 HTTP 2 已启用（或 HTTP 1.1 的压缩和长连接已打开），并找到真正的根因。
  • 消费者达到限额时返回 429 和 Retry-After；在所有响应里提供限流信息头。
  • 由提供者制定缓存策略（考虑数据的组成、易变性和使用场景），用 Cache-Control 告知消费者。
  • 用条件请求（ETag + If-None-Match → 304 Not Modified）让消费者只在数据变化时才下载。
  • 可以让消费者通过内容协商或 Prefer 头选择返回的模型；用字段选择进一步减少数据。
  • 考虑把反复出现的冗余信息放到专门的操作里。
  • 用部分更新（PATCH）代替整体替换（PUT）以减少上行数据；优先使用简单、通行的 JSON Merge Patch。
  • 页大小从 1 到一个高效的上限，默认值偏小；出于性能优先考虑游标分页。
  • 提供批量操作：更新时把 ID 放进每个元素的数据里，删除时放进查询参数；也可以用筛选条件代替 ID。
  • 根据业务和实现约束决定批量操作是全有或全无还是允许部分成功；后者返回 207 Multi-Status。
  • 用行为调节型作用域或专门的操作来限制谁能做批量操作。
  • 需要重度优化时，在业务 API 之上建一层体验 API，让业务 API 保持通用。

动手练习

  1. 在线学习平台有几万门课程。用户按领域、描述和评分搜索。GET /courses 返回全部课程，每项只有 id 和 name；GET /courses/{courseId} 返回课程的全部信息，包括完整的 lessons 列表和领域的长描述。有什么效率问题？
    参考答案 ① 列表不分页、不能筛选：每次返回几万条 → 加上 domain、stars、q 等筛选和分页。 ② 列表里的摘要缺少用户搜索时关心的数据（领域、评分、简介）：为了展示结果，前端得为每门课再调一次读取 → 把这些放进摘要模型。 ③ 读取操作返回的数据过多：搜索时根本不需要 lessons（应通过 GET /courses/{id}/lessons 单独获取）；领域的长描述在每门课里重复 → 只留 code 和 name，详情通过 GET /domains 获取并缓存。
  2. 图书馆 API 的 GET /books 按可借状态、书名、作者等搜索。新书每月 12 日 00:00 上架；任何一本书随时可能被借走或归还，改变其可借状态。1 月 11 日上午 11 点的一次调用应返回什么缓存相关的头？
    参考答案 可借状态随时会变，所以不能给一个固定的 max-age（哪怕离新书上架只剩 13 小时）。 应返回 Cache-Control: no-cache（可以缓存，但用前必须校验）和一个 ETag；消费者之后用 If-None-Match 做条件请求，没变就得到 304。 如果支持内容协商，再加 Vary。
  3. 社交网络的「时间线」操作 GET /threads 有 q、next、limit 三个查询参数，其中 limit 的 default: 10000、maximum: 1000000。有效率问题吗？
    参考答案 用游标分页是对的。但默认页大小 10000 太离谱：大多数调用用的是默认值，绝大部分数据没人看；最大值 100 万更可能直接拖垮服务器。 改成贴合实际使用的值，例如 minimum: 1、default: 20、maximum: 100（仓库的 13. …/Listing 13.3 是原始定义）。
  4. 把本章的「校验式缓存」客户端代码跑起来，对着一个返回 ETag 的公开 API（比如 GitHub API）连续请求两次，观察第二次的状态码。
