第 6 章

用 OpenAPI 描述 HTTP 操作

前几章我们把设计记在电子表格里。它够用，但没有任何工具读得懂它。 OpenAPI 规范是描述 REST API 的行业标准格式：人能读，机器也能读，文档、Mock、代码生成、网关配置都认它。 这一章学会用它把路径、方法、输入和输出写下来；数据模型留给下一章。

本章目标

  • 知道 OpenAPI 是什么、它在整个 API 生命周期里能做什么
  • 读得懂 YAML，并知道它和 JSON 的对应关系
  • 分清「规范优先」和「代码优先」两种写法，知道各自的利弊
  • 会写：最小文档 → 路径 → 路径参数 → 操作 → 查询参数 → 请求体 → 响应状态 → 响应体 → 响应头

OpenAPI 是什么

OpenAPI 规范（OpenAPI Specification）是一种开源的 API 描述格式。 一份 OpenAPI 文档记录了一个 API 的资源路径、HTTP 操作、输入、输出和数据模型（数据模型用 JSON Schema 来写，下一章讲）。

ⓘ OpenAPI 和 Swagger 是什么关系

OpenAPI 的前身叫 Swagger 规范，最初是 Swagger 这套开源工具（生成文档和 SDK）自带的格式。 2015 年 Swagger 2.0 规范被捐给 Linux 基金会下的 OpenAPI Initiative，之后演进为 OpenAPI 3.0（2017）和 3.1（2021）。 现在「Swagger」是 SmartBear 公司的品牌名，指的是工具；格式本身叫 OpenAPI。

其他类型的 API 也有各自的描述格式：SOAP 用 WSDL，GraphQL 用 GraphQL Schema，gRPC 用 Protocol Buffers，异步 API 用 AsyncAPI。

在设计阶段，OpenAPI 的好处尤其明显：

  • 它提供了一个结构来引导你，减少遗漏和错误；
  • 它有复用机制，同一个模型定义一次、到处引用；
  • Linter 可以自动分析它、找出设计错误（第 18 章）；
  • 文档工具能把它渲染成漂亮的页面，领域专家不用懂 OpenAPI 语法也能参与讨论；
  • 用它一键生成 Mock，亲手调一下还没开发的 API，往往能暴露出纸面上看不出的问题（第 19 章）。
💡 找工具

官方工具目录在 tools.openapis.org。或者直接搜「你想做的事 + OpenAPI」。

YAML 速成

OpenAPI 文档可以用 JSON 或 YAML 写。本教程用 YAML：括号和引号少，人读写更舒服，还能写注释。 YAML 是 JSON 的近亲，能表达同样的东西：

YAML
a-string: value
a-number: 123
a-boolean: true

an-object:
  a-property: value
  another-property: value

an-array:
  - item-1-property-1: one
    item-1-property-2: 1
  - item-2-property-1: two
    item-2-property-2: 2

# 这是注释
等价的 JSON
{
  "a-string": "value",
  "a-number": 123,
  "a-boolean": true,
  "an-object": {
    "a-property": "value",
    "another-property": "value"
  },
  "an-array": [
    { "item-1-property-1": "one",
      "item-1-property-2": 1 },
    { "item-2-property-1": "two",
      "item-2-property-2": 2 }
  ]
}
JSONYAML
属性名必须加双引号通常不加（纯数字的键要加，如 "200"）
字符串必须加双引号通常不加（只含数字或含特殊字符时要加，如 "1.0"）
对象{ } 和逗号换行 + 缩进
数组[ ] 和逗号换行 + 短横线 -
注释不支持# 开头
⚠ 缩进就是结构

YAML 最常见的坑是缩进错位，而且不容易看出来。如果编辑器报「不允许属性 X」，问题多半就出在 X 这一层或附近的缩进上。 另外：YAML 转 JSON 时注释会丢失。

怎么写 OpenAPI 文档

规范优先 vs 代码优先

  • 规范优先（specification-first）：用编辑器直接写 OpenAPI 文档，它独立于实现而存在。
  • 代码优先（code-first）：只写控制器和数据模型的代码（不写业务逻辑），让框架生成 OpenAPI 文档。

这两个词经常和「设计优先（design-first）」混在一起。设计优先是指先设计、后实现，也就是这整套教程在讲的事 —— 它与上面两种写法都兼容。真正不推荐的是「拿到需求直接写实现、根本不设计」。

维度规范优先代码优先
独立 vs 同步 优 文档是独立的事实来源，可以用来检验实现是否符合预期；多出来的接口网关不会暴露 优 文档永远和代码一致
劣 实现悄悄变了，也没有独立的「应该是什么样」可供对照
编辑体验 优 OpenAPI 比开发框架好学，不用搭环境；有图形化编辑器 优 开发者改起来顺手
劣 不写代码的人很难参与；改个描述可能要重新编译部署
文档质量 优 能用上 OpenAPI 的全部特性 劣 框架未必支持所有特性，可能要加一堆专门的注解才能补齐
技术栈 优 不用过早选定技术栈 劣 必须先选技术栈；而且面对实现代码，更容易把内部细节带进设计

一般推荐规范优先，本教程也采用它。但要看场合：如果文档和代码混在一起不成问题、对文档质量要求不高、实现不会悄悄演变，代码优先也是合理的。两者可以随时互相切换。

代码优先长什么样

为了让你对「代码优先」有直观感受，下面用三个主流框架各写一个最小的例子。只写了接口的形状，没有业务逻辑 —— 框架就能生成 OpenAPI 文档。

💡 给老 API 补文档的捷径

如果要为一个已有的、没有文档的 API 补文档，在实现里加一个 OpenAPI 库是最快的办法。得到的文档不会 100% 完整，但所有操作及其输入和成功输出都能看到。

编辑器、版本、格式

  • 编辑器：学习阶段建议用左边写代码、右边实时渲染的编辑器，比如免安装的 Swagger Editor Next（支持到 3.1）。日常大量使用时，可以考虑带图形界面的编辑器。
  • 版本：有 2.0、3.0、3.1 三个。别用 2.0。理想情况用 3.1；如果某些工具还不支持，用 3.0 也可以，两者差别很小（3.1 支持更新的 JSON Schema 和 webhook）。本教程用 3.1。
  • 格式：YAML 或 JSON，看喜好。本教程用 YAML。

第一步：描述资源路径

最小的 OpenAPI 文档

开始设计路径时，就可以创建文档了。一份合法的文档至少有三个顶层属性：

openapi: 3.1.0          # 这份文档用的 OpenAPI 版本（3.0 的话写 3.0.3）
info:                   # API 的元数据
  title: Online Shopping     # API 的名称
  version: "1.0"             # API 的版本；加引号确保它是字符串而不是数字
paths: {}               # 必须有；先放一个空对象让文档合法

加一条路径

路径是 paths 下面的一个键，值是一个「路径项」对象：

paths:
  /products:            # 「目录」资源的路径
    summary: Catalog    # 资源的自然语言名称
💡 认真写 summary 和 description

这些属性大多是可选的，但强烈建议填上。它们把 OpenAPI 文档和能力画布里的自然语言连接起来， 让任何人（包括半年后的你）都能看懂每个 HTTP 元素的业务含义。

带路径参数的路径

路径里只要出现 {xxx}，就必须在这条路径的 parameters 列表里声明它，否则文档不合法：

paths:
  /products/{productReference}:
    summary: Product
    parameters:                    # 路径级参数：对这条路径下的所有操作都生效
      - name: productReference     # 必须与路径里花括号中的名字一致
        in: path                   # 参数所在的位置
        required: true             # 路径参数必须是 true
        schema: {}                 # 数据类型，下一章再填；先放空对象保证合法

有多个路径参数时，往列表里继续加元素即可。

第二步：描述操作

选定 HTTP 方法后，把它的小写形式作为键加到路径下面，并用 summary 写上操作的名称：

paths:
  /products:
    summary: Catalog
    post:
      summary: Add a product to the catalog
    get:
      summary: Search for products
  /products/{productReference}:
    summary: Product
    parameters:
      - name: productReference
        in: path
        required: true
        schema: {}
    get:
      summary: Get product details
    put:                             # 也可以用 patch
      summary: Modify a product
    delete:
      summary: Remove a product from the catalog

文档的骨架已经出来了。此时渲染一下，就能得到一份可以拿去讨论的「API 能力总览」。

第三步：描述输入

HTTP 请求里放数据的位置有四个（第 4 章）。OpenAPI 把它们分成两组： 请求头、路径参数、查询参数统称非 body 参数，放在 parameters 列表里；请求体单独放在 requestBody 里。

查询参数

paths:
  /products:
    get:
      summary: Search for products
      parameters:                # 操作级参数列表
        - name: keywords
          in: query              # 位置：查询参数
          schema: {}             # 没写 required → 默认可选
        - name: category
          in: query
          required: false        # 也可以显式写出「可选」
          schema: {}

in 的取值是 query、path 或 header。 参数可以定义在路径级（对该路径下所有操作生效）或操作级。

💡 可以先粗后细

还没想清楚具体有哪些筛选项时，可以先写一个叫 filters 的参数占位，等做数据建模时再换成真正的 keywords、category……路径参数的名字也一样，可以后改。

请求体

paths:
  /products:
    post:
      summary: Add a product to the catalog
      requestBody:
        description: Product info        # 请求体的自然语言描述
        content:                         # 请求体的内容
          application/json:              # 媒体类型：这里是 JSON
            schema: {}                   # 数据模型，下一章再填

content 下面的键是媒体类型（media type），说明请求体的格式。我们暂时统一用 application/json，其他选择第 9 章再说。 即使还不知道具体模型，也建议把 content 填上最少的内容 —— 这样文档工具才会把请求体显示出来。

第四步：描述响应状态

操作的输出写在 responses 里，以 HTTP 状态码为键（要加引号，否则 YAML 会把它当数字）：

paths:
  /products:
    post:
      summary: Add a product to the catalog
      responses:
        "201":
          description: Product added to the catalog      # 面向业务的输出描述
        "400":
          description: Wrong product information
        "500":
          description: Unexpected server error

两种输出共用一个状态码

「搜索商品」有两种成功输出 ——「找到了」和「没找到」—— 都用 200。但 YAML 里一个键不能出现两次，所以把它们合并成一个响应，把描述连起来： 

    get:
      summary: Search for products
      responses:
        "200":
          description: Products matching filters found or no products matching filters
        "400":
          description: Wrong filters
        "500":
          description: Unexpected server error
⚠ 能合并的前提

共用同一个状态码的几种输出，通常数据类型也相同（这里都是商品摘要的列表，只是一个为空）。 如果它们的数据类型不同，说明操作或数据的识别可能有问题：要么找一个共同的父类型，要么把操作拆开。

第五步：描述响应内容

响应体

写法和请求体类似，只是自然语言描述的位置略有不同：响应本身有 description（输出的含义），数据的描述放在 schema.description 里。

      responses:
        "201":
          description: Product added to the catalog
          content:
            application/json:
              schema:
                description: Product info.      # 数据的描述
        "400":
          description: Wrong product information
          content:
            application/json:
              schema:
                description: Error info.

没有响应体的响应

不写 content 就表示没有响应体：

  /products/{productReference}:
    delete:
      summary: Remove a product from the catalog
      responses:
        "204":
          description: Product removed            # 204 No Content：没有 content
        "404":
          description: No product found
          content:
            application/json:
              schema:
                description: Error info.

响应头

响应头写在响应对象的 headers 映射里，头的名字是键：

        "201":
          description: Product added to the catalog
          headers:
            Location:                     # 头的名字
              description: Product URL
              required: true              # 表示这个头总是会返回
              schema: {}
          content:
            application/json:
              schema:
                description: Product info.

头对象的结构和参数对象基本一样，只是没有 name 和 in（名字已经是键了，位置必然是 header）。

OpenAPI 文档就是数据

因为它是结构化的 YAML/JSON，用几行代码就能读它。下面的脚本读入上面的文件，打印出一张「操作总览」—— 正是我们之前在电子表格里手工维护的那张表。文档工具、Mock、代码生成器本质上都是在做同样的事。 

# pip install pyyaml
import yaml

METHODS = ("get", "post", "put", "patch", "delete")

with open("online-shopping.openapi.yaml") as f:
    doc = yaml.safe_load(f)

print(f"{doc['info']['title']} v{doc['info']['version']}\n")

for path, item in doc["paths"].items():
    print(f"{path}  ({item.get('summary', '')})")
    for method in METHODS:
        op = item.get(method)
        if not op:
            continue
        statuses = ", ".join(op.get("responses", {}).keys())
        print(f"  {method.upper():6} {op.get('summary', ''):36} → {statuses}")

// npm install yaml
import { readFileSync } from "node:fs";
import { parse } from "yaml";

const METHODS = ["get", "post", "put", "patch", "delete"] as const;

type Operation = { summary?: string; responses?: Record<string, unknown> };
type PathItem = { summary?: string } & Partial<Record<(typeof METHODS)[number], Operation>>;
type OpenApiDoc = {
  info: { title: string; version: string };
  paths: Record<string, PathItem>;
};

const doc: OpenApiDoc = parse(readFileSync("online-shopping.openapi.yaml", "utf8"));

console.log(`${doc.info.title} v${doc.info.version}\n`);

for (const [path, item] of Object.entries(doc.paths)) {
  console.log(`${path}  (${item.summary ?? ""})`);
  for (const method of METHODS) {
    const op = item[method];
    if (!op) continue;
    const statuses = Object.keys(op.responses ?? {}).join(", ");
    console.log(`  ${method.toUpperCase().padEnd(6)} ${(op.summary ?? "").padEnd(36)} → ${statuses}`);
  }
}

        System.out.printf("%s v%s%n%n", doc.getInfo().getTitle(), doc.getInfo().getVersion());

        doc.getPaths().forEach((path, item) -> {
            System.out.printf("%s  (%s)%n", path, item.getSummary());
            // readOperationsMap() 返回这条路径上定义的所有「HTTP 方法 → 操作」
            item.readOperationsMap().forEach((PathItem.HttpMethod method, var op) -> {
                String statuses = String.join(", ", op.getResponses().keySet());
                System.out.printf("  %-6s %-36s → %s%n", method, op.getSummary(), statuses);
            });
        });
    }
}

本章小结

  • API 规范是描述 API 的数据格式，可用于整个生命周期；OpenAPI（原 Swagger 规范）是 REST API 的行业标准。
  • 设计时使用 OpenAPI 能简化描述、辅助思考、方便讨论。
  • 通常推荐规范优先；视情况也可以代码优先。
  • OpenAPI 文档可以和 HTTP 操作设计、数据建模并行编写，从设计路径时就开始。
  • 资源路径是 paths 下的键；路径参数必须在路径级的 parameters 里定义，且 required: true。
  • HTTP 方法以小写形式作为路径下的键。
  • 请求头和查询参数放在操作的 parameters 里，用 in 指明位置；请求体放在 requestBody 里。
  • 填上 content 才能让请求体在文档工具里显示；schema 标出了之后要描述数据的位置。
  • 状态码是 responses 下的键；共用状态码的输出只有在数据类型相同时才合并。
  • 响应头放在 headers，响应体放在 content。
  • 用 summary 和 description 保留自然语言描述，把文档和能力画布连起来。

动手练习

  1. 修正下面的路径定义： 
    paths:
  /books/{bookReference}:
    summary: A book
    parameters:
      - name: bookId
        in: path
        schema: {}
    参考答案 两处错误：参数名 bookId 与路径里的 bookReference 不一致；路径参数缺少 required: true。 把 name 改为 bookReference（或把路径改成 {bookId}），并加上 required: true。 仓库里的 Appendix - Solutions to Exercises/Listing A.5 是标准答案。
  2. 在线教学系统：描述「某位讲师开设的某门课程」这个资源的路径。
    参考答案 /instructors/{instructorId}/courses/{courseId}，并在路径级 parameters 里声明两个路径参数，都是 in: path、required: true。
  3. 徒步应用：描述「获取某条路线的分段列表，并允许按难度筛选」这个操作的输入。
    参考答案 路径 /trails/{trailId}/segments：trailId 是路径级的路径参数（必填）； get 操作的 parameters 里加一个 name: difficulty、in: query 的可选参数。
  4. 下面的操作描述有两处问题，找出来： 
    paths:
  /hotels/{hotelId}:
    summary: An hotel
    get:
      summary: Get hotel details
      responses:
        "200":
          description: Hotel details successfully retrieved
          content:
            schema: {}
    参考答案 ① 路径参数 hotelId 没有在 parameters 里声明。 ② content 下面缺了媒体类型这一层，应为 content: → application/json: → schema: {}。 另外从设计上看，带路径参数的操作还应该有 404 和 500 响应。
  5. 把本章的完整文档贴进 Swagger Editor Next，看看渲染效果；再跑一下「列出所有操作」的脚本。
