第 17 章

优化 OpenAPI 文档

第 6 章结束时，我们的文档里 500 响应写了五遍。现在想给所有 500 加一个 Error-Id 响应头 —— 得改五处，漏一处就不一致了。 商品 ID 在路径参数里是整数、在某个模型里又成了字符串。 重复不只是麻烦，它是不一致的温床。这一章学习用 OpenAPI 和 JSON Schema 的复用机制把重复消掉。

本章目标

  • 知道什么时候做优化（以及为什么要和设计分开）
  • 让 schema 保持一致：复用、深层引用、覆盖描述、读写合一、allOf
  • 让参数、请求体、响应头、响应保持一致：components 下的各种可复用元素
  • 建立跨 API 共享的 OpenAPI 组件库
  • 把 OpenAPI 的写法也纳入设计指南

优化什么、什么时候优化

优化 OpenAPI 文档有两个目的：保证 API 设计的一致性，以及让文档更容易编写和维护。

★ 先把设计做对，再优化文档

不要让 OpenAPI 的技巧干扰关于 HTTP 和数据建模的讨论。先把必要的信息写进文档，之后再看能怎么优化。 有了经验以后，你会自然而然地在设计时就用上其中一些技巧，写得更快 —— 但初学时、或者对比较复杂的技巧，分成单独的一步更稳妥。

让数据模型保持一致

① 复用 schema（复习）

第 7 章已经学过：把模型定义在 components.schemas 下，用 $ref 引用。

paths:
  /products:
    get:
      responses:
        "200":
          content:
            application/json:
              schema:
                type: object
                properties:
                  data:
                    type: array
                    items:
                      $ref: "#/components/schemas/ProductSummary"
components:
  schemas:
    SupplierSummary: ...
    Product:
      properties:
        supplier:
          $ref: "#/components/schemas/SupplierSummary"     # 两个模型共用
    ProductSummary:
      properties:
        supplier:
          $ref: "#/components/schemas/SupplierSummary"     # 同一个子模型

建议把所有资源模型（包括完整版、摘要版等各种形态）都定义成可复用的 schema：它们集中在一处，便于阅读和复用，也可以先建模再使用。 被多个资源模型共用的子模型（SupplierSummary）也放在这里。代价是 components.schemas 里可能塞满各种小工具 schema —— 排序时把资源模型放前面、工具模型放后面会好一些。

② 深层引用：指向 schema 的一部分

商品 ID 出现在三个地方：Product.id、ProductSummary.id 和路径参数 productId。 可以定义一个 ProductId 小 schema 让三处都引用它 —— 但那样很快就会有 OrderId、SupplierId……一大堆微型 schema。 换个办法：把完整的定义写在 Product 的 id 属性上（Product 本来就是所有商品数据的源头），其他地方用深层引用指向它： 

paths:
  /products/{productId}:
    parameters:
      - name: productId
        in: path
        required: true
        schema:
          $ref: "#/components/schemas/Product/properties/id"     # 指向 Product 里的 id 属性
components:
  schemas:
    ProductSummary:
      properties:
        id:
          $ref: "#/components/schemas/Product/properties/id"     # 同一个定义
    Product:
      properties:
        id:                              # 唯一的定义处
          title: ProductId               # 工具里会显示在类型旁边：string (ProductId)
          description: Product unique identifier
          type: string

③ 覆盖引用的描述

引用一个通用的 schema 时，它原本的描述往往太泛。在 $ref 旁边写一个 description 就能替换掉它：

components:
  schemas:
    Amount:
      description: An amount of money          # 通用的描述
      type: number
    Product:
      properties:
        price:
          description: The product's price in USD     # 覆盖：结合上下文的描述
          $ref: "#/components/schemas/Amount"
    Order:
      properties:
        total:
          description: The total amount
          $ref: "#/components/schemas/Amount"

OpenAPI 3.1 允许对任何用 $ref 引用的元素覆盖 summary 和 description。

⚠ OpenAPI 3.0 不支持

3.0 的工具会忽略 $ref 旁边的 description，或者直接报解析错误。可以用 allOf 模拟类似的效果，但那会让文档变得难读 —— 不如升级到 3.1。

④ 读写合一的模型

第 7 章为了得到创建/替换模型，把 Product 复制了一份再删掉服务端管理的属性。两份几乎一样的 schema 迟早会各自跑偏。 JSON Schema 的 readOnly 和 writeOnly 标志让一个 schema 身兼两职： 

components:
  schemas:
    Product:
      properties:
        id:
          readOnly: true          # 只出现在响应里（由服务端生成）
          type: string
        name:
          type: string
        price:
          type: number
        dateAdded:
          readOnly: true
          type: string
          format: date

paths:
  /products/{productId}:
    get:
      responses:
        "200":
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Product"      # 响应：包含 readOnly 属性
    put:
      requestBody:
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/Product"        # 请求：自动排除 readOnly 属性
⚠ 慎用 writeOnly

writeOnly 表示「只出现在请求里」。它通常意味着输入和输出的结构有差异 —— 而第 9 章说过，应该尽量让输入与输出对应， 这样消费者才能把读到的数据改一改就直接发回去。（密码这类只写不读的数据是合理的例外。）

这个技巧在代码里也有直接的对应物 —— 同一个类，某些字段只在序列化（输出）时出现：

from datetime import date
from pydantic import BaseModel, Field

class Product(BaseModel):
    # json_schema_extra 让生成的 OpenAPI 里带上 readOnly: true
    id: str | None = Field(default=None, json_schema_extra={"readOnly": True})
    name: str
    price: float
    dateAdded: date | None = Field(default=None, json_schema_extra={"readOnly": True})

@app.put("/products/{product_id}", response_model=Product)
def replace_product(product_id: str, body: Product) -> Product:
    # 请求里即使带了 id / dateAdded 也不采用：它们由服务端管理（第 9 章的「宽进」）
    stored = products.replace(product_id, name=body.name, price=body.price)
    return Product(**stored)        # 响应里包含 id 和 dateAdded

import { z } from "zod";

// 唯一的事实来源
const Product = z.object({
  id: z.string(),                    // 服务端生成（readOnly）
  name: z.string(),
  price: z.number(),
  dateAdded: z.string().date(),      // 服务端生成（readOnly）
});

// 输入形态：从同一个 schema 派生，去掉只读属性 —— 不是另写一份
const READ_ONLY = { id: true, dateAdded: true } as const;
const ProductInput = Product.omit(READ_ONLY);

type Product = z.infer<typeof Product>;            // { id, name, price, dateAdded }
type ProductInput = z.infer<typeof ProductInput>;  // { name, price }

app.put("/products/:productId", async (c) => {
  // z.object 默认丢弃多余的属性：请求里带了 id 也不会报错（第 9 章的「宽进」）
  const input = ProductInput.parse(await c.req.json());
  const stored: Product = products.replace(c.req.param("productId"), input);
  return c.json(stored);
});

import com.fasterxml.jackson.annotation.JsonProperty;
import com.fasterxml.jackson.annotation.JsonProperty.Access;

// 一个类，输入输出共用
public record Product(
    @JsonProperty(access = Access.READ_ONLY) String id,           // 只序列化（输出），反序列化时忽略
    String name,
    BigDecimal price,
    @JsonProperty(access = Access.READ_ONLY) LocalDate dateAdded
) {}

@PutMapping("/products/{productId}")
public Product replaceProduct(@PathVariable String productId, @RequestBody Product body) {
    // body.id() 和 body.dateAdded() 一定是 null：即使请求里带了，Jackson 也会忽略
    return products.replace(productId, body.name(), body.price());   // 返回值里两者都有
}
// springdoc 会据此在生成的 OpenAPI 里标上 readOnly: true

⑤ 用 allOf 从摘要构造完整模型

摘要是完整模型的子集。之前是复制粘贴出来的，同样有跑偏的风险。JSON Schema 的 allOf（「同时满足列表里的所有 schema」）可以反过来： 完整模型 = 摘要 + 其余属性。 

components:
  schemas:
    ProductSummary:                 # 摘要：照常定义
      required: [id, name, price]
      properties:
        id: ...
        name: ...
        price: ...
    Product:                        # 完整模型
      allOf:                        # 合并下面的所有 schema
        - $ref: "#/components/schemas/ProductSummary"     # ① 摘要里的一切
        - required: [dateAdded, supplier]                 # ② 只属于完整模型的其余属性
          properties:
            description: ...
            dateAdded: ...
            supplier: ...

它和读写合一的技巧完全兼容：readOnly 标志可以写在摘要里，也可以写在 allOf 的第二项里。

优化要有度

⚠ 一点重复有时比一堆技巧好

优化过头的文档 —— 尤其是大量使用 allOf 的 —— 可能变得很难读懂。意识到这一点就好，不必太纠结：有少量重复的文档也许反而更容易维护。 JSON Schema 还有 anyOf、oneOf 等用于多态的关键字，组合起来会更复杂，而且有些关键字和代码生成器不兼容（第 19 章）。

让参数保持一致

路径级参数

路径参数永远定义在路径级的 parameters 里（第 6 章），免得在每个操作里重复。 但路径级参数不限于路径参数：任何被该路径下所有操作共用的参数都可以放在这里，比如一个表示 API 版本的请求头： 

paths:
  /products/{productId}:
    parameters:
      - name: productId
        in: path
        required: true
        schema: ...
      - name: Version               # 请求头，对 get / put / delete 都生效
        in: header
        required: true
        schema:
          type: string
          const: "2"                # const：唯一允许的值
    get: ...
    put: ...
    delete: ...

遗憾的是，OpenAPI 3 没有办法为「所有路径的所有操作」统一定义参数。但可以做到只定义一次、到处引用：

可复用的参数

components:
  parameters:                       # 可复用参数的定义处
    ProductId:                      # 标识符（不是参数名）
      name: productId               # 内容与 parameters 列表里的一项完全相同
      in: path
      required: true
      schema:
        $ref: "#/components/schemas/Product/properties/id"

paths:
  /products/{productId}:
    parameters:
      - $ref: "#/components/parameters/ProductId"          # 别忘了前面的短横线
  /products/{productId}/suppliers:
    parameters:
      - description: Same as in Read Product               # 同样可以覆盖描述
        $ref: "#/components/parameters/ProductId"

一组查询参数

分页需要 next 和 limit 两个参数。逐个定义、逐个引用既啰嗦又容易漏。 一个巧妙的办法：定义一个对象类型的查询参数。按 OpenAPI 的默认序列化规则，对象的每个属性会展开成一个独立的查询参数。 

components:
  parameters:
    Pagination:
      name: pagination              # 只在文档里显示，不会出现在请求中
      description: |
        Pagination parameters (`.../?next=s00999&limit=10`)
      in: query
      schema:
        type: object                # 对象 → 每个属性序列化成一个查询参数
        properties:
          next:
            description: Next page cursor
            type: string
          limit:
            description: Number of elements per page
            type: number

paths:
  /products:
    get:
      parameters:
        - $ref: "#/components/parameters/Pagination"     # 一次引用，得到 next 和 limit 两个参数
ⓘ 这个技巧不常见

它很强大，但少有人用，有些工具渲染出来的效果也不够清楚。所以要像上面那样在 description 里明确说明用法，并指出 pagination 这个名字不会出现在请求里。 它也不能用来定义一组请求头 —— 被序列化的是参数的内容，不会变成多个头。

让请求体和响应保持一致

components 下还有三种可复用的元素，定义和使用的方式与 schema、参数如出一辙：

元素定义在引用典型用途
请求体components.requestBodies#/components/requestBodies/{Id}创建和替换操作共用同一个请求体
响应头components.headers#/components/headers/{Id}所有 201 都返回的 Location
响应components.responses#/components/responses/{Id}所有操作共用的 500；读取和更新共用的 404

可复用的请求体

components:
  requestBodies:
    ProductCreateOrReplace:
      description: Product info
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/Product"

paths:
  /products:
    post:
      requestBody:
        $ref: "#/components/requestBodies/ProductCreateOrReplace"
  /products/{productId}:
    put:
      requestBody:
        description: |
          Extra properties are ignored. The complete Product data
          returned by Read product is accepted.
        $ref: "#/components/requestBodies/ProductCreateOrReplace"

可复用的响应头和响应

components:
  headers:
    ResourceLocation:               # 标识符，不是头的名字
      description: Created resource URL
      schema:
        type: string
  responses:
    ResourceNotFound:               # 通用的「资源不存在」
      description: No resource was found
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/Error"            # 可复用元素可以引用别的可复用元素
    ProductNotFound:                # 基于通用响应、只换了描述的特化版本
      description: No product was found
      $ref: "#/components/responses/ResourceNotFound"
    UnexpectedError:
      description: Unexpected server error
      content:
        application/problem+json:
          schema:
            $ref: "#/components/schemas/UnexpectedError"

paths:
  /products:
    post:
      responses:
        "201":
          headers:
            Location:               # 头的名字必须在这里写出
              description: The created product's URL
              $ref: "#/components/headers/ResourceLocation"
        "500":
          $ref: "#/components/responses/UnexpectedError"
  /products/{productId}:
    get:
      responses:
        "404":                      # 状态码必须在这里写出
          $ref: "#/components/responses/ProductNotFound"
        "500":
          $ref: "#/components/responses/UnexpectedError"
    put:
      responses:
        "404":
          $ref: "#/components/responses/ProductNotFound"
        "500":
          $ref: "#/components/responses/UnexpectedError"
ⓘ OpenAPI 自己也有不一致的地方
  • 可复用的参数自带名字（name），可复用的响应头却不带 —— 头的名字是使用处的键。请求头要定义成 in: header 的可复用参数，而不是放在 components.headers 里。
  • 可复用的响应不包含状态码 —— 状态码是使用处的键。

这是格式设计上已知的不足，未来的版本会改进。你看，连 OpenAPI 这样的格式也有设计不一致、可以改进的地方 —— 本教程讲的东西同样适用于设计这类格式。

现在回到本章开头的问题：给所有 500 加一个 Error-Id 头 —— 只需要改 UnexpectedError 这一处。

跨 API 共享的组件库

统一的错误模型、分页参数、500 响应……这些东西在所有 API 里都应该一模一样。把它们放进一个（或几个）OpenAPI 组件库， 各个 API 的文档都去引用。这样的库是设计指南的一部分（第 16 章），也是 API 治理的有力工具。

定义库

库本身是一份合法的 OpenAPI 文件，只是没有 paths：

openapi: 3.1.0
info:
  title: Shared components
  version: "1.0"            # 这个库自己的版本，与引用它的 API 的版本无关
                            # 没有 paths，也没有 webhooks
components:
  schemas:
    Errors: ...
  parameters:
    Pagination: ...
  headers:
    ResourceLocation: ...
  responses:
    ResourceNotFound: ...

components 下除了 securitySchemes 之外的元素都可以这样共享（安全方案是按名字而不是按 $ref 使用的，这也是 OpenAPI 的一个设计局限）。

引用库里的组件

$ref 的值变成「文件的路径或 URL + 文件内的 JSON Pointer」：

openapi: 3.1.0
info:
  title: Shopping
  version: "2.3"
paths:
  /products:
    get:
      parameters:
        - $ref: "/path/to/shared-components.yaml#/components/parameters/Pagination"
        #        └────── 相对或绝对的路径/URL ──────┘└────── 文件内的 JSON Pointer ──────┘

相对路径是相对于发出引用的那个文件的位置计算的。两个文件在同一目录时写 "shared-components.yaml#/components/…" 即可。

解析跨文件的引用

有些工具（比如代码生成器）不支持拆分成多个文件的 OpenAPI 文档。这时需要先把它们打包（bundle）成一个文件 —— 作者推荐 Redocly CLI： 

npx @redocly/cli bundle shopping.openapi.yaml -o bundled.openapi.yaml

各语言的 OpenAPI 解析库也都能在读取时自动解析引用。下面的代码读入一个引用了共享库的文档，输出解析后的结果：

# pip install prance openapi-spec-validator
from prance import ResolvingParser

# 读取 shopping.openapi.yaml，并把所有 $ref（本地的和跨文件的）替换成它们指向的内容
parser = ResolvingParser("shopping.openapi.yaml")
doc = parser.specification

params = doc["paths"]["/products"]["get"]["parameters"]
print(params[0]["name"], "←", params[0]["schema"]["properties"].keys())
# pagination ← dict_keys(['next', 'limit'])     # 引用已经被库里的定义替换

# 想自己动手也不难：JSON Pointer 就是一条逐段往下走的路径
def resolve_pointer(document: dict, pointer: str):
    node = document
    for part in pointer.lstrip("#/").split("/"):
        node = node[part.replace("~1", "/").replace("~0", "~")]   # JSON Pointer 的转义规则
    return node

print(resolve_pointer(doc, "#/components/schemas/Product/properties/id"))

// npm install @apidevtools/swagger-parser
import SwaggerParser from "@apidevtools/swagger-parser";

// bundle：把跨文件的 $ref 收拢成只含内部 $ref 的单个文档
const bundled = await SwaggerParser.bundle("shopping.openapi.yaml");

// dereference：把所有 $ref 都替换成它们指向的内容
const doc: any = await SwaggerParser.dereference("shopping.openapi.yaml");

const params = doc.paths["/products"].get.parameters;
console.log(params[0].name, "←", Object.keys(params[0].schema.properties));
// pagination ← [ 'next', 'limit' ]     // 引用已经被库里的定义替换

// 想自己动手也不难：JSON Pointer 就是一条逐段往下走的路径
function resolvePointer(document: any, pointer: string): unknown {
  return pointer
    .replace(/^#\//, "")
    .split("/")
    .map((part) => part.replace(/~1/g, "/").replace(/~0/g, "~"))   // JSON Pointer 的转义规则
    .reduce((node, part) => node[part], document);
}

console.log(resolvePointer(bundled, "#/components/schemas/Product/properties/id"));

库文件必须能独立编辑

✗ 不完整的片段文件
name: pagination
description: Pagination parameters
in: query
schema: ...

可以用 $ref: "…/pagination-parameter.yaml" 引用，但它不是合法的 OpenAPI 文件：解析器没法单独校验它，编辑器也帮不上忙。

✓ 每个库文件都是合法的文档
  • 一份带 info 和 components 的完整 OpenAPI 文件；或者
  • 一份独立的 JSON Schema 文件（用 $ref: "…/errors-schema.json" 引用，不需要 JSON Pointer）。

后者要注意工具支持：好用的 OpenAPI 图形化编辑器不一定能处理纯 JSON Schema 文件，而且它通常得是 JSON 而不是 YAML。

把 OpenAPI 的写法纳入设计指南

技巧这么多，很难全记住。在设计指南（第 16 章）里补充 OpenAPI 相关的内容：

  • 组件库放在哪、什么时候用、怎么用；
  • 编写 OpenAPI 文档的通用约定，例如「引用资源 ID 的 schema 时一律用深层引用，不单独定义微型 schema」「所有 500 必须引用共享的 UnexpectedError」。

下一章会讲如何自动检查这些约定有没有被遵守。

要解决的重复技巧
同一个模型在多处出现components.schemas + $ref
模型的某个属性被别处重复定义深层引用 …/Product/properties/id
通用 schema 的描述不贴合上下文在 $ref 旁边写 description 覆盖（3.1）
输入模型和输出模型几乎一样readOnly（慎用 writeOnly）
摘要模型和完整模型有重叠allOf：完整 = 摘要 + 其余
路径下所有操作共用的参数路径级 parameters
多个路径共用的参数components.parameters
一组总是一起出现的查询参数对象类型的可复用查询参数
多个操作共用的请求体 / 响应头 / 响应components.requestBodies / headers / responses
多个 API 共用的元素外部组件库 + 文件#指针 形式的 $ref

本章小结

  • 不要让复杂的 OpenAPI 技巧干扰 HTTP 和数据建模。先把必要的信息写进文档，之后再优化。
  • 在 components.schemas 下定义可复用的 schema，用 $ref 引用，以保证一致。
  • 在 $ref 旁边放一个 description，可以覆盖任何可复用组件的描述（OpenAPI 3.1）。
  • 用深层引用指向 schema 的内部，避免定义大量微型 schema。
  • 用 readOnly 标志创建读写合一的 schema；writeOnly 可能在请求与响应之间引入有风险的不一致。
  • 用 allOf 把摘要 schema 和包含其余属性的内联 schema 合并，定义出完整的 schema。
  • 在优化和它带来的复杂度之间找到平衡。
  • 路径下所有操作共用的参数一律定义在路径级。
  • 可复用的参数、请求体、响应头、响应分别定义在 components 的 parameters、requestBodies、headers、responses 下。
  • 定义一个对象类型的可复用查询参数，就得到了一组可复用的查询参数。
  • 把组件库定义在合法的、可独立编辑的 OpenAPI 或 JSON Schema 文件里。

动手练习

本仓库 17. Optimizing an OpenAPI document/ 里的 Listing 17.21 – 17.24 是四道练习的原题，答案在 Appendix - Solutions to Exercises/ 的 Listing A.24 – A.27。

  1. /authors 和 /books 的 get 各自定义了 401（描述分别是「Unauthorized」和「Invalid token」）和 500（「Server error」和「Unexpected error」）。怎么优化？
    参考答案 两处的 401 和 500 本应相同，却已经出现了描述不一致。 在 components.responses 下定义 Unauthorized 和 UnexpectedError，两个操作都用 $ref 引用。它们也很适合放进跨 API 的组件库。
  2. /authors/{authorId} 的 get 和 delete 各自定义了一遍 authorId 路径参数（type: string），而响应里的 id 属性又单独写了一遍 type: string。怎么优化？
    参考答案 ① 把 authorId 提到路径级的 parameters。 ② 把响应的内联 schema 提取成 components.schemas.Author。 ③ 路径参数的 schema 用深层引用：$ref: "#/components/schemas/Author/properties/id"。
  3. POST /authors 的请求体是 {name}，响应体是 {id, name}，两者各写了一份内联 schema。怎么优化？
    参考答案 定义一个读写合一的 Author schema，把 id 标为 readOnly: true，请求体和响应体都引用它。
  4. AuthorSummary 有 id 和 name；Author 有 id（readOnly）、name 和 genres。怎么优化？
    参考答案 Author 用 allOf：第一项 $ref 到 AuthorSummary，第二项只定义 genres。把 readOnly: true 移到 AuthorSummary 的 id 上。
