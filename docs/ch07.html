第 7 章

用 JSON Schema 描述数据

上一章的 OpenAPI 文档里留下了一堆空的 schema: {}。现在把它们填上。 OpenAPI 描述数据用的是另一个独立的标准 —— JSON Schema。 学会它，第 5 章设计的那些模型（完整、摘要、创建……）就都能写进文档了。

本章目标

  • 知道 JSON Schema 是什么，以及它和 OpenAPI 的关系
  • 会把资源模型定义为 components.schemas 下的可复用 schema
  • 会描述对象、原子属性、嵌套对象、数组，以及必填属性
  • 会用内联 schema 描述参数和响应头，并控制数组参数的序列化方式
  • 会用 $ref 引用可复用 schema，以及混用内联和引用

JSON Schema 是什么

JSON Schema 是一种用来校验和注解 JSON（或 YAML）数据的格式。 一份 JSON Schema 文档（简称 schema）可以表达这样的规则：

这份数据是一个对象；它必须有一个 amount 属性，是大于 0 的数字；它可以有一个 currency 属性，是字符串，取值只能是 USD 或 EUR。

schema 里还能放不参与校验的附加信息，比如把 currency 描述为「ISO 4217 标准货币代码」。

JSON Schema 独立于 OpenAPI 存在，可以单独用来校验配置文件、生成表单等。 在 OpenAPI 里，它负责描述和记录数据，并由此惠及 OpenAPI 的所有用途：设计、文档、Mock、测试……

亲手校验一次

各语言都有成熟的 JSON Schema 校验库。下面用同一个 schema 校验两份数据，感受一下它到底在做什么：

# pip install jsonschema
from jsonschema import Draft202012Validator

schema = {
    "type": "object",
    "required": ["productReference", "name", "price"],
    "properties": {
        "productReference": {"type": "integer"},
        "name": {"type": "string"},
        "price": {"type": "number"},
        "keywords": {"type": "array", "items": {"type": "string"}},
    },
}

validator = Draft202012Validator(schema)

good = {"productReference": 12345, "name": "Cowboy Bebop", "price": 49.99}
bad = {"productReference": "12345", "name": "Cowboy Bebop", "keywords": ["anime", 42]}

print(validator.is_valid(good))          # True

for error in validator.iter_errors(bad):
    print(list(error.path), "→", error.message)
# [] → 'price' is a required property
# ['productReference'] → '12345' is not of type 'integer'
# ['keywords', 1] → 42 is not of type 'string'

// npm install ajv
import Ajv2020 from "ajv/dist/2020";

const schema = {
  type: "object",
  required: ["productReference", "name", "price"],
  properties: {
    productReference: { type: "integer" },
    name: { type: "string" },
    price: { type: "number" },
    keywords: { type: "array", items: { type: "string" } },
  },
};

const ajv = new Ajv2020({ allErrors: true });
const validate = ajv.compile(schema);

const good = { productReference: 12345, name: "Cowboy Bebop", price: 49.99 };
const bad = { productReference: "12345", name: "Cowboy Bebop", keywords: ["anime", 42] };

console.log(validate(good));             // true

if (!validate(bad)) {
  for (const error of validate.errors ?? []) {
    console.log(error.instancePath || "/", "→", error.message);
  }
}
// / → must have required property 'price'
// /productReference → must be integer
// /keywords/1 → must be string

// 依赖：com.networknt:json-schema-validator
import com.fasterxml.jackson.databind.ObjectMapper;
import com.networknt.schema.*;

public class ValidateProduct {
    public static void main(String[] args) throws Exception {
        String schemaJson = """
            {
              "type": "object",
              "required": ["productReference", "name", "price"],
              "properties": {
                "productReference": { "type": "integer" },
                "name": { "type": "string" },
                "price": { "type": "number" },
                "keywords": { "type": "array", "items": { "type": "string" } }
              }
            }
            """;

        JsonSchema schema = JsonSchemaFactory
            .getInstance(SpecVersion.VersionFlag.V202012)
            .getSchema(schemaJson);

        ObjectMapper mapper = new ObjectMapper();
        var good = mapper.readTree("""
            { "productReference": 12345, "name": "Cowboy Bebop", "price": 49.99 }""");
        var bad = mapper.readTree("""
            { "productReference": "12345", "name": "Cowboy Bebop", "keywords": ["anime", 42] }""");

        System.out.println(schema.validate(good).isEmpty());     // true

        schema.validate(bad).forEach(error -> System.out.println(error.getMessage()));
        // $: required property 'price' not found
        // $.productReference: string found, integer expected
        // $.keywords[1]: integer found, string expected
    }
}
ⓘ 版本与格式
  • OpenAPI 3.1 用的是 JSON Schema 2020-12 版，OpenAPI 3.0 用的是较老的版本。除非用到高级特性，两者写出来的 schema 通常一样。本章的写法两者都兼容。
  • OpenAPI 文档是 YAML，里面的 schema 也就用 YAML 写；文档是 JSON 的话 schema 也是 JSON。

把资源模型放在哪里

上一章的 schema 属性都在各个操作里。但资源的完整模型应该放在另一个地方：components.schemas。 这里的 schema 不依附于任何操作，可以被多处引用。

  • 可以像第 5 章那样，独立于操作来设计资源；
  • 文档工具会单独展示这些模型，让人一眼看到 API 涉及哪些业务概念；
  • 「商品」模型会被好几个操作返回，定义一次、到处引用，保证一致，也省得复制粘贴。
openapi: 3.1.0
info: ...
paths: ...
components:          # 存放可复用元素（schema、参数、响应……）
  schemas:           # 可复用的 JSON Schema，每个有一个名字
    Product: {}      # 先放个空的，马上来填
💡 两个小约定
  • schema 的名字没有硬性规定，但 PascalCase（ProductSummary）最常见，大概是因为它和类名的习惯一致。这些名字只出现在文档里，不会出现在实际传输的数据里。
  • 顶层属性建议按 info → paths → components 的顺序排：读的人先关心概况，再看有哪些操作，最后看数据模型。

对象和它的属性

schema 通常从 type 开始。对象的属性写在 properties 里：键是属性名，值又是一个 JSON Schema。 

    Product:
      type: object                    # 这是一个对象
      properties:                     # 它的属性
        productReference:             # 属性名
          type: integer               #   ↓ 这里又是一个 schema
          description: Unique identifier

原子类型

JSON Schema 有四种原子类型。把你习惯的编程语言类型映射过去：

嵌套对象

对象类型的属性，写法和最外层的对象一模一样 —— 这就是 JSON Schema 的递归之美：不管在哪一层，每个元素都是一个 schema。

        supplier:
          type: object                # supplier 也是对象，就像 Product 本身
          properties:
            supplierCode:
              type: string
              description: Unique identifier
            name:
              type: string

数组

数组的 type 是 array，再用 items 给出元素的 schema：

        keywords:
          type: array                 # 这是一个数组
          items:                      # 数组元素的 schema
            type: string              # → 字符串的数组

items 里可以放任何 schema，所以对象的数组、数组的数组都能表达。

必填属性

「必填」不写在属性自己身上，而是写在所属对象的 required 列表里。 不在列表里的就是可选的。每一层对象各有各的 required。

完整的 Product schema

components:
  schemas:
    Product:
      type: object
      required:                       # 这一层对象的必填属性
        - productReference
        - name
        - category
        - price
        - dateAdded
        - supplier
      properties:
        productReference:
          type: integer
          description: Unique identifier
        name:
          type: string
        description:
          type: string
        keywords:
          type: array
          items:
            type: string
        category:
          type: string
        price:
          type: number
          description: Price in USD
        dateAdded:
          type: string
          format: date
        isProductUnavailable:
          type: boolean
          description: Temporarily unavailable
        supplier:
          type: object
          required:                   # supplier 这一层的必填属性
            - supplierCode
            - name
          properties:
            supplierCode:
              type: string
              description: Unique identifier
            name:
              type: string
💡 属性的顺序

type、required、properties 的先后没有规定，但建议就按这个顺序写。properties 往往很长，如果把 type 和 required 放在它后面，很容易被淹没。

描述非 body 数据：内联 schema

和上一章一样，输入输出数据按位置分两组：非 body 数据（路径参数、查询参数、请求头、响应头）和 body 数据。 它们在 OpenAPI 里位置不同，但都用 JSON Schema 来描述。先看非 body 数据，顺便学习内联 schema —— 直接写在 schema 属性下面的 schema。

路径参数

参数往往对应资源的某个属性。直接把那个属性的 schema 抄过来：

paths:
  /products/{productReference}:
    summary: Product
    parameters:
      - name: productReference
        in: path
        required: true
        schema:
          type: integer          # 抄自 Product.properties.productReference

数组型的查询参数

查询参数不一定是原子值。keywords 筛选条件是个字符串数组，它在 URL 里该怎么写？ OpenAPI 用 style 和 explode 来说明序列化方式： 

  /products:
    get:
      summary: Search for products
      parameters:
        - name: keywords
          in: query
          style: form            # 查询参数的默认 style
          explode: false         # 默认是 true；设为 false → 逗号分隔
          schema:
            type: array
            items:
              type: string

这个设计选择会直接影响两端的代码。下面是客户端按 explode: false 拼 URL、服务端把它解析回数组的写法：

响应头

有些数据没法从资源模型里抄，比如 Location 头（新资源的 URL），就直接写一个专用的内联 schema：

      responses:
        "201":
          headers:
            Location:
              description: Product URL
              required: true
              schema:
                type: string       # 不来自任何资源模型，现写的

描述 body 数据：引用可复用 schema

用 $ref 引用

任何出现 schema 的地方，既可以写内联 schema，也可以写一个引用：$ref 属性，值是一个 JSON Pointer，指向真正的 schema 所在的位置。

引用避免了重复，也避免了「复制了五份、后来只改了三份」的不一致。要改模型，只改一处。 错误响应同理：在 components.schemas 里定义一个 Error，所有 4XX、5XX 响应都引用它。

派生模型

第 5 章从完整模型派生出了创建模型等。在 OpenAPI 里（现阶段）最简单的做法是：复制 Product，改个名字，然后从 properties 和 required 里删掉不需要的属性。 

components:
  schemas:
    Product: ...

    ProductCreationOrReplacement:     # Product 的副本，去掉了服务端管理的属性：
      type: object                    #   productReference、dateAdded、supplier.name
      required:
        - name
        - category
        - price
        - supplier
      properties:
        name:
          type: string
        description:
          type: string
        keywords:
          type: array
          items:
            type: string
        category:
          type: string
        price:
          type: number
          description: Price in USD
        isProductUnavailable:
          type: boolean
        supplier:
          type: object
          required:
            - supplierCode
          properties:
            supplierCode:
              type: string

然后在两个操作的请求体里引用它：

paths:
  /products:
    post:
      requestBody:
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/ProductCreationOrReplacement"
  /products/{productReference}:
    put:
      requestBody:
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/ProductCreationOrReplacement"
⚠ 复制粘贴的代价

两份几乎一样的 schema 时间长了可能会各自跑偏。现阶段先这么做，因为简单。第 17 章会介绍如何用一个「读写通用」的 schema 取代它们。

混用内联和引用

「搜索商品」返回的是 ProductSummary 的数组。数组这层壳只在这里用，写成内联；元素则引用可复用的 schema： 

paths:
  /products:
    get:
      responses:
        "200":
          content:
            application/json:
              schema:
                type: array                                      # 内联的数组 schema
                items:
                  $ref: "#/components/schemas/ProductSummary"    # 元素是引用
components:
  schemas:
    ProductSummary:                   # Product 的摘要版
      type: object
      required: [productReference, name, category, price]
      properties:
        productReference:
          type: integer
        name:
          type: string
        keywords:
          type: array
          items:
            type: string
        category:
          type: string
        price:
          type: number

可复用 schema 内部也能引用别的 schema。比如把 Product 里的 supplier 抽成 SupplierSummary，将来「搜索供应商」也能用它：

components:
  schemas:
    Product:
      type: object
      properties:
        supplier:
          $ref: "#/components/schemas/SupplierSummary"
    SupplierSummary:
      type: object
      required: [supplierCode, name]
      properties:
        supplierCode:
          type: string
        name:
          type: string
💡 YAML 的紧凑写法

上面的 required: [productReference, name] 是 YAML 的「流式」写法，和分行用 - 列出完全等价，只是更省地方。

⚠ 先别过度优化

把模型拆小有助于避免重复，但第一遍请专注于把 API 描述清楚，别陷进 OpenAPI 的技巧里。优化是第 17 章的事。

从 schema 到代码里的类型

schema 写好之后，实现和消费 API 的代码里都需要对应的类型。可以手写，也可以用生成器（如 openapi-generator、openapi-typescript、datamodel-code-generator）从 OpenAPI 文档自动生成。 下面是 ProductSummary 在三种语言里的样子，注意必填/可选是怎么体现的： 

# 可由 datamodel-code-generator 从 OpenAPI 文档生成
from pydantic import BaseModel

class ProductSummary(BaseModel):
    productReference: int            # type: integer，在 required 里 → 没有默认值
    name: str
    keywords: list[str] | None = None   # 不在 required 里 → 可以缺省
    category: str
    price: float                     # type: number

# 解析并校验一段 JSON：不符合 schema 会抛出 ValidationError
summary = ProductSummary.model_validate_json(
    '{"productReference": 12345, "name": "Cowboy Bebop", "category": "BD", "price": 49.99}'
)
print(summary.price)                 # 49.99

// 可由 openapi-typescript 从 OpenAPI 文档生成
export interface ProductSummary {
  productReference: number;          // type: integer，在 required 里 → 没有问号
  name: string;
  keywords?: string[];               // 不在 required 里 → 带问号，可以缺省
  category: string;
  price: number;                     // type: number
}

// TypeScript 的类型只在编译期存在；运行时要校验的话用 Ajv 或 Zod
const response = await fetch("https://api.shp.ng/products?category=BD");
const products: ProductSummary[] = await response.json();
console.log(products[0]?.price);     // 49.99

// 可由 openapi-generator 从 OpenAPI 文档生成
public record ProductSummary(
    @NotNull Integer productReference,   // type: integer，在 required 里 → @NotNull
    @NotNull String name,
    List<String> keywords,               // 不在 required 里 → 可以为 null
    @NotNull String category,
    @NotNull Double price                // type: number
) {}

// 用 Jackson 把 JSON 解析成 record
ObjectMapper mapper = new ObjectMapper();
ProductSummary summary = mapper.readValue("""
    {"productReference": 12345, "name": "Cowboy Bebop", "category": "BD", "price": 49.99}
    """, ProductSummary.class);
System.out.println(summary.price());     // 49.99

本章小结

  • JSON Schema 是独立的格式，OpenAPI 用它来描述数据。
  • 在添加完 HTTP 操作之后，一边设计数据一边用 JSON Schema 把它写进 OpenAPI。
  • 把资源模型定义为 components.schemas 下的可复用 schema，既能更好地呈现业务概念，也便于跨操作复用。
  • schema 通常以 type 开头：object、array、string、number、integer、boolean。
  • 对象有 properties 映射（属性名 → schema）和 required 列表（必填属性的名字）。
  • 数组的 items 是其元素的 schema。
  • 操作的输入输出 schema 填在上一章留下的 schema 属性里。
  • components.schemas.Name 可以用 $ref: "#/components/schemas/Name" 引用。
  • 用引用来避免重复和不必要的差异；派生模型也定义为可复用 schema。
  • schema 的值可以是内联 schema、引用，或两者混用。

动手练习

  1. 像素画设备的「屏幕」由 36×36 个发光方块组成。屏幕有 id（如 SC001）和一个像素矩阵（数组的数组）。每个像素有 rgb 数组（如 [10, 23, 45]）、0 到 1 之间的 brightness（如 0.3）和 on 标志。除 brightness 外都必填。写出 Screen、Pixels、Pixel 三个可复用 schema。
    参考答案 
    components:
  schemas:
    Screen:
      type: object
      required: [id, pixels]
      properties:
        id:
          type: string
        pixels:
          $ref: "#/components/schemas/Pixels"
    Pixels:
      type: array            # 行的数组
      items:
        type: array          # 每一行是像素的数组
        items:
          $ref: "#/components/schemas/Pixel"
    Pixel:
      type: object
      required: [rgb, on]
      properties:
        rgb:
          type: array
          items:
            type: integer
        brightness:
          type: number
        on:
          type: boolean
    仓库里的 Appendix - Solutions to Exercises/Listing A.10 是书中的答案。
  2. 音乐流媒体 API。用 OpenAPI 描述这次调用：GET /artists/pink-floyd/albums?releaseYear=1969，返回 200 和一个专辑数组，每张专辑有 id、name、mainArtist（含 id、name）、releaseYear，以及可能没有的 comment。
