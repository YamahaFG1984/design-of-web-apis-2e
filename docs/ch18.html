第 18 章

把设计指南自动化

指南说属性名要用驼峰式。可手一滑就把 account 写成了 Account；缩写该写 sourceIBAN 还是 sourceIban 也总拿不准； 搜索操作忘了加分页；分页参数到底叫 cursor 还是 next？ 靠人脑记住所有规则既累又慢。程序员早就有解决办法：lint。这一章用 Spectral 给 OpenAPI 文档做 lint，把指南变成自动检查。

本章目标

  • 理解 API linting 是什么、它和设计指南的关系
  • 会用 Spectral CLI，并看懂一条规则的 given / then 结构
  • 会决定一条规则该检查什么、粒度多大
  • 会用 JSONPath 和别名定位 OpenAPI 文档里的元素
  • 会做五类典型检查：值与键、存在、不存在、引用、部分 schema，以及用自定义函数做跨元素检查
  • 会用严重级别和消息给出有帮助的反馈
  • 会组织、共享规则集，并在具体的 API 上调整和忽略

API linting 是什么

Linter 是分析源代码、找出错误和风格问题的程序。API linting 把同样的做法用在 API 的定义上 —— 也就是 OpenAPI 文档。 它可以在 IDE 里边写边查，可以在终端里跑，也可以接进 CI/CD 流水线；而且不关心文档是手写的还是从代码生成的。

★ Linting 是指南的自动化，而不是指南的替代

没有指南的 linting，就像没分析需求就开始写 GET /products：指南提供的是经过论证的理由（第 16 章），没有它，lint 规则很容易变成无关、繁琐甚至错误的约束，反而导致糟糕的设计。 反过来，指南也应该配上 linting：它替你盯着细节（大小写、安全、模式的套用），让你不必反复翻指南，把精力留给它做不到的事 —— 判断设计是否真的满足了用户需求。

Linting 在设计和开发阶段尤其有价值：它能在上线之前拦住那些本可避免的错误 —— 等上线后再去改一个属性名的大小写，就是破坏性修改了（第 15 章）。

对 linter 的要求

开发规则时
  • 能自动化指南的大部分内容
  • 能自定义检查、复用配置
  • 能返回有助于解决问题的反馈
  • 能把规则分组组织
使用规则时
  • 能从一个集中的地方共享规则
  • 能针对某个 API 调整共享的规则
  • 能添加某个 API 特有的规则
  • 能忽略特定的问题

本章使用 Spectral：开源、强大、灵活、应用广泛，并且满足上面所有要求。 工具在不断演进（尤其是结合 AI 之后），换用别的 linter 时，拿这八条去衡量即可。Linting 也不限于 OpenAPI：Spectral 还能检查 AsyncAPI，gRPC 和 GraphQL 也各有自己的 linter。

一条规则怎样工作

规则集（ruleset）是一个 YAML 文件，rules 下的每个键是一条规则的名字。 given 里的 JSONPath 是一种在 JSON/YAML 文档里选取值的标准写法（RFC 9535）；then 里调用的是 Spectral 自带的或你自己写的函数。

💡 几个实用提示
  • 在 IDE 的终端里运行 Spectral，输出里的位置可以点击，直接跳到 OpenAPI 文件的对应行。
  • spectral lint --help 查看全部选项；-f json 或 -f junit 可以改变输出格式，方便接入 CI/CD。
  • VS Code 等编辑器有 Spectral 扩展：编辑规则集时有提示，编辑 OpenAPI 文件时实时 lint。
  • 规则集也可以用 JSON、JavaScript 或 TypeScript 写，但 YAML 最容易维护，和各种支持 Spectral 的工具也最兼容。

决定规则检查什么

不留神的话，你会造出强制执行不必要甚至错误模式的规则，或者一条规则检查太多东西、反馈让人无从下手。四条原则：

① 只创建指南需要的规则

每条规则都要有出处。用 documentationUrl 指向指南里的对应章节： 

rules:
  resource-name-plural:
    documentationUrl: https://guidelines.intra/principles#resource-names
    description: Resource names must be plural

如果你想加一条 resource-id-number（「资源 ID 必须是数字」）却在指南里找不到依据，要么先去扩充指南并说明这条规则的价值（第 16 章），要么 —— 更可能 —— 在调研之后发现根本不需要它。

② 把需求切成小块

③ 用共享组件简化规则

在把指南切碎之前，先想想能不能往 OpenAPI 组件库（第 17 章）里加一个共享组件。 与其写一堆复杂的规则去检查 500 响应的媒体类型、描述和 schema，不如在库里定义一个标准的 500 响应，然后只用一条规则检查「每个 500 都引用了它」。 文档更好写、更一致，lint 报的问题更少，修起来也更容易。

④ 用简洁的名字和描述检验粒度

规则名与描述评价
api-guidelines
「API 必须遵守我们的设计指南」		✗ 简洁，但什么也没说
search-operation-pagination-filters-success-error
「搜索操作必须有可选的 next 和 size 分页参数、可选的筛选参数、一个 schema 为……的 200 响应……」		✗ 说得很清楚，但明显在用一条规则做太多检查
standard-pagination-parameters
「搜索操作的分页参数必须用 $ref: …#/components/parameters/Pagination 定义」		✓ 只解决一个小问题（而且巧妙地借助了共享组件）

如果名字和描述说不清规则在检查什么，或者又长又罗列了许多检查，粒度就不对。

定位：找到要检查的元素

先确认找对了

开发一条新规则时，先用一个临时的 then 调用 undefined 函数（它断言「这个值不应该存在」，于是凡是找到的元素都会被报出来），在一份测试文档上跑一下，就能看到 given 到底选中了什么： 

rules:
  semantic-version:
    documentationUrl: https://guidelines.intra/principles#versioning
    description: API must use semantic version (like 1.1)
    given:
      - $.info.version          # 文档根（$）下 info 对象的 version 属性
    then:
      - function: undefined     # 临时的：只为了看 given 找到了什么

4:12  warning  semantic-version  "version" property must be undefined  info.version

位置是 info.version —— 正是我们想要的。测试文档要真实、语法正确，既包含想命中的元素，也包含想排除的元素。

JSONPath 速查

写法含义例子
$文档的根$.info.version
a.ba 的 b$.paths
a.*a 对象的所有值，或 a 数组的所有项$.paths.* → 所有路径对象
[a,b]键为 a 或 b 的元素$.paths.*[post,put] → 所有 post 和 put 操作
..b遍历整个文档，找出所有的 b$..parameters → 路径级、操作级和可复用的参数列表
[?(条件)]满足条件的元素；@ 代表当前元素，条件的写法类似 JavaScript$..parameters[?(@.in === "query" || @.in === "path")]
@property条件里表示当前元素的键$.paths[?(@property.match(/}$/))] → 以 } 结尾的路径
a^a 的父元素$..properties^ → 所有定义了 properties 的 schema
ⓘ 两点提醒
  • Spectral 用的是 JSONPath Plus 这个实现，比标准多一些功能（如 ^ 和 @property）。写 given 时参考它的文档。
  • 为了清晰和准确，宁可写几条简单的路径，也不要写一条复杂的。..b 可能会意外抓到 schema 里碰巧叫 b 的属性 —— 在 .. 后面多加几层来避免（$..b.c）。

引用：解析后的文档 vs 原始文档

OpenAPI 文档里的元素可能是内联定义的，也可能藏在 $ref 后面（甚至在另一个文件里）。 好消息是：默认情况下，Spectral 的规则运行在「解析后」的文档上 —— 所有 $ref 都已经被替换成它们指向的内容，你不用操心。 想检查 $ref 本身时，把规则的 resolved 设为 false： 

rules:
  resolved-path-level-parameters:          # resolved 默认是 true
    given:
      - $.paths.*.parameters.*.name        # 即使参数是用 $ref 定义的，也能拿到 accountId
    then:
      function: undefined

  unresolved-path-level-parameters:
    resolved: false                        # 在原始文档上运行
    given:
      - $.paths.*.parameters.*.$ref        # 拿到 "#/components/parameters/AccountId"
    then:
      function: undefined

别名：可复用的路径

很多规则要定位同样的东西 ——「所有参数」「搜索操作」。把这些 JSONPath 定义成别名（alias），既避免重复和出错，也让规则更易读： 

aliases:
  # 按我们的指南：集合资源的路径不以 {路径参数} 结尾，单个资源的路径以它结尾
  CollectionResources:
    - $.paths[?(!@property.match(/}$/))]
  UnitResources:
    - $.paths[?(@property.match(/}$/))]

  # 资源类型 + HTTP 方法 = 典型操作
  SearchOperations:
    - "#CollectionResources.get"          # 扩展别名：在后面接相对的 JSONPath
  ReadOperations:
    - "#UnitResources.get"

  AllParameters:
    - $.paths.*.parameters.*              # 路径级
    - $.paths.*.*.parameters.*            # 操作级
    - $.components.parameters.*           # 可复用的
  AllQueryParameters:
    - "#AllParameters[?(@.in === 'query')]"
  AllPathParameters:
    - "#AllParameters[?(@.in === 'path')]"

rules:
  parameters-path-query-camel-case:
    given:
      - "#AllQueryParameters.name"        # 要加引号，否则 # 会被当成 YAML 注释
      - "#AllPathParameters.name"
    then:
      function: casing
      functionOptions:
        type: camel

检查：验证元素的值

① 值和键的基本检查

rules:
  path-parameter-names:
    given:
      - "#AllPathParameters.name"
    then:                             # 可以有多个检查
      - function: casing              # 核心函数：检查大小写风格
        functionOptions:
          type: camel
      - function: pattern             # 核心函数：检查是否匹配正则
        functionOptions:
          match: /Id$/                # 路径参数的名字必须以 Id 结尾

  query-parameters-optional:
    given:
      - "#AllQueryParameters"
    then:
      - field: required               # field：检查找到的元素的某个子属性
        function: falsy               # 必须为假（false、未定义……）→ 查询参数不能是必填的

  property-names:
    given:
      - $..[schema,schemas]..properties
    then:
      - field: "@key"                 # 特殊的 field：检查对象的每个「键」
        function: casing
        functionOptions:
          type: camel

常用的核心函数：

函数作用
casing大小写风格（camel、snake、kebab、pascal……）
pattern匹配（match）或不匹配（notMatch）正则表达式
truthy / falsy值为真 / 为假
defined / undefined存在 / 不存在
schema值符合给定的 JSON Schema —— 最万能的一个
enumeration、length、alphabetical、xor……取值范围、长度、排序、互斥……

② 确保某个元素存在

对象里的键：用 field + defined。

  error-500-defined:
    given:
      - $.paths.*.*.responses         # 定位到 responses 对象（它一定存在）
    then:
      field: "500"                    # 再检查它有没有 "500" 这个键
      function: defined
⚠ 不能直接定位那个可能不存在的东西

如果把 given 写成 $.paths.*.*.responses.500，那么没有定义 500 的操作根本不会被选中，then 也就不会执行 —— 规则永远不报错。要定位它的父元素，再用 field 检查。

数组里的项：用 field + schema 函数，配合 JSON Schema 的 contains（数组里至少有一项符合）和 const（等于这个值）。

  correlation-id-defined:             # 每条路径都要有 Correlation-Id 请求头
    given:
      - $.paths.*
    then:
      - field: parameters             # 路径级参数列表不存在时也能发现
        function: schema
        functionOptions:
          schema:
            type: array
            contains:                 # 数组里要有一项……
              properties:
                in:
                  const: header       # ……in 等于 header
                name:
                  const: Correlation-Id    # ……name 等于 Correlation-Id

③ 确保某个元素不存在

直接定位不该出现的东西，用 undefined：

  no-404-without-path-parameter:
    description: Operations on a path without path parameters must not have a 404
    given:
      - $.paths[?(!@property.match(/{/))].*.responses.404
    then:
      function: undefined

  no-operation-level-correlation-id:
    given:
      - $.paths.*.*.parameters[?(@.name === "Correlation-Id")]
    then:
      function: undefined

④ 检查引用

确保用了组件库里的标准组件，或者用了引用而不是内联定义。记得 resolved: false：

  500-defined-and-with-shared-component:
    resolved: false
    given:
      - $.paths.*.*.responses
    then:
      - field: "500"                  # 必须存在，而且必须正好是这个引用
        function: schema
        functionOptions:
          schema:
            const:
              $ref: "./library.openapi.yaml#/components/responses/Error500"

  shared-correlation-id:
    resolved: false
    given:
      - $.paths.*
    then:
      - field: parameters
        function: schema
        functionOptions:
          schema:
            type: array
            contains:
              const:
                $ref: "./library.openapi.yaml#/components/parameters/CorrelationId"

  response-schema-ref:                # 响应体的 schema 必须是引用，不能内联
    resolved: false
    given:
      - $.paths.*.*.responses.*.content.application/json.schema
    then:
      - field: $ref
        function: defined

⑤ 检查 schema 的一部分

指南规定：搜索操作的响应必须是一个对象，里面有一个 data 数组，数组的元素是对象 —— 至于元素具体长什么样，各个操作不同，不关心。 这时不能用 const 去比对整个 schema，而要写一个「JSON Schema 的 JSON Schema」： 

  list-response:
    # 搜索操作的所有成功响应的 schema
    given: "#SearchOperations.responses[?(@property.match(/^2/))].content.application/json.schema"
    then:
      function: schema
      functionOptions:
        schema:                       # ↓ 这是在描述「被检查的那个 schema 应该长什么样」
          type: object
          required: [required, properties]
          properties:
            required:                 # 被检查的 schema 的 required 必须是 [data]
              type: array
              const: [data]
            properties:               # 被检查的 schema 的 properties……
              type: object
              properties:
                data:                 # ……必须有 data
                  required: [type, items]
                  properties:
                    type:
                      const: array    # ……data 的 type 是 array
                    items:
                      required: [properties]     # ……元素是带 properties 的对象
                      properties:
                        properties:
                          type: object
ⓘ 脑子要转个弯

被检查的值本身就是一个 JSON Schema，所以 properties 这个词会出现两层含义：外层的 properties 是「我这个校验用的 schema 的属性」，内层名为 properties 的键是「被检查的那个 schema 里叫 properties 的属性」。schema 函数的校验反馈可能不太好懂，下一节讲怎么让它变友好。

⑥ 跨元素检查：自定义函数

有些检查要比较文档里两个不同位置的东西：创建操作的请求和响应是否用了同一个读写合一的 schema（第 17 章）？搜索的筛选参数是否对应返回模型里的属性？ 核心函数做不到，要写自定义函数。Spectral 的自定义函数用 JavaScript 写，放在规则集旁边的 functions/ 目录里： 

functions:
  - consistentReferences          # 对应 ./functions/consistentReferences.js（文件名，不是函数名）

rules:
  consistent-rw-reference:
    resolved: false
    given:
      - $.paths.*[post,put]
    then:
      - function: consistentReferences      # 和核心函数一样使用

/**
 * @param input   given 找到的一个值（这里是一个操作对象）
 * @param options then 里的 functionOptions
 * @param context 上下文：input 在文档中的位置（context.path）、整个文档等
 * @returns 问题列表；没有问题就返回空数组
 */
function compareReferences(input, options, context) {
  const problems = [];

  const requestRef = input.requestBody.content["application/json"].schema["$ref"];

  const successStatus = Object.keys(input.responses).find((k) => k.match(/^2/));
  const responseRef = input.responses[successStatus].content["application/json"].schema["$ref"];

  if (requestRef !== responseRef) {
    // 报两个问题：一个指向请求，一个指向响应
    problems.push({
      message: "Request schema must match response schema",
      path: [...context.path, "requestBody", "content", "application/json", "schema", "$ref"],
    });
    problems.push({
      message: "Response schema must match request schema",
      path: [...context.path, "responses", successStatus, "content", "application/json", "schema", "$ref"],
    });
  }
  return problems;
}

export default compareReferences;     // 必须是默认导出

每个问题有一个 message 和一个可选的 path（不给就用 input 自己的位置）。仓库里的完整版本还用 createRulesetFunction 声明了输入和选项的 schema，并支持一个 requestSuffix 选项。

反馈：让问题容易被解决

规则查出问题后，输出要让人看得懂、改得了。它应该说明：是什么问题、全部的问题、在哪里、多重要、怎么修。前三样 Spectral 已经做了（同一个问题即使来自被多处引用的组件，也只报一次），我们要管的是后两样。

严重级别

severity 有四个取值。怎么解读由你定；下面是作者的建议，对应指南里的 MUST / SHOULD / MAY：

severity含义例子
error必须修属性名不是驼峰式；没有定义安全作用域
warn（默认）如果确实是问题，应该修POST 的请求体没有任何必填属性 —— 很少见，多半是漏了
info可选的改进搜索操作可以加上筛选条件
hint需要进一步调查用了表示文件上传的媒体类型 —— 请做影响分析

建议总是显式写出 severity：这会逼你思考这条规则要查的问题到底有多重要。

有助于解决问题的消息

消息的来源有三个，优先级从高到低：规则的 message → 规则的 description → 函数返回的消息。message 里可以用占位符：

rules:
  property-name-camel:
    description: Property names must be camelCased
    documentationUrl: https://guidelines.intra/principles#naming
    severity: error
    message: "{{property}} must be camelCased"      # 用了占位符必须加引号
    given:
      - $..[schema,schemas]..properties
    then:
      field: "@key"
      function: casing
      functionOptions:
        type: camel

  204-no-body:
    severity: error
    message: Remove the response body (content) or change status (200, 201)
    given:
      - $.paths.*.*.responses.204.content
    then:
      function: undefined
占位符替换成
{{property}}问题路径的最后一段（如属性名 buyPRice）
{{path}}问题的完整路径
{{value}}找到的值
{{description}}规则的描述
{{error}}函数返回的消息
函数默认的消息

must be camel case —— 读的人可能不知道 camel case 是什么。

"content" property must be undefined —— 所以呢？

自定义的消息

buyPRice must be camelCased —— 指明了是谁，还示范了什么是驼峰式。

Remove the response body (content) or change status (200, 201) —— 给出了两种修法。

这正是第 9 章讲的错误处理原则：反馈要能指导修复。

因为严重级别或消息而拆分规则

  • 缺失和写错的严重程度不同。指南说搜索操作可以有一个字符串类型的 q 参数。 那就需要两条规则：search-q-defined（info：没定义，建议加上）和 search-q-valid（error：定义了但类型不对）。
  • 一条消息说不清多个检查。Spectral 不支持为每个 then 单独定制消息。如果一条规则做了好几种检查导致消息含糊，就把它拆开。这往往也说明规则的粒度本来就不对。

组织与使用规则

把规则分成多个规则集

规则多了以后，按主题拆成小的规则集，再用一个主规则集通过 extends 把它们汇总：

# ---------- errors.spectral.yaml ----------
description: Error handling
documentationUrl: https://guidelines.intra/errors
rules:
  error-500-defined:
    severity: error
    message: Operation misses a 500 response
    given:
      - $.paths.*.*.responses
    then:
      field: "500"
      function: defined

# ---------- openapi.spectral.yaml ----------
extends:
  - [spectral:oas, off]            # 导入 Spectral 内建的 OpenAPI 规则，但全部先关掉
rules:
  oas3-schema: true                # 只开启需要的：OpenAPI 文档的语法必须合法
  path-keys-no-trailing-slash: error     # 开启并覆盖其严重级别：路径不能以 / 结尾

# ---------- guidelines.spectral.yaml（主规则集）----------
extends:
  - ./errors.spectral.yaml         # 相对路径、绝对路径或 URL 都可以
  - ./search.spectral.yaml
  - ./openapi.spectral.yaml
💡 把规则集放进代码仓库并打版本

规则集要随指南一起演进。保留各个历史版本，以免指南的修改给现有 API 的 CI/CD 流水线带来破坏性的 lint 变化（除非你就是想这么做）。

在具体的 API 上使用

在 API 的仓库里放一个 .spectral.yaml（用这个文件名，运行时就不用加 -r）：导入共享的指南，按需微调，加上本 API 特有的规则，忽略不打算修的问题。

extends:
  - https://guidelines.intra/guidelines.spectral.yaml     # 从集中的位置拉取共享的规则

rules:
  # ---- 调整导入的规则 ----
  pagination: info                    # 在这个 API 上降低严重级别
  vocabulary-experimental: true       # 开启一条默认关闭（recommended: false）的实验性规则

  # ---- 本 API 特有的规则 ----
  bnkng-http-sig:
    description: Every path must use the HTTP signature parameter
    severity: error
    given:
      - $.paths.*
    then:
      - field: parameters
        function: schema
        functionOptions:
          schema:
            type: array
            contains:
              const:
                $ref: "#/components/parameters/HttpSignature"

# ---- 忽略不打算修的问题 ----
overrides:
  - files:
      - "**/openapi.yaml#/paths/~1accounts/get"     # 文件 + 指向问题位置的 JSON Pointer
    rules:
      search-q-defined: off

overrides 里的 JSON Pointer 由 CLI 输出的点分路径改写而来：paths./accounts.get → 前面加 #，. 换成 /，而路径里本身的 / 要转义成 ~1 → #/paths/~1accounts/get。

把 lint 接进你的构建流程

Spectral 是 Node.js 工具，但任何语言的项目都能用它：CLI 的 -f json 输出是结构化的，用脚本包一层就能接进自己的构建。 下面的代码运行 lint，按严重级别汇总，有 error 时让构建失败（TypeScript 版直接调用 Spectral 的库，不经过 CLI）： 

"""lint_api.py —— 在 Python 项目（或任何 CI）里运行 Spectral 并汇总结果"""
import json, subprocess, sys

SEVERITY = {0: "error", 1: "warn", 2: "info", 3: "hint"}

result = subprocess.run(
    ["npx", "spectral", "lint", "openapi.yaml", "--format", "json", "--quiet"],
    capture_output=True, text=True,
)
problems = json.loads(result.stdout or "[]")

for p in sorted(problems, key=lambda p: p["severity"]):
    line = p["range"]["start"]["line"] + 1          # Spectral 的行号从 0 开始
    where = ".".join(str(s) for s in p["path"])
    print(f"{SEVERITY[p['severity']]:5} L{line:<4} {p['code']:32} {p['message']}  ({where})")

errors = [p for p in problems if p["severity"] == 0]
print(f"\n共 {len(problems)} 个问题，其中 {len(errors)} 个必须修复")
sys.exit(1 if errors else 0)                        # 有 error 就让构建失败

// lint-api.ts —— 直接调用 Spectral 的库，不经过 CLI
// npm install @stoplight/spectral-core @stoplight/spectral-ruleset-bundler @stoplight/spectral-runtime
import { readFileSync } from "node:fs";
import * as fs from "node:fs";
import { Spectral, Document } from "@stoplight/spectral-core";
import { Yaml } from "@stoplight/spectral-parsers";
import { bundleAndLoadRuleset } from "@stoplight/spectral-ruleset-bundler/with-loader";
import { fetch } from "@stoplight/spectral-runtime";

const SEVERITY = ["error", "warn", "info", "hint"];

const spectral = new Spectral();
spectral.setRuleset(await bundleAndLoadRuleset(`${process.cwd()}/.spectral.yaml`, { fs, fetch }));

const document = new Document(readFileSync("openapi.yaml", "utf8"), Yaml, "openapi.yaml");
const problems = await spectral.run(document);

for (const p of [...problems].sort((a, b) => a.severity - b.severity)) {
  const line = p.range.start.line + 1;              // 行号从 0 开始
  console.log(
    `${SEVERITY[p.severity].padEnd(5)} L${String(line).padEnd(4)} ${String(p.code).padEnd(32)} ` +
    `${p.message}  (${p.path.join(".")})`,
  );
}

const errors = problems.filter((p) => p.severity === 0);
console.log(`\n共 ${problems.length} 个问题，其中 ${errors.length} 个必须修复`);
process.exit(errors.length ? 1 : 0);                // 有 error 就让构建失败

// LintApi.java —— 在 Java 项目（或 Maven/Gradle 的构建步骤）里运行 Spectral 并汇总结果
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.util.*;

public class LintApi {
    static final String[] SEVERITY = {"error", "warn", "info", "hint"};

    public static void main(String[] args) throws Exception {
        Process process = new ProcessBuilder(
                "npx", "spectral", "lint", "openapi.yaml", "--format", "json", "--quiet")
            .redirectError(ProcessBuilder.Redirect.DISCARD)
            .start();
        JsonNode problems = new ObjectMapper().readTree(process.getInputStream());
        process.waitFor();

        List<JsonNode> sorted = new ArrayList<>();
        problems.forEach(sorted::add);
        sorted.sort(Comparator.comparingInt(p -> p.get("severity").asInt()));

        int errors = 0;
        for (JsonNode p : sorted) {
            int severity = p.get("severity").asInt();
            if (severity == 0) errors++;
            int line = p.at("/range/start/line").asInt() + 1;       // 行号从 0 开始
            List<String> path = new ArrayList<>();
            p.get("path").forEach(segment -> path.add(segment.asText()));
            System.out.printf("%-5s L%-4d %-32s %s  (%s)%n",
                SEVERITY[severity], line, p.get("code").asText(),
                p.get("message").asText(), String.join(".", path));
        }

        System.out.printf("%n共 %d 个问题，其中 %d 个必须修复%n", sorted.size(), errors);
        System.exit(errors > 0 ? 1 : 0);                            // 有 error 就让构建失败
    }
}
ⓘ Linter 做不到的事

Linter 只看得到 API 的描述。它不知道某个操作是否该设计成长操作（那取决于业务和架构），更不知道设计是否满足了用户需求。 可以期待未来结合了 AI 的 linter 更聪明 —— 能自动修复、能参考更广的上下文 —— 但判断「做对了事」仍然是设计者的职责。

本章小结

  • Linting 是用程序（linter）分析源代码以发现错误或风格问题。API linting 用 API linter 分析 OpenAPI 文档，发现设计问题和 OpenAPI 写法问题，并防止日后本可避免的破坏性修改；用它来自动化设计指南。
  • Spectral 是一个 API linter：能自动化指南的大部分内容、可自定义和复用、能给出有帮助的反馈、能组织和共享规则，并能在具体的 API 上调整规则和忽略问题。替代品也应满足这些要求。
  • 在 rules 下的每条规则里，用 given 的 JSONPath 找到要检查的元素，用 then.function 检查它们。
  • 用 documentationUrl 指向指南，只创建有依据、有必要的规则；基于指南里的小陈述和共享组件创建规则，再组合起来覆盖更大的主题；用简洁的名字和描述检验粒度。
  • JSONPath：$（根）、a.b、a.*、..b、[a,b]、a[?(条件)]。
  • 在 aliases 下定义可复用的路径，用 #AliasName 使用、#AliasName.相对路径 扩展；用「资源类型 + HTTP 方法」定位典型操作。
  • 用 pattern、casing、falsy、truthy 等核心函数检查原子值；用 field: "@key" 检查对象的键。
  • 用 field + defined 检查对象里某个键存在；用 schema 函数配合 contains 和 const 检查数组里有某一项；用 undefined 确保某个元素不存在。
  • 用 resolved: false 检查是否使用了对本地或共享组件的引用。
  • 用 schema 函数和「JSON Schema 的 JSON Schema」确保数据模型符合某个模式；用自定义函数做跨元素的检查。
  • 用 severity 表明问题是必须修的错误、可能的问题、可选的改进，还是需要进一步调查；用 message（可含占位符）给出有助于解决问题的消息。
  • 把规则分组，用 extends 导入规则集；在 OpenAPI 文档旁边放一个 .spectral.yaml，导入并定制共享的指南、添加 API 特有的规则，并用 overrides 忽略不需要解决的问题。
