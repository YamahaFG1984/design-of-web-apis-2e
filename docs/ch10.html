第 10 章

好用、可互操作的操作流

想象用购物 API 买 10 本书：先搜商品，再列促销，自己把两份数据合并才能算出真实价格；然后调用 10 次「加入购物车」；最后结账失败 —— 库存不够。 每个操作单独看都没毛病，串起来却是一场折磨。这一章把视角从单个操作拉高到一连串调用。

本章目标

  • 理解什么是操作流，以及好的操作流有哪些特征
  • 会发现流程中的三类问题：重复调用、要消费者加工数据、可避免的错误
  • 会用四种手段优化流程：增强操作、新增专用操作、合并操作、补充数据
  • 避免让 API 的流程绑死消费者的界面流程
  • 设计灵活的「保存数据」流程：既能分步保存，也能一步到位

什么是好的操作流

操作流（operation flow）是消费者为了完成一个用例而进行的一连串 API 调用。它既包括第 2 章识别能力时描述的那些用例， 也包括消费者利用 API 的通用性自己发明的新用例。

以租车为例。最初的流程有六步，每一步单独看都好用，但整体可以大幅改进：

好的操作流：

  • 建立在好用的操作和数据之上。搜索返回的车辆 ID 就是读取和租车时要用的那个 ID；租车失败时给出有用的反馈。
  • 被当作一个整体来设计。零件都好，拼起来不一定好。
  • 简洁。步骤尽量少。
  • 灵活。不约束消费者的调用顺序；最好能从中间某一步切入 —— 这也提高了互操作性。
  • 在流程的语境里满足需求。如果 API 同时处理租车和卖车，租车流程里用「搜索可租的车」比通用的「搜索车」更合适。
  • 各步骤互相帮助。前一步的输出能直接当后一步的输入，尽量减少加工和出错。
  • 一致、标准。相似的用例用相似的流程。比如租车和往门店加车都要上传文件（驾照、行驶证），那就用同一套上传模式。获取 API 凭证的流程则由安全框架标准化（第 12 章）。
⚠ 流程直接影响最终用户

API 流程里的每一步、每一个错误，最终都会变成用户在界面上要点的按钮、要看的报错。

什么时候优化、怎么优化

流程优化排在数据（第 8 章）和操作（第 9 章）之后，因为要先有打磨好的零件。也不要在识别能力时（第 2 章）就做，那会拖慢讨论，甚至偏离需求。

找问题：问四个问题
  • 这一步真的需要吗？
  • 这个错误能预防吗？
  • 能不能不让消费者加工输出来得到下一步的输入？
  • 流程中保存数据的方式合理吗？
做优化：四种手段
  • 给操作增加与用例相关的功能（如筛选项）
  • 新增针对用例的专用操作
  • 合并操作
  • 补充针对用例的数据（提示性的或加工好的）

案例一：让转账流程简洁、少出错、灵活

起点

用银行 API 从一个账户向另一个账户转账：

用例步骤操作输出问题
列出自己的付款账户列出账户账户列表消费者得自己排除 BLOCKED 的账户
列出已登记的收款人列出收款人收款人列表
列出自己的收款账户列出账户账户列表和第一步是同一次调用；又得排除 BLOCKED；还得和收款人合并
转账转账错误：付款/收款账户无效；金额不在允许范围内

转账可能失败的原因很多，而消费者几乎没法提前知道：

  • 付款账户不属于用户，或账户状态不允许转账；
  • 某些付款/收款组合不被允许（比如从储蓄账户转给别人）；
  • 金额不能超过付款账户余额；储蓄账户有最低转入额和余额上限；
  • 转给他人时，有一个取决于用户等级和近 30 天累计转账额的上限。

只有四次调用，看起来很短。但开发者要写一堆容易出错的代码，最终用户则只能靠试错 —— 再好的错误提示也挽救不了这种体验。

逐步优化

  1. 同样的读取只调一次。「列出付款账户」和「列出收款账户」调的是同一个操作、拿的是同一份数据。合并为一步。 （这不改变 API 设计，只改变我们描述用例的方式。）
  2. 给操作加筛选？小心。加一个 GET /accounts?status=not:BLOCKED 能省掉消费者的过滤 —— 但「被冻结的账户不能转账」是银行的内部规则，不该让消费者知道。 换成 GET /accounts?transfer=enabled 呢？意图清楚了，可「能否用于转账」已经超出了「账户」这个资源的范围，一个重要的能力被藏进了通用操作里（第 9 章）。
  3. 新增专用操作。GET /transfer-sources：「列出转账付款方」，只返回可以作为付款方的账户。 它专属于转账用例，开发者也很容易把它和转账请求里的 source 属性联系起来。
  4. 合并成专用操作。收款方 = 自己的可用账户 + 已登记的收款人。「转账收款方」这个聚合概念在业务上是成立的。 但不是所有付款/收款组合都合法，所以操作应该是「列出某个付款方可用的收款方」：GET /transfer-sources/{accountId}/destinations。 （路径用了可互操作的 accountId；这并不意味着 GET /transfer-sources/{accountId} 也要存在 —— 没有需求就不加。）
  5. 补充加工好的数据。金额范围取决于付款方余额、收款方类型、用户等级、近期累计额……与其把这些原始数据散落在各处让消费者去算， 不如让实现算好，把现成的金额范围直接放在每个「付款方—收款方」组合上。

别绑死消费者的界面

优化到这一步，数据不用加工了，错误也几乎不会发生了。但还有一个问题：

⚠ 聚合要有度

任何优化 —— 尤其是合并操作 —— 都不能以牺牲数据和操作的清晰度为代价。 「一次返回所有账户、所有转账和全部用户资料」从转账或银行业务的角度看都没有意义，既难懂又难用。 聚合必须在业务上讲得通，而不是为某个消费者量身定做。

ⓘ 错误没有完全消失

有了这些数据引导，转账几乎不会失败。但意外的服务端错误、或者流程进行中余额恰好变化导致的错误，仍然可能发生 —— 第 9 章的错误处理依然必要。

案例二：灵活的数据保存流程

起点：开户

用银行 API 开一个账户的原始流程：

逐步优化

  1. 允许部分保存。先收集最少的关键数据，其余的让消费者想什么时候给就什么时候给、顺序任意。 邮箱对整个流程至关重要，所以在发起申请时就要求提供；其他一切都通过「更新」操作逐步补齐。 但有一条底线：不接受无效数据。缺数据可以，错数据不行。
  2. 谨慎地合并保存操作。服务、网点、银行卡、户主信息都是「开户申请」这个概念的组成部分， 把各自的「添加/更新」合并进「更新开户申请」是说得通的。 但「列出服务」「列出网点」「列出银行卡种类」不该合并 —— 它们是互不相干的概念，合在一起筛选也没法做。好在分开也不影响流程的灵活性。
  3. 让校验更顺滑，并把它和「完成」分开。部分保存有个副作用：消费者怎么知道还缺什么？每次更新后都调一次「校验」太麻烦。 更好的办法：在申请数据里直接带上状态信息。发起和更新操作仍然返回 2XX（申请不完整在这里不算错误），同时返回：
    • status：INCOMPLETE（还缺必填数据）或 COMPLETE（齐了）；
    • messages：格式沿用第 9 章的错误列表，说明具体缺什么。
    状态变成 COMPLETE 后，消费者可以把全部数据展示给用户做最后确认，然后才调用「确认申请」。
  4. 同时支持一步到位。不是所有消费者都有需要一步步填表的最终用户 —— 比如银行的合作方用批处理程序开户。 两种做法：加一个查询参数 POST /account-applications?completion=true（数据不全就报错）； 或者更明确地拆成两个资源：/account-applications（一次给全）和 /partial-account-applications（分步）。
  5. 把消费者引导到最终的资源。分步申请确认之后，就变成了一个正式的开户申请。可以返回 201 Created 加 Location 和数据； 也可以用我们还没用过的 3XX 重定向：返回 303 See Other 和 Location 头，不带响应体，由消费者决定要不要跟过去取数据。
⚠ 先确认「任意顺序」可行

业务规则或实现上的限制有时会让某些数据必须先于另一些保存。设计前和领域专家、实现团队确认（第 14 章）。

实现分步保存

关键在于区分两类问题：无效的数据立刻拒绝，缺少的数据只在元数据里提示。

from fastapi import FastAPI, HTTPException, Response
from pydantic import BaseModel, EmailStr

app = FastAPI()
REQUIRED = ["services", "branchId", "cardType", "holderName", "holderAddress"]
CARD_TYPES = {"debit", "credit"}

class ApplicationInit(BaseModel):
    email: EmailStr                       # 发起时唯一必填：能联系到申请人

class ApplicationPatch(BaseModel):        # 其余全部可选，任意顺序提供
    services: list[str] | None = None
    branchId: str | None = None
    cardType: str | None = None
    holderName: str | None = None
    holderAddress: str | None = None

def with_metadata(application: dict) -> dict:
    """数据 + 元数据：每次保存后都告诉消费者还缺什么"""
    missing = [name for name in REQUIRED if not application.get(name)]
    return {
        "data": application,
        "metadata": {
            "status": "INCOMPLETE" if missing else "COMPLETE",
            "messages": [{"type": "MISSING_PROPERTY",
                          "detail": f"{name} is missing",
                          "source": {"location": "body", "pointer": f"#/{name}"}}
                         for name in missing],
        },
    }

@app.post("/partial-account-applications", status_code=201)
def initiate(body: ApplicationInit):
    application = store.create({"email": body.email})
    return with_metadata(application)                 # 201：不完整不是错误

@app.patch("/partial-account-applications/{application_id}")
def update(application_id: str, body: ApplicationPatch):
    application = store.get(application_id) or _not_found()
    changes = body.model_dump(exclude_none=True)
    if "cardType" in changes and changes["cardType"] not in CARD_TYPES:
        raise HTTPException(400, f"Invalid cardType; allowed: {sorted(CARD_TYPES)}")  # 无效数据：拒绝
    application.update(changes)
    return with_metadata(application)

@app.post("/partial-account-applications/{application_id}/validations")
def validate(application_id: str):
    application = store.get(application_id) or _not_found()
    result = with_metadata(application)
    if result["metadata"]["status"] != "COMPLETE":
        raise HTTPException(400, result["metadata"]["messages"])     # 现在缺数据才算错误
    final = store.promote(application)                # 变成正式的开户申请
    return Response(status_code=303,                  # 303 See Other：去这里看结果
                    headers={"Location": f"/account-applications/{final['id']}"})

import { Hono } from "hono";
import { z } from "zod";
import { zValidator } from "@hono/zod-validator";

const app = new Hono();
const REQUIRED = ["services", "branchId", "cardType", "holderName", "holderAddress"] as const;

const ApplicationInit = z.object({ email: z.string().email() });   // 发起时唯一必填：能联系到申请人
const ApplicationPatch = z.object({                                 // 其余全部可选，任意顺序提供
  services: z.array(z.string()),
  branchId: z.string(),
  cardType: z.enum(["debit", "credit"]),                            // 无效的值会被 zValidator 以 400 拒绝
  holderName: z.string(),
  holderAddress: z.string(),
}).partial();

type Application = { id: string; email: string } & z.infer<typeof ApplicationPatch>;

/** 数据 + 元数据：每次保存后都告诉消费者还缺什么 */
function withMetadata(application: Application) {
  const missing = REQUIRED.filter((name) => application[name] === undefined);
  return {
    data: application,
    metadata: {
      status: missing.length ? "INCOMPLETE" : "COMPLETE",
      messages: missing.map((name) => ({
        type: "MISSING_PROPERTY",
        detail: `${name} is missing`,
        source: { location: "body", pointer: `#/${name}` },
      })),
    },
  };
}

app.post("/partial-account-applications", zValidator("json", ApplicationInit), (c) => {
  const application = store.create(c.req.valid("json"));
  return c.json(withMetadata(application), 201);                    // 201：不完整不是错误
});

app.patch("/partial-account-applications/:id", zValidator("json", ApplicationPatch), (c) => {
  const application = store.get(c.req.param("id"));
  if (!application) return c.json({ message: "Application not found" }, 404);
  Object.assign(application, c.req.valid("json"));
  return c.json(withMetadata(application));
});

app.post("/partial-account-applications/:id/validations", (c) => {
  const application = store.get(c.req.param("id"));
  if (!application) return c.json({ message: "Application not found" }, 404);
  const { metadata } = withMetadata(application);
  if (metadata.status !== "COMPLETE") {
    return c.json({ errors: metadata.messages }, 400);              // 现在缺数据才算错误
  }
  const final = store.promote(application);                         // 变成正式的开户申请
  return c.redirect(`/account-applications/${final.id}`, 303);      // 303 See Other
});

@RestController
@RequestMapping("/partial-account-applications")
public class PartialApplicationController {

    record ApplicationInit(@NotNull @Email String email) {}          // 发起时唯一必填：能联系到申请人
    record ApplicationPatch(List<String> services, String branchId, CardType cardType,
                            String holderName, String holderAddress) {}  // 其余全部可选
    enum CardType { debit, credit }                                  // 无效的值会被 Spring 以 400 拒绝

    record Message(String type, String detail, Map<String, String> source) {}
    record Metadata(String status, List<Message> messages) {}
    record Envelope(Application data, Metadata metadata) {}

    /** 数据 + 元数据：每次保存后都告诉消费者还缺什么 */
    private Envelope withMetadata(Application application) {
        List<Message> messages = application.missingProperties().stream()
            .map(name -> new Message("MISSING_PROPERTY", name + " is missing",
                                     Map.of("location", "body", "pointer", "#/" + name)))
            .toList();
        return new Envelope(application,
            new Metadata(messages.isEmpty() ? "COMPLETE" : "INCOMPLETE", messages));
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)                              // 201：不完整不是错误
    public Envelope initiate(@Valid @RequestBody ApplicationInit body) {
        return withMetadata(store.create(body.email()));
    }

    @PatchMapping("/{id}")
    public Envelope update(@PathVariable String id, @RequestBody ApplicationPatch body) {
        Application application = store.find(id);
        application.merge(body);                                     // 只覆盖提供了的属性
        return withMetadata(application);
    }

    @PostMapping("/{id}/validations")
    public ResponseEntity<?> validate(@PathVariable String id) {
        Envelope result = withMetadata(store.find(id));
        if (!result.metadata().status().equals("COMPLETE")) {        // 现在缺数据才算错误
            return ResponseEntity.badRequest().body(Map.of("errors", result.metadata().messages()));
        }
        Application finalApplication = store.promote(result.data()); // 变成正式的开户申请
        return ResponseEntity.status(HttpStatus.SEE_OTHER)           // 303 See Other
            .location(URI.create("/account-applications/" + finalApplication.id()))
            .build();
    }
}
💡 通用的 data + metadata 结构

上一章给列表响应引入了 {data, metadata} 的结构。把它推广到所有响应，就能在任何地方干净地把「业务数据」和「关于这份数据的信息」（缺什么、哪里不对、分页……）分开。

本章小结

  • 操作流是消费者为完成一个用例而进行的一连串 API 调用。
  • 好的操作流建立在好用的数据和操作之上，但还必须被当作整体来看。
  • 流程要简洁：步骤尽量少。
  • 流程要灵活：适用于各种场景，少约束界面流程，最好能从中间某一步切入。
  • 流程中的操作要在该流程的语境里满足需求，并帮助调用流程里的其他操作。
  • 相似的流程复用相似的模式，以求一致、标准、可猜测。
  • 在改进完数据和操作之后再优化流程。
  • 找优化点：质疑步骤的必要性，检查错误和数据加工能否避免，重新考虑数据的保存方式。
  • 优化手段：增加针对用例的功能或数据、新增专用操作、合并操作 —— 但不能牺牲清晰度和范围。
  • 允许部分保存，让消费者按需收集数据；发起流程时别忘了收集最少的关键数据。
  • 把校验和完成分开：让消费者知道还缺什么，让最终用户在结束前有机会核对。
  • 同时支持一步到位和分步保存，让消费者自己选择。

动手练习

  1. 医疗预约 API 的挂号流程：GET /doctors（返回所有医生）→ GET /doctors/{doctorId}/slots（返回该医生已占用和空闲的时段）→ PATCH /doctors/{doctorId}/slots/{slotId}（把患者信息写进时段）。有什么问题？
    参考答案 ① 要消费者加工数据：从全部时段里自己挑出空闲的 → 提供筛选或专用操作「列出可预约时段」。 ② 必须先选医生再看时段，流程死板 → 提供跨医生搜索：GET /available-slots?specialty=…&date=…。 ③ 「预约」这个核心能力被藏在「更新时段」里，而且暴露了提供者的数据模型 → POST /appointments（请求体：时段 ID、患者信息），以后还能自然地取消、改期。 ④ 可避免的错误：两人同时抢同一个时段时，要有明确的错误反馈。
  2. 装修报价 API：发起报价 → 设置房间数（已设置则失败）→ 逐个添加房间（上一个房间没填完则失败）→ 依次设置面积、现状、可达性（顺序错了就失败）→ 添加服务 → 描述项目（房间没填完则失败）→ 估价。如何改进？
    参考答案 这是典型的「保存步骤绑死流程」，而且明显在照着一个向导式 UI 设计。改进： ① 支持一步到位：POST /quotes 一次提交项目描述和所有房间（每个房间含面积、现状、可达性、服务），直接返回估价 —— 对「快速粗估」来说这才是主路径。 ② 支持分步：POST /partial-quotes 加 PATCH 任意顺序补充，响应里用 status 和 messages 说明还缺什么。 ③ 去掉「房间数」这个步骤 —— 它可以从房间列表推断出来。 ④ 把一个房间的面积、现状、可达性合并成对「房间」资源的一次创建/更新。
  3. 挑一个你熟悉的 App 里的多步表单（注册、下单、报销……），画出它背后可能的 API 调用序列，然后用本章的四个问题检查它。
