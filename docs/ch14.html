第 14 章

让设计适配上下文

日常手表和潜水表都是看时间的，但后者要在高压下、被戴着厚手套的人操作 —— 设计完全不同。API 也一样。 如果合作方需要实时知道商品价格的变动，让他们每秒读一遍全部商品显然不是好设计。 除了安全和效率，数据的性质、操作的性质、消费者的限制、系统和业务的现实，都会约束我们的设计。

本章目标

  • 会识别、质疑、然后才适应上下文约束
  • 处理常见的消费者和提供者限制：不支持的 HTTP 方法、不同的数据格式、计划内停机、URL 兼容性
  • 设计文件的上传和下载，包括大文件和委托给存储系统的情况
  • 用 Webhook 把提供者一侧发生的事件通知给消费者
  • 用轮询和回调处理耗时很长的操作
  • 知道什么时候该考虑 REST 以外的 API 类型

上下文如何影响设计

因素例子设计中要问的问题
消费者的限制银行业的老系统只会用 POST 和 XML目标消费者相对于我们惯常的做法有什么限制吗？
领域的约束银行系统之间普遍使用 ISO 20022 XML 报文行业、组织或领域里有既定的标准或惯例吗？
通信方式「与顾问实时聊天」「有新交易时通知合作方」需要「消费者请求—提供者响应」以外的通信方式吗？
数据的性质开户要上传证件；现有的交易 ID 里含 /涉及文件吗？数据能安全地放进 URL 吗？
操作的性质自动审核证件要 1 分钟；有时还需要人工审核有超过几秒钟的处理吗？有人参与吗？
实现的限制开发说「用 Java 实现不了部分更新」这个真的实现不了吗？
基础设施与业务转账子系统每晚 0–1 点停机跑批；跨行网络节假日关闭能力跨了多个系统或团队吗？系统和业务是 7×24 运转的吗？

「Java 实现不了部分更新」？能实现。「那些消费者只会 POST 和 XML」？老银行系统早就支持更多了。 和排查性能问题一样（第 13 章），先找根因。不过，并非所有约束都是「问题」—— 有时只是需要换一种更合适的设计模式或工具。

ⓘ 取舍会变成先例

如果同一个难题在不同地方反复出现，为它做的取舍就会演变成标准化的解决方案（比如用 POST /search 处理敏感的查询条件）。 要始终如一地应用它 —— 设计指南（第 16 章）会帮你做到。 另外，如果能力横跨多个团队，一个共享的 API 会导致归属不清和协调困难；拆成各自归属明确的 API 更好，哪怕设计上不那么理想（又是康威定律）。

常见的消费者与提供者约束

消费者不支持某些 HTTP 方法

现在很少见了，但值得了解。某个老应用发不了 PATCH，另一些发不了 DELETE。 可以让他们自己搭一层 BFF 去转换；但如果受影响的消费者很多，通行的解法是支持 X-HTTP-Method-Override 请求头 （没有 RFC 定义，但已是事实标准，很多 HTTP 服务器都支持）： 

POST /transfers/123
X-HTTP-Method-Override: PATCH

{ "amount": { "value": 200 } }

不同的消费者习惯不同的数据格式

银行要提供一个核验账户信息的 API。大企业习惯 ISO 20022 的 XML 报文，初创公司习惯简单的 JSON。 用内容协商（第 9 章）可以同时满足两者。但要留意：如果后续的用例让 ISO 20022 反过来约束了整个设计和能力， 就得考虑为不同市场提供不同的 API，或者只支持一种格式 —— 这时应回到「定义」阶段和相关方澄清目标。

计划内的不可用

转账子系统每晚停一小时；跨行支付网络在元旦这样的日子关闭。前者也许可以通过改造系统解决，后者无法避免。两种设计：

拒绝，并告知何时恢复
POST /transfers

HTTP/1.1 503 Service Unavailable
Retry-After: Tue, 02 Jan 2024 00:00:00 GMT
Content-Type: application/problem+json

{ "title": "Transfers are unavailable
            on banking holidays", ... }
接受，稍后处理
POST /transfers

HTTP/1.1 202 Accepted
Location: /transfers/12345

{
  "id": "12345",
  "status": "DELAYED",
  "processingDate": "2024-01-02",
  ...
}

Retry-After 的值可以是 HTTP 日期，也可以是秒数（3600）。 右边的做法体验更好，但要求在接受时就完成所有必要的检查；到执行时余额不足的风险依然存在 —— 这和预约转账是同一类风险，可以接受。

数据与 URL 的兼容性

  • 特殊字符。路径参数和查询参数里的 /、? 等必须做 URL 编码。如果交易 ID 是 123/456，消费者每次用它拼路径都得记得编码，很容易出错。 最好让会进 URL 的数据（尤其是 ID）不含这类字符；改不了底层数据的话，就在 API 层把它转换成 123-456。
  • 长度。HTTP 没规定 URL 的最大长度，但各种浏览器、服务器、代理有。超过约 2000 个字符就可能出问题。 GET /transactions?id=ID1,ID2,… 一次筛 200 个 ID 就会逼近这个上限 —— 可以改用 POST /transactions/search（第 12 章），或者干脆让消费者分两次调用。

处理文件

交易分类的图标、PDF 对账单、开户时的居住证明照片……对 HTTP 来说，请求体里是 JSON 还是 PDF 没有区别，但设计上文件需要特别对待。

⚠ 上传的文件必须查毒

文件上传必须检查病毒和恶意软件。你的组织多半已经有标准化的安全上传方案；没有的话必须先定出来。无论哪种情况，都去找安全团队。

在流程中收集文件

第 10 章设计了灵活的开户流程。现在要加上证件上传，两种常见做法：

一次调用同时发送数据和文件

有时无法分步：消费者只能发一次请求，或者实现无法保存中间状态。（先质疑这个限制。）这时可以把数据和文件混在一起发，两种方式：

JSON + Base64 编码的文件
POST /account-applications
Content-Type: application/json

{
  "name": "Spike Spiegel",
  "address": { "city": "Tokyo" },
  "documents": [
    { "type": "identity",
      "content": "SGVsbG8s..." },
    { "type": "residence",
      "content": "IFdvcmxkIQ..." }
  ]
}
multipart/form-data
POST /account-applications
Content-Type: multipart/form-data; boundary="--123--boundary"

--123--boundary
Content-Type: application/json
Content-Disposition: form-data; name=data

{ "name": "Spike Spiegel", "address": { ... },
  "documents": [ { "type": "identity" },
                 { "type": "residence" } ] }
--123--boundary
Content-Type: image/png
Content-Disposition: form-data; name=documents

<二进制数据>
--123--boundary
Content-Type: application/pdf
Content-Disposition: form-data; name=documents

<二进制数据>
  • Base64 把二进制变成文本，但体积增大约 33%（HTTP 压缩能抵消一部分，对 JPG 来说最终大约多 5–10%）。
  • multipart 更标准，传的是原始二进制。每个「部分」可以有自己的媒体类型；同名的多个部分（两个 documents）被视为数组，实现再按顺序与 data.documents 里的类型信息对应。
⚠ 混合发送的缺点

数据有一个小错（比如缺了某个属性），整个请求连同所有文件都得重传；多个文件很容易撞上请求大小的上限；有些老系统处理不了 multipart 或 Base64。 它适合简单的场景，比如「一个文件 + 一点放不进 URL 或头里的元数据」—— 这种情况推荐 multipart。

响应里要不要内嵌文件

「读取账户」可以返回一个 iconUrl，也可以直接返回 Base64 编码的 icon。后者省了一次调用 —— 但那次调用本来是可以缓存的。 如果给每笔交易都内嵌分类图标，消费者会反复下载同一张图。把文件和数据分开，文件才能被单独获取、缓存、按需要的尺寸和格式（Accept 头、width/height 参数）获取。

💡 同一个路径，文件或元数据

对同一个文件资源做内容协商：带 Accept: application/json 返回文件的元数据，不带则返回文件内容本身。

用 OpenAPI 描述文件

请求体或响应体是原始文件时，只要在 content 下列出媒体类型，值留空对象即可（也可以用通配符 image/*；任意二进制用 application/octet-stream）：

paths:
  /files:
    post:
      requestBody:
        content:
          application/pdf: {}        # 接受 PDF、PNG、JPG
          image/png: {}
          image/jpeg: {}
      responses:
        "201":
          description: File uploaded   # 照常返回 Location 头和文件 ID
  /files/{fileId}:
    get:
      responses:
        "200":
          description: File content or metadata
          content:
            application/pdf: {}      # 原始文件
            image/png: {}
            image/jpeg: {}
            application/json:        # 文件的元数据
              schema:
                type: object

JSON 里内嵌的 Base64 文件，用 JSON Schema 的 contentMediaType 和 contentEncoding；multipart 请求体则用 OpenAPI 的 encoding 对象指定每个部分允许的媒体类型：

components:
  schemas:
    Account:
      properties:
        icon:
          type: string
          contentMediaType: image/png     # 字符串里装的是什么
          contentEncoding: base64         # 它是怎么编码的

paths:
  /account-applications:
    post:
      requestBody:
        content:
          multipart/form-data:
            schema:
              properties:                 # 每个根属性是一个「部分」
                data:                     # 对象或数组默认是 application/json
                  properties:
                    name:
                      type: string
                    documents:
                      type: array
                      items:
                        properties:
                          type:
                            type: string
                            enum: [identity, residence]
                documents:
                  type: array
                  items:
                    type: string
                    format: binary        # 默认是 application/octet-stream
            encoding:
              documents:                  # 覆盖默认的媒体类型
                contentType: application/pdf, image/png, image/jpeg

高效地处理文件

文件比普通数据大得多，变化却少得多，所以效率更要讲究：

目标HTTP 机制
没变就不重新下载缓存与条件请求（第 13 章）。上传成功后也不要把文件原样返回，只确认并返回 ID
断点续传、分段并行下载请求头 Range: bytes=0-10485759 → 206 Partial Content；范围无效则 416 Range Not Satisfiable
分段上传POST /files + Content-Range: 0-500/1000 → 202 Accepted + Location；再 PUT 剩余部分
避免白传一个会被拒绝的大文件在专用操作里公布允许的类型和大小；超限返回 413 Content Too Large；最后的手段是 Expect: 100-continue：先只发头部，服务端检查令牌、路径、Content-Type、Content-Length 后回 100 Continue，消费者才发送文件内容

这些功能自己实现起来可能很复杂，只在处理大文件时才值得；通常的做法是交给专门的文件存储系统。

把上传下载委托给存储系统

出于安全、性能或架构的原因，文件常常放在专门的存储系统里（比如云上的对象存储）。理想情况下实现应该对消费者隐藏这一点。 但有时做不到 —— 比如我们的 API 网关会把整个请求读完再转发，处理大文件太吃资源，平台团队禁止二进制文件经过它。 

import httpx

api = httpx.Client(base_url="https://api.bank.com", headers={"Authorization": f"Bearer {token}"})

# ① 向业务 API 要一份「上传请求的描述」
upload = api.post("/account-applications/123/documents/residence/upload-requests").json()

# ② 按描述把文件直接传到存储系统 —— 不要硬编码方法和头，用返回的
with open("proof-of-residence.pdf", "rb") as f:
    r = httpx.request(upload["method"], upload["url"], headers=upload["headers"], content=f)
r.raise_for_status()

# 下载则简单得多：跟随 303 重定向即可
pdf = api.get("/accounts/123/statements/2024-01", follow_redirects=True).content

const base = "https://api.bank.com";
const auth = { Authorization: `Bearer ${token}` };

type UploadRequest = { method: string; url: string; headers: Record<string, string> };

// ① 向业务 API 要一份「上传请求的描述」
const upload: UploadRequest = await (
  await fetch(`${base}/account-applications/123/documents/residence/upload-requests`, {
    method: "POST", headers: auth,
  })
).json();

// ② 按描述把文件直接传到存储系统 —— 不要硬编码方法和头，用返回的
const response = await fetch(upload.url, {
  method: upload.method,
  headers: upload.headers,
  body: file,                       // 浏览器里的 File，或 Node 里的 Buffer / 流
});
if (!response.ok) throw new Error(`Upload failed: ${response.status}`);

// 下载则简单得多：fetch 默认就会跟随 303 重定向
const pdf = await (await fetch(`${base}/accounts/123/statements/2024-01`, { headers: auth })).blob();

// ① 向业务 API 要一份「上传请求的描述」
UploadRequest upload = api.post()
    .uri("/account-applications/123/documents/residence/upload-requests")
    .retrieve().body(UploadRequest.class);

// ② 按描述把文件直接传到存储系统 —— 不要硬编码方法和头，用返回的
HttpRequest.Builder request = HttpRequest.newBuilder(URI.create(upload.url()))
    .method(upload.method(), HttpRequest.BodyPublishers.ofFile(Path.of("proof-of-residence.pdf")));
upload.headers().forEach(request::header);

HttpResponse<Void> response = HttpClient.newHttpClient()
    .send(request.build(), HttpResponse.BodyHandlers.discarding());
if (response.statusCode() >= 300) throw new IllegalStateException("Upload failed");

// 下载则简单得多：让客户端跟随重定向即可
HttpClient downloader = HttpClient.newBuilder().followRedirects(HttpClient.Redirect.NORMAL).build();

配合方案 B 的通用文件资源时，对应的是 POST /file-upload-requests。这样，因系统架构而产生的操作都留在文件 API 里，不会污染业务 API。

用 Webhook 通知消费者

什么是 Webhook

到目前为止都是消费者调提供者。但有时提供者需要主动联系消费者：使用银行 API 的第三方想在用户账户出现新交易时立刻知道。 交易随时可能发生（实时支付、刷卡）。让第三方每秒调一次「列出交易」？绝大多数时候什么都没有，白白压垮基础设施；调得不频繁，又会很晚才知道。

Webhook 应该是可选的

不是所有消费者都能实现 Webhook：有的只有手机 App、没有后端；有的因为基础设施或安全原因没法对外暴露接口。 所以要保证他们用普通的 API 调用也能做到同样的事（只是不实时）。这可能需要补充操作： 现有的 GET /accounts/{accountId}/transactions 得逐个账户去查，不如加一个 GET /transactions，一次取回所有可见账户里「上次之后」的新交易。

设计 Webhook 操作

和设计普通操作一样：满足需求、好用、高效、安全，用 OpenAPI 描述。区别是：Webhook 总是 POST，路径由消费者自己定。

使用标准的事件格式：CloudEvents

POST /notifications
Content-Type: application/cloudevents+json

{
  "specversion": "1.0",                          // CloudEvents 的版本
  "type": "com.banking.transaction.new",         // 事件类型（反向域名风格）
  "source": "/transactions",                     // 事件发生的上下文
  "id": "123",                                   // source + id 唯一标识一个事件
  "data": {                                      // 事件自己的数据
    "id": "123",
    "amount": 36.2
  }
}

CloudEvents 是一个与协议无关的事件格式标准，用它可以省去自己发明格式的工夫，也便于互操作。 （批量发送多个事件可以用 application/cloudevents-batch+json，请求体是数组。）

事件里放多少数据

轻事件（thin）重事件（thick）
data 的内容只有一个指针：{ "href": "/transactions/123" }可以直接使用的数据（相当于读取该资源的响应）
消费者收到后还得调一次 API通常不用再调
适合易变的数据（账户余额变化很快，发过去可能已经过时）；体积大的数据（年度对账单）小而稳定的数据（一笔交易）

CloudEvents 建议整个事件不超过 64 KB，以保证能在各种协议上传递。

安全

  • 事件里的数据同样要最小化。如果某些消费者不该看到交易的商户信息（第 12 章），发事件时也得遵守同样的规则 —— 或者改发轻事件。
  • Webhook 由消费者实现，但采用什么安全措施由提供者规定，确保只有我们能调用它。和安全专家确定方案：用共享密钥给消息签名、IP 白名单、双向 TLS、OAuth 2.0，可以组合使用。

期望的行为

我们只需要知道消费者收到了。Webhook 回任何 2XX 都行，最好在几毫秒内；不需要返回数据或 Location。

★ 实现 Webhook 的原则：收下就走

Webhook 的实现要尽量简单，才能响应快、少出错。它可以检查安全和数据格式，然后把事件放进数据库或队列 —— 不要在这里处理事件，处理交给之后的另一个环节。

import hashlib, hmac
from fastapi import FastAPI, Header, HTTPException, Request, Response

app = FastAPI()
SECRET = settings.webhook_secret.encode()          # 与提供者共享的密钥

@app.post("/notifications")
async def receive_event(request: Request, x_signature: str = Header(...)):
    raw = await request.body()

    # ① 安全：验证签名，确认消息确实来自提供者且未被篡改
    expected = hmac.new(SECRET, raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, x_signature):
        raise HTTPException(401, "Invalid signature")

    # ② 格式：只做最基本的检查
    event = await request.json()
    if event.get("specversion") != "1.0" or "type" not in event:
        raise HTTPException(400, "Not a CloudEvents 1.0 event")

    # ③ 去重：提供者可能重发；source + id 唯一标识一个事件
    key = f"{event['source']}#{event['id']}"
    if not seen_events.add_if_absent(key):
        return Response(status_code=204)           # 已经收过，直接确认

    # ④ 入队，立刻返回。真正的处理由后台消费者完成
    await queue.put(event)
    return Response(status_code=204)

import { Hono } from "hono";
import { createHmac, timingSafeEqual } from "node:crypto";

const app = new Hono();
const SECRET = process.env.WEBHOOK_SECRET!;        // 与提供者共享的密钥

type CloudEvent<T = unknown> = { specversion: string; type: string; source: string; id: string; data: T };

app.post("/notifications", async (c) => {
  const raw = await c.req.text();

  // ① 安全：验证签名，确认消息确实来自提供者且未被篡改
  const expected = createHmac("sha256", SECRET).update(raw).digest("hex");
  const received = c.req.header("X-Signature") ?? "";
  if (expected.length !== received.length ||
      !timingSafeEqual(Buffer.from(expected), Buffer.from(received))) {
    return c.json({ message: "Invalid signature" }, 401);
  }

  // ② 格式：只做最基本的检查
  const event: CloudEvent = JSON.parse(raw);
  if (event.specversion !== "1.0" || !event.type) {
    return c.json({ message: "Not a CloudEvents 1.0 event" }, 400);
  }

  // ③ 去重：提供者可能重发；source + id 唯一标识一个事件
  if (!(await seenEvents.addIfAbsent(`${event.source}#${event.id}`))) {
    return c.body(null, 204);                      // 已经收过，直接确认
  }

  // ④ 入队，立刻返回。真正的处理由后台消费者完成
  await queue.send(event);
  return c.body(null, 204);
});

@RestController
public class WebhookController {

    record CloudEvent(String specversion, String type, String source, String id, JsonNode data) {}

    @PostMapping(path = "/notifications", consumes = "application/cloudevents+json")
    public ResponseEntity<Void> receiveEvent(@RequestBody byte[] raw,
                                             @RequestHeader("X-Signature") String signature)
            throws Exception {
        // ① 安全：验证签名，确认消息确实来自提供者且未被篡改
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(webhookSecret, "HmacSHA256"));
        String expected = HexFormat.of().formatHex(mac.doFinal(raw));
        if (!MessageDigest.isEqual(expected.getBytes(), signature.getBytes())) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
        }

        // ② 格式：只做最基本的检查
        CloudEvent event = objectMapper.readValue(raw, CloudEvent.class);
        if (!"1.0".equals(event.specversion()) || event.type() == null) {
            return ResponseEntity.badRequest().build();
        }

        // ③ 去重：提供者可能重发；source + id 唯一标识一个事件
        if (!seenEvents.addIfAbsent(event.source() + "#" + event.id())) {
            return ResponseEntity.noContent().build();     // 已经收过，直接确认
        }

        // ④ 入队，立刻返回。真正的处理由后台消费者完成
        queue.send(event);
        return ResponseEntity.noContent().build();
    }
}

调用失败了怎么办

消费者的 Webhook 超时了，或者返回了非 2XX。可以提供的补救手段，由简到繁：

  1. 让消费者用普通操作自己补（GET /transactions）—— 但不同的事件要调不同的操作，消费者实现起来麻烦；
  2. 提供专门的「列出通知」操作，可以筛出未送达的；
  3. 提供按需重发（通过开发者门户或一个 API 操作），让补发的事件走和正常事件一样的通道；
  4. 自动重试，但要有上限（例如 24 小时内最多 5 次），超过后由消费者按需重发。

要不要建事件历史和重试机制、做到什么程度，和架构师一起评估。GitHub、PayPal 这些成熟 API 的 Webhook 文档很值得参考。

用 OpenAPI 描述 Webhook

openapi: "3.1.0"
info: ...
paths:                               # 普通操作
  /accounts:
    get: ...
webhooks:                            # 由消费者实现的 Webhook
  TransactionNotification:           # 不是路径，而是一个标识符（路径由消费者定）
    post:
      summary: New transaction
      description: |
        To be implemented by consumers. Events are resent up to 5 times
        over 24 hours in case of failure. Must respond in less than 200 ms.
      security:
        - WebhookMutualTLS: []
      requestBody:
        content:
          application/cloudevents+json:
            schema:
              $ref: "#/components/schemas/TransactionEvent"
      responses:
        "2XX":                       # OpenAPI 支持状态码通配符
          description: Event successfully sent
components:
  securitySchemes:
    WebhookMutualTLS:
      type: mutualTLS

webhooks 是 OpenAPI 3.1 才有的。除了键是标识符而不是路径，其余和普通操作的写法完全一样。用 description 写明调用方的行为（重试策略）和对实现的期望（响应时间）。

耗时很长的操作

有些操作要几分钟甚至几小时：在一段两小时的视频里找小猫，或者银行的市场压力测试模拟（最长一小时）。 技术上可以让消费者一直等着，但应该避免：连接数和基础设施会吃紧；连接一旦因超时中断，消费者得从头再来，之前的计算全白费。

发起 + 轮询

关键是给消费者足够的信息来优化轮询：进度百分比、进度速率、预计结束时间。也可以在 GET 的成功响应里带上 Retry-After（不常见，但在这里很合理）。 

import time
import httpx

api = httpx.Client(base_url="https://api.bank.com")

# ① 发起：立刻得到 202 和状态资源的地址
started = api.post("/simulations", json={"scenario": "market-crash"})
assert started.status_code == 202
status_url = started.headers["Location"]           # /simulations/12345

# ② 轮询：听服务端的话，别自己猜间隔
while True:
    r = api.get(status_url)
    simulation = r.json()
    if simulation["status"] != "IN_PROGRESS":
        break
    print(f"进度 {simulation['progressPercentage']}%")
    time.sleep(int(r.headers.get("Retry-After", 30)))   # 服务端建议多久后再来

print("结果：", simulation["status"])

const base = "https://api.bank.com";
const sleep = (seconds: number) => new Promise((r) => setTimeout(r, seconds * 1000));

type Simulation = { id: string; status: "IN_PROGRESS" | "DONE" | "FAILED"; progressPercentage?: number };

// ① 发起：立刻得到 202 和状态资源的地址
const started = await fetch(`${base}/simulations`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ scenario: "market-crash" }),
});
if (started.status !== 202) throw new Error(`Unexpected status ${started.status}`);
const statusUrl = base + started.headers.get("Location");   // /simulations/12345

// ② 轮询：听服务端的话，别自己猜间隔
let simulation: Simulation;
while (true) {
  const response = await fetch(statusUrl);
  simulation = await response.json();
  if (simulation.status !== "IN_PROGRESS") break;
  console.log(`进度 ${simulation.progressPercentage}%`);
  await sleep(Number(response.headers.get("Retry-After") ?? 30));   // 服务端建议多久后再来
}

console.log("结果：", simulation.status);

record Simulation(String id, String status, Double progressPercentage) {}

// ① 发起：立刻得到 202 和状态资源的地址
ResponseEntity<Simulation> started = api.post().uri("/simulations")
    .body(Map.of("scenario", "market-crash"))
    .retrieve().toEntity(Simulation.class);
if (started.getStatusCode() != HttpStatus.ACCEPTED) throw new IllegalStateException();
URI statusUri = started.getHeaders().getLocation();          // /simulations/12345

// ② 轮询：听服务端的话，别自己猜间隔
Simulation simulation;
while (true) {
    ResponseEntity<Simulation> response = api.get().uri(statusUri).retrieve().toEntity(Simulation.class);
    simulation = response.getBody();
    if (!"IN_PROGRESS".equals(simulation.status())) break;
    System.out.printf("进度 %.1f%%%n", simulation.progressPercentage());

    String retryAfter = response.getHeaders().getFirst(HttpHeaders.RETRY_AFTER);
    Thread.sleep(Duration.ofSeconds(retryAfter != null ? Long.parseLong(retryAfter) : 30));
}

System.out.println("结果：" + simulation.status());

用回调代替轮询

也可以在操作结束时主动通知消费者。这叫回调（callback），和 Webhook 是同一种东西 —— 由提供者定义、由消费者实现的反向 API。本教程这样区分两个词：

触发原因例子
Webhook提供者一侧发生的事件刷卡产生了一笔新交易
回调消费者之前发起的动作有了结果消费者启动的模拟跑完了

设计上没有区别，所以保持一致：同样的 CloudEvents 格式、同样的安全配置、同样在开发者门户上登记的 URL。 事件类型是 com.banking.simulation.end；因为模拟结果数据量巨大，用轻事件，只带一个指向模拟资源的引用。

在 OpenAPI 里，回调可以像 Webhook 一样写在 webhooks 下；但更明确的做法是写在发起它的那个操作的 callbacks 里：

paths:
  /simulations:
    post:
      summary: Run market stress simulation
      responses:
        "202":
          description: Simulation started
      callbacks:                         # 与 responses 同级
        SimulationEnd:                   # 回调的标识符
          "{webhookUrl}":                # 回调的 URL：可以是固定的，也可以含运行时变量
            post:
              summary: Simulation has ended
              security:
                - WebhookMutualTLS: []
              requestBody:
                content:
                  application/cloudevents+json:
                    schema:
                      $ref: "#/components/schemas/SimulationEndEvent"
              responses:
                "2XX":
                  description: Event successfully sent

回调的 URL 可以引用请求或响应里的数据。如果让消费者在发起时通过查询参数指定（POST /simulations?callback=https://…），这里就写 {$request.query.callback}。 我们选择所有 Webhook 和回调共用开发者门户上登记的地址，所以用了一个自定义变量 {webhookUrl}。

💡 常见的语法错误

编辑器报错时，检查两点：callbacks 是否和 responses 同级；回调是否先有标识符、再有 URL 两层（很容易漏掉其中一层）。

让消费者选择执行方式

对能力非常有限的消费者，可以用 Prefer 头（第 13 章）让他们选择同步执行：Prefer: response=synchronous 会一直等到模拟结束才返回 201 Created； 不带或 response=asynchronous 则立即返回 202。同步执行并不高效，慎用，并用行为调节型作用域（如 simulation:run:synchronous）只开放给选定的消费者。

考虑 REST 以外的 API 类型

🔨 工具定律

「手里只有锤子，看什么都像钉子。」对熟悉工具的过度依赖是一种认知偏差。API 类型和方案里的其他部分一样，应该根据需求和上下文来选。作为设计者，了解这些替代方案能帮你及时发现问题、提醒架构师。

类型擅长什么例子注意
事件驱动架构（EDA） 内部系统之间发送事件：提供者往消息通道发布，消费者订阅 交易系统发布「新交易」事件。对外的 Webhook 背后可以就是它 Webhook 适合跨互联网；内部用 EDA 更合适
Server-Sent Events（SSE） 服务端通过 HTTP 向客户端单向流式推送文本 模拟的实时进度、实时行情、AI 回复的流式输出 只需一次普通的 HTTP 调用，常与 REST 搭配；但长连接耗资源
WebSocket 双向实时通信，文本和二进制都行 户主与银行顾问聊天 大量连接耗资源；防火墙和代理可能拦截
GraphQL 聚合多个 API 的数据；精确选择要取的字段；有订阅机制 为前端做的 BFF（第 13 章） 缓存、防止过于复杂的查询、安全都有挑战。不需要它的独特功能时，设计良好的 REST + HTTP/2 就够了
gRPC 充分利用 HTTP/2（含双向流）；Protobuf 二进制格式更紧凑、序列化更快 微服务之间大量的内部通信 浏览器不支持

什么时候选

通常进入设计阶段时，团队已经有一套默认的技术栈和 API 类型。但需求分析可能揭示出与默认选择不相容的要求：

默认是 REST，遇到这些时考虑别的
  • 需要向消费者流式推送数据 → SSE
  • 需要双向通信 → WebSocket
  • 需要向内部系统发送事件 → EDA
  • 要做 BFF，且确实需要其独特功能 → GraphQL
默认不是 REST，遇到这些时考虑 REST
  • 设计公开或合作伙伴 API（绝大多数是 REST）
  • 私有 API 将来可能对外开放
  • API 要被浏览器调用
  • 需要跨互联网的「提供者 → 消费者」通信（HTTP Webhook / 回调）

本章小结

  • 先质疑约束，确认它无法解决，再调整设计。
  • 用 X-HTTP-Method-Override 请求头让消费者调用他们发不出的方法。
  • 格式差异不影响流程时，用内容协商提供多种格式；否则考虑分成不同的 API，或只支持一种。
  • 计划内不可用：返回 503 和 Retry-After，或者接受请求稍后处理并返回 202 Accepted。
  • 确保数据（尤其是 ID）能安全地放进 URL，且 URL 不超过约 2000 个字符。
  • 流程中上传文件：用通用的文件资源（POST /files）再关联到业务资源，或直接挂在业务资源下。
  • 可以用 Base64 或 multipart 混合文件和数据，但要注意效率。
  • OpenAPI 中：原始文件只需在 content 下列出媒体类型；Base64 文件用 contentMediaType 和 contentEncoding；multipart 用 encoding 对象。
  • 文件要启用缓存；创建或上传时不回传文件。大文件可支持分段下载（Range）、分段上传（Content-Range）和上传预检（Expect: 100-continue）—— 最好依托文件管理系统。
  • 从第三方系统下载：用 303 See Other 重定向到安全的 URL。上传：返回安全 URL、HTTP 方法和头。
  • 定义由消费者实现的 Webhook 来通知提供者一侧的事件，避免低效的轮询；但要让消费者不靠 Webhook 也能取到数据。
  • 用 CloudEvents 标准设计事件。易变或庞大的数据用轻事件，小而稳定的数据用重事件。
  • 考虑提供事件重发或历史事件查询，以应对失败。
  • Webhook 写在 OpenAPI 的 webhooks 下；长操作的回调写在该操作的 callbacks 下。
  • 长操作：返回 202，提供进度信息或 Retry-After 来优化轮询；或用回调通知结束。
  • 需要流式数据、双向通信、内部事件、高度定制的 BFF 时，考虑 REST 以外的 API 类型。

动手练习

  1. 「木材即服务」公司提供按尺寸定制的木板，想用 API 实现自动下单。但订单需要人工审核，所以只能在工作时间处理。怎么调整设计？
    参考答案 先质疑：人工审核真的必要吗？能否只对异常订单做？如果确实无法避免： ① 下单是一个长操作（有人参与）：POST /orders 返回 202 Accepted，订单状态为 PENDING_VALIDATION，并给出预计审核时间；消费者通过 GET /orders/{id} 轮询，或通过回调/Webhook 得知审核结果。 ② 非工作时间：与其返回 503，不如照常接受订单排队（202 + 预计处理时间）—— 对消费者友好得多。
  2. 快递公司的 API 因为消费者反复调用 GET /shipments 和 GET /shipments/{shipmentId} 查物流状态而过载。怎么办？
    参考答案 提供 Webhook（如 com.vfs.shipment.status-changed 事件）在状态变化时主动通知，消除轮询的理由。 对无法实现 Webhook 的消费者：启用缓存与条件请求（ETag/304）、在响应里给出预计的下次更新时间、提供「某时间点之后有变化的运单」筛选； 并配合限流和限流信息头。
  3. 音乐分析 API 只有一个操作：请求体里是 Base64 编码的音视频文件和一组处理任务（测速、识别和弦、生成伴奏……），每个任务对每分钟音频要处理 1 秒到 1 分钟；响应一次性返回所有结果，其中可能包含 Base64 编码的文件。用户常常分几轮对同一个文件做不同的处理。有哪些问题？
    参考答案 ① 大文件用 Base64 塞在 JSON 里：体积膨胀、任务参数写错一点就得重传；而且每轮处理都要重传同一个文件 → 先 POST /files（或两步上传）得到 fileId，之后的处理请求只引用它。 ② 处理可能长达数分钟乃至更久，却是同步调用 → POST /processing-tasks 返回 202，提供进度与轮询，或用回调通知完成。 ③ 结果里内嵌 Base64 文件 → 返回生成文件的 ID/URL，按需单独下载（可缓存、可断点续传）。 ④ 一个操作里混着性质不同的任务和结果 → 每个任务成为独立的资源，各有自己的状态和结果。
