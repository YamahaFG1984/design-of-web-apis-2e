第 8 章

好用、可互操作的数据

第一部分我们设计出了一个「做对的事」的 API。从这一章开始进入第二层：让它好用（容易理解、用起来顺手） 而且可互操作（不同系统之间不用费劲转换就能对接）。先从最小的单位 —— 数据 —— 开始。

本章目标

  • 理解 API 的用户体验，以及「好用」「可互操作」各指什么
  • 选择并加工出「拿来即用」的数据
  • 为原子数据选择合适的类型和格式（数字、代码、日期时间）
  • 用对象和数组把数据组织好，并控制好粒度
  • 起出简单、有层次、简短的名字
  • 在整个 API 乃至所有 API 之间保持一致，尽量采用标准

API 也有用户体验

想象一台洗衣机，启动后屏幕显示 EC 50400。翻说明书才知道：这是「洗涤结束时间，从零点起算的秒数」。 知道了还得心算。直接显示「14:35 洗完」不好吗？ 这台洗衣机满足了需求（洗衣服、告诉你什么时候洗完），但不好用。

再想象洗衣机面板上的那些洗涤图标（一个水盆下面两条线 = 轻柔洗）。它们未必一眼能懂，但全世界的衣物标签都用同一套（ISO 3758 标准）—— 这就是互操作性：衣服标签和任何一台洗衣机都能对上。

谁的体验

API 的用户体验（UX）常被叫作开发者体验（DX），因为主要用户是写代码调用它的开发者。 但用户不止他们：在电子表格里调 API 的业务分析师、用 API 客户端做测试的 QA、浏览开发者门户做选型的架构师、越来越多的 AI 应用， 以及隔着一层应用间接感受 API 的最终用户。

对公开 API，体验差的后果是用户掉头就走。对私有 API，后果更隐蔽也更糟：你没法换，只能日复一日地忍受它带来的复杂代码和不稳定。

好用、可互操作的数据有什么特征

无论数据出现在哪里 —— 路径、参数、请求头、请求体、成功响应还是错误响应 —— 都适用下面几条。以一个租车 API 为例：

特征反例改进
满足用户需求用内部黑话「业务区域引用」来称呼门店位置叫「门店位置」。从外向内看自己的数据
容易找到和理解"la": 12 和 "lo": 34 散落在一堆属性中间一个 location 对象，里面是 latitude 和 longitude
减少消费者的工作只给经纬度，消费者得自己做逆地理编码直接附上现成的 address
一致门店位置是十进制度数的对象，车辆位置却是 "place": ["34° 0' 0", "12° 0' 0"]所有位置都用相似的名字、同样的结构和单位
标准（互操作）自创的坐标表示法考虑采用 GeoJSON（RFC 7946）的 Geometry 对象
ⓘ 标准不一定好用

GeoJSON 的点长这样：{"type": "Point", "coordinates": [12, 34]}。数组里哪个是经度哪个是纬度？很多人永远记不住。 标准有时会为了通用或效率牺牲易用性，采用前要掂量。

什么时候做、怎么做

好用性是对数据建模的第二遍处理。第一遍（第 5 章）建模时不要争论 longitude 还是 lng、要不要用 GeoJSON —— 识别出「需要坐标」就够了。 第二遍按下面的顺序过一遍。本章接下来换一个例子：银行 API 里的「银行账户」资源。

选择并加工出拿来即用的数据

目标：消费者拿到数据后不用思考、不用加工就能直接使用（或者能直接提供）。

1. 选简单但够用的数据

银行系统里一个账户有好几种余额（计算方式不同）。全给出来最通用，但消费者得自己判断该用哪个； 只给银行 App 里最常显示的那一个最简单，但限制了可能性。怎么选要看目标用户： 面向非专业人士就给一个；面向银行业专家就全给。折中方案：全给，但标出默认的那个。

2. 加辅助数据，消除猜测

余额是 123。123 什么？欧元？并非所有欧洲国家都用欧元，就算用，也可能开了外币账户。 把币种和金额放在一起，解读就既容易又准确。

3. 加处理过的数据，替消费者省事

需求之一是「帮用户评估还能花多少钱」。第一遍建模时我们给了余额和透支额度信息（是否启用、额度多少）。 但这要求消费者自己写逻辑：如果透支启用，就把额度加到余额上。是加还是减？有没有已知但未入账的交易要考虑？ 直接给一个 可安全支出金额（safe to spend），消费者就什么都不用算了。 

account = httpx.get(f"{base}/accounts/{iban}").json()

# ✗ 之前：消费者要实现银行的业务规则，而且很容易算错
#   {"balance": 1700, "overdraftActive": true, "overdraftLimit": 100}
safe_to_spend = account["balance"]
if account["overdraftActive"]:
    safe_to_spend += account["overdraftLimit"]     # 是加还是减？未入账交易算了吗？
print(f"可用：{safe_to_spend}")                     # 币种是什么？只能猜

# ✓ 之后：加工好的数据 + 辅助数据，拿来即用
#   {"safeToSpend": {"amount": 1800, "currency": "EUR"}}
sts = account["safeToSpend"]
print(f"可用：{sts['amount']} {sts['currency']}")

const account = await (await fetch(`${base}/accounts/${iban}`)).json();

// ✗ 之前：消费者要实现银行的业务规则，而且很容易算错
//   {"balance": 1700, "overdraftActive": true, "overdraftLimit": 100}

if (account.overdraftActive) {
  safeToSpend += account.overdraftLimit;           // 是加还是减？未入账交易算了吗？
}
console.log(`可用：${safeToSpend}`);                // 币种是什么？只能猜

// ✓ 之后：加工好的数据 + 辅助数据，拿来即用
//   {"safeToSpend": {"amount": 1800, "currency": "EUR"}}
const { amount, currency } = account.safeToSpend;
console.log(new Intl.NumberFormat("zh-CN", { style: "currency", currency }).format(amount));

// ✗ 之前：消费者要实现银行的业务规则，而且很容易算错
record OldAccount(BigDecimal balance, boolean overdraftActive, BigDecimal overdraftLimit) {}

OldAccount old = api.get().uri("/accounts/{iban}", iban).retrieve().body(OldAccount.class);
BigDecimal safeToSpend = old.balance();
if (old.overdraftActive()) {
    safeToSpend = safeToSpend.add(old.overdraftLimit());   // 是加还是减？未入账交易算了吗？
}
System.out.println("可用：" + safeToSpend);                 // 币种是什么？只能猜

// ✓ 之后：加工好的数据 + 辅助数据，拿来即用
record Amount(BigDecimal amount, String currency) {}
record Account(String iban, Amount safeToSpend) {}

Account account = api.get().uri("/accounts/{iban}", iban).retrieve().body(Account.class);
System.out.printf("可用：%s %s%n", account.safeToSpend().amount(), account.safeToSpend().currency());
★ 这也是在隐藏提供者视角

辅助数据和加工数据让消费者不必实现我们的业务规则，也就不会因为不了解内情或数据不全而出错。加了 safeToSpend 之后，可以重新审视余额和透支信息是否还有必要保留。

5. 其他数据也尽量用众所周知或标准的

行内系统用 EU、UD 表示欧元和美元，内部人人都懂。但对外应使用国际通行的 ISO 4217 货币代码：EUR、USD。 没有标准可用也不要紧，系统间共享的约定也能实现互操作；实在不行，只在本地通用也可以接受。

原子数据的类型与格式

布尔值只要名字起得好，天然就好用。字符串和数字则容易出问题：

数据不好的写法问题好的写法
余额"€1,234.5"把可计算的数字格式化成了字符串1234.5 + 单独的币种
账号1234567是数字形式的编码，丢了前导零"0001234567"
账户类型1 或 "xbt"人看不懂的代码"checking"
创建日期409228260人读不出来的时间戳"1982-12-20"

数字要不要格式化成字符串

  • 会被用来计算的数字，不要格式化。"€1,234.5" 看似省事，可消费者想计算时得先解析它； 而且格式因地而异 —— 法国的界面应该显示 1 234,5 €。怎么给人看由消费者按用户的区域设置决定，API 只给原始数字和币种。
  • 数字形式的编号或代码，适合格式化成字符串。账号 1234567 要补齐前导零到固定长度才是合法账号，这个长度连行业老手都记不住，所以直接给 "0001234567"。

避免人读不懂的代码

1、7、"xbt"、"tvp" 没有字典就无法解读；c、s 这类缩写也只有内行能猜到。 用完整的英文单词："checking"、"savings" —— 也就是你写代码时会放进枚举里的那种值。

如果代码已经被多个系统使用、改不了，就在旁边加一个人能读的标签： "type": 7, "typeLabel": "savings"，或者做成一个带 code 和 label 的对象。

日期和时间：用 ISO 8601

API 里表示时间通常有两种方式。强烈推荐后者：

Unix 时间戳（数字）ISO 8601（字符串）
示例4092282601982-12-20T10:31:00Z
人能读吗✗ 看日志时无法判断是哪天✓
只表示日期✗ 分不清它是日期还是日期时间✓ 1982-12-20
单位✗ 秒？毫秒？1704067200 按秒是 2024 年，按毫秒是 1970 年 1 月✓ 无歧义
时区只能是 UTCZ 表示 UTC；也可带偏移 +01:00
手工构造测试数据✗ 很难✓ 改个数字就行
💡 默认用 UTC

UTC 不受夏令时影响（切换那天凌晨 1:30 可能出现两次）。只有在确实需要时（比如审计或监管要求记录交易的当地时间）才使用带偏移的时间。只需要日期就别带时间，省得处理时区。

各语言处理 ISO 8601 都是一行的事：

from datetime import date, datetime, timezone

executed = datetime.fromisoformat("1982-12-20T10:31:00+00:00")   # 3.11+ 也接受结尾的 Z
created = date.fromisoformat("1982-12-20")

print(executed.year, executed.tzinfo)        # 1982 UTC
print(datetime.now(timezone.utc).isoformat(timespec="seconds"))
# 2025-03-01T14:35:00+00:00

# 对比：时间戳得先知道单位，否则差出 1000 倍
print(datetime.fromtimestamp(409228260, timezone.utc))            # 按秒 → 1982-12-20
print(datetime.fromtimestamp(409228260 / 1000, timezone.utc))     # 按毫秒 → 1970-01-05

const executed = new Date("1982-12-20T10:31:00Z");

console.log(executed.getUTCFullYear());      // 1982
console.log(new Date().toISOString());       // 2025-03-01T14:35:00.000Z
console.log(new Date().toISOString().slice(0, 10));   // 只要日期：2025-03-01

// 对比：时间戳得先知道单位。JavaScript 的 Date 用毫秒，Unix 时间用秒
console.log(new Date(409228260 * 1000).toISOString());  // 按秒 → 1982-12-20T10:31:00.000Z
console.log(new Date(409228260).toISOString());         // 当成毫秒 → 1970-01-05T17:40:28.260Z

组织数据

如果游戏手柄的方向键随机散落在各处，你肯定用不顺手。数据也一样。对比同一份账户数据的两种形态：

扁平、杂乱

分组、分层、排序

  "type": "checking",

    "limit": { "amount": 100, "currency": "EUR" }

用对象分组

左边的 overdraft facility 和 limit 是一回事，但谁看得出来？ 可以改名为 overdraft facility limit（靠名字关联），再把两者挪到一起（靠位置关联）， 但最好的办法是放进一个 overdraft facility 对象：里面是 active 和 limit。 业务概念一目了然，代码里也能当作一个整体来处理。

更通用的概念也值得成组：每一个金额都变成带 amount 和 currency 的对象。 这样每个值都能独立理解，而且同一种结构在各处复用，更有利于互操作。

用数组分组

两种余额原本各占几个属性，还有一个 default balance 指向默认的那个。 既然它们都是余额，就放进 balances 数组，每项带 type；默认标记变成其中一项上的布尔值。

💡 经验法则

看到 conceptThis、conceptThat 这样共享前缀的属性 → 考虑对象。看到 value1、value2……valueN → 用数组（比如把地址的 line1–line4 换成 lines 数组）。

排序

  • 数组里的顺序对处理和展示有实际意义。JSON Schema 没法正式描述排序，就写在 description 里：「按余额类型排序：先 value-date 后 expected」。
  • 对象的属性顺序不影响代码，但影响人阅读数据和文档：相关的放一起，重要的放前面。
⚠ 别过度组织

每个子对象都应该代表一个业务概念，最好还能复用。不要为了分组而分组，更不要照着 UI 的版块来分组。

数据的粒度与范围

看相关性，不看大小

模型有 20 个属性还是 100 个、3 层深还是 10 层深，本身都不是问题。问题是每一个元素有没有存在的理由。 iban、number、type、name 是表示一个银行账户所必需的；safe to spend 是满足需求所必需的； 而领域专家认为 creation date 对操作账户毫无帮助 —— 删掉它，模型更简单，干扰更少。

内嵌列表

内嵌别的资源：给多少

账户需要关联「户主」和「透支服务」这两个独立资源。可以给一个 ID、一份摘要，或者完整的模型（第 5 章的典型模型）。判断方法：

★ 消费者读了这个资源之后，是不是每次都得接着去读那个内嵌资源？

是 → 它们是一个整体，至少内嵌摘要（需要更多就给完整模型）。例：银行顾问处理账户时总要看户主姓名，只给户主 ID 就得多调 N 次。
否 → 它们只是有关联，给一个 ID 就够。例：有了 safe to spend，处理账户时并不需要透支服务的细节。
一串光秃秃的 ID 列表往往毫无意义：要么至少给摘要，要么考虑去掉这个列表。

起个好名字

什么时候起名

要分清两件事：识别出正确的概念（第一遍设计）和设计好用的名字（现在）。 第一遍时直接叫它「overdraft facility active」就够了。名字受类型、格式和上下文影响： 它可能后来变成了字符串枚举（active / suspended / ended），可能被放进了对象里所以叫 active 就行，甚至可能根本没被保留。 所以起名是最后一步。

三条原则

  • 简单：用人人都懂的词，避免黑话 —— 但不要为了简单牺牲含义。
  • 有层次：用大小写分隔单词（camelCase 或 snake_case）；多个词按「父/宽泛 → 子/具体」从左到右排。
  • 简短：争取不超过三个词（同样不能牺牲含义）。上下文已经说明的前缀、表示类型的后缀、不影响理解的词，都可以去掉。避免缩写，除非是广为人知的。

修一个烂名字

ⓘ camelCase 还是 snake_case？

Java 和 JavaScript 习惯 overdraftFacility，Python 习惯 overdraft_facility。消费者很容易适配，按你的偏好选，但选了就全程一致。

一致与标准化

好用和互操作的共同基础是一致。它难在无处不在：选哪些数据、怎么组织、什么类型和格式、叫什么名字、用什么标准 —— 之前做过的每一个决定，都会成为之后设计的先例。第一个日期叫 whateverDate 并用了 ISO 8601，以后所有日期最好都照此办理。

在尽可能大的范围内寻求一致

动手建模前先找一找：团队或组织里是否已有「银行账户」模型？行业里有没有标准（银行业的 ISO 20022）？ 能复用就复用，不能直接用就借鉴其中的模式。

⚠ 采用现成模型前要确认两件事

它真的满足你的需求吗？可互操作却不满足需求是不可接受的。它的复杂度可以接受吗？标准往往不是为非专业用户设计的。

标识符：用同一个、按同一种方式命名

如果账户模型用 IBAN 标识账户，转账的付款方却用内部 ID、收款方用账号，那就既不一致也难对接。全部用 IBAN，才既一致又可互操作。

标识符的命名模式也要定下来，让人一眼认出「哪个是本资源的 ID、哪些是指向别的资源的 ID」：

不一致：哪个才是资源标识符？
// 账户
{ "accountId": "...", "iban": "...", "ownerRef": "..." }

// 户主
{ "ownerId": "..." }
一致：本资源叫 id，别处叫 资源名Id
// 账户
{ "id": "...", "iban": "...", "ownerId": "..." }

// 户主
{ "id": "..." }

这个约定意味着：资源自己的标识符永远叫 id，在其他地方引用它时叫 资源名Id。 如果标识符同时是有业务含义的重要数据（IBAN），它可以在资源里出现两次：既是 id，也是 iban。

命名、类型、结构都要一致

转账模型与账户模型不一致
// 账户
{ "balance": { "value": 123.45, "currency": "EUR" },
  "created": "2024-02-01",
  "number": "00012345" }

// 转账
{ "amount": 12,
  "currency": "EUR",
  "executionDate": 1707215025,
  "accountNumber": "12345" }
一致
// 账户
{ "balance": { "value": 123.45, "currency": "EUR" },
  "created": "2024-02-01",
  "number": "00012345" }

// 转账
{ "amount": { "value": 12, "currency": "EUR" },
  "executed": "2024-02-06T10:23:45Z",
  "accountNumber": "00012345" }

左边有四处不一致：金额的结构、日期的类型（时间戳 vs ISO 8601）、日期的命名模式（created vs executionDate）、账号的格式（有无前导零）。

在代码里，一致性的最好载体是可复用的类型。定义一次 Amount，所有出现金额的地方都用它，想不一致都难：

from datetime import date, datetime
from decimal import Decimal
from typing import Literal
from pydantic import BaseModel, Field

class Amount(BaseModel):
    """所有金额都用这个结构：数值 + ISO 4217 货币代码"""
    value: Decimal
    currency: str = Field(pattern=r"^[A-Z]{3}$", examples=["EUR"])

class BankAccount(BaseModel):
    id: str                                   # 本资源的标识符永远叫 id（值是 IBAN）
    iban: str
    number: str = Field(pattern=r"^\d{11}$")  # 字符串，保留前导零
    type: Literal["checking", "savings"]      # 人能读的代码
    balance: Amount
    safeToSpend: Amount
    created: date                             # 只需要日期 → ISO 8601 日期

class MoneyTransfer(BaseModel):
    id: str
    sourceAccountId: str                      # 引用别的资源：资源名 + Id，同样用 IBAN
    destinationAccountId: str
    amount: Amount                            # 与 balance 同一种结构
    executed: datetime                        # 需要时间 → ISO 8601 日期时间（UTC）

💡 把决定沉淀下来

每做一个决定就创造了一个先例。把它们记录成团队的设计指南（第 16 章），并在 OpenAPI 里定义成可复用的 schema（第 17 章），以后就不用靠记忆来保持一致。

本章小结

  • 除了满足需求，用户还期望 API 好用：容易理解、用起来愉快。设计可以吸引用户，也可以赶走用户。
  • 不论数据出现在哪里，都应简单、清晰、有帮助、直观、可互操作。
  • 好用性放在第二遍处理：先确认数据满足需求，再打磨。
  • 让数据拿来即用：选简单而有效的数据，补充辅助数据和加工后的数据，使用众所周知或标准的数据和标识符。
  • 会参与计算的数字不要格式化成字符串；数字形式的编号或代码可以。
  • 避免人读不懂的代码；避不开就加一个可读的标签。
  • 日期时间用 ISO 8601；只在必要时才带时间精度，以免处理时区。
  • 用对象归拢同一概念的属性，用数组归拢同类元素；给数组排序以便处理，给对象属性排序以便查找。
  • 不要纠结属性数量和层级深度，要追问每个元素是否相关。
  • 内嵌其他资源时，按需选择 ID、摘要或完整模型；不要内嵌需要搜索和分页的大数组。
  • 起名放在定好类型、格式和组织之后：用简单的词、用大小写分词、按层次排列、去掉父级前缀/类型后缀/多余的词，尽量不超过三个词。
  • 先看有没有标准或现成的模型可用；在尽可能大的范围内保持一致，同时权衡复杂度并确保满足需求。

动手练习

  1. 机票比价 API 返回的航班数据如下。如何让它更好用、更可互操作？ 
    {
  "flight": {
    "number": "AF1234",
    "departureAirport": 12345,
    "departureTime": 1733063400,
    "arrivalAirport": 67890,
    "endTime": 1733073000
  },
  "class": 56,
  "price": { "base": 150, "taxes": "50.00", "discount": 0.1 }
}
    参考答案 ① 机场用内部数字 ID → 换成标准的 IATA 代码（"CDG"），并附上名称和城市。 ② 时间戳 → ISO 8601（航班时刻对旅客来说是当地时间，这里适合带时区偏移）。 ③ departureTime 与 endTime 命名不一致 → arrivalTime；还可以把出发和到达各自归成对象 departure: {airport, time}、arrival: {…}。 ④ "class": 56 是看不懂的代码 → "economy"。 ⑤ 价格：taxes 是字符串而其他是数字，类型不一致；缺币种；消费者得自己算总价 → 加上 total 和 currency；discount: 0.1 含义不明（比例？金额？）。 ⑥ 加上处理过的数据，如飞行时长（"PT2H40M"）。
  2. 音频流媒体的「艺人」完整模型包含 id、name、bio、genres、albums（列表）、tracks（列表）。有该去掉的吗？
    参考答案 tracks 应去掉：一位艺人可能有成百上千首曲目，需要筛选和分页，应通过独立的操作获取。 albums 也类似，数量可能不少；可以去掉，或只保留少量有明确含义的子集（比如「最新专辑」）。genres 很短，保留。
  3. 图书馆 API 的「图书」数据：{"bookReference":"B12345","title":"The Eternal Champion","authorCode":"A123","name":"Michael Moorcock","published_year":1970,"authDob":"1939-12-18"}。列出命名和组织上的问题并修正。
    参考答案 问题：大小写风格混用（published_year）；name 是谁的名字不明确；authDob 是缩写；作者的三个属性散落各处；标识符命名不成模式。修正后： 
    {
  "id": "B12345",
  "title": "The Eternal Champion",
  "publishedYear": 1970,
  "author": {
    "id": "A123",
    "name": "Michael Moorcock",
    "birthDate": "1939-12-18"
  }
}
