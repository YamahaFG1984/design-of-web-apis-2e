第 11 章

好用、可互操作的 API

数据、操作、操作流都打磨过了，最后退到最远处看整个 API。 设想一家公司的信息系统被分成二十几块，每块暴露一个就叫「API」的 API，里面有几百个操作 —— 没有人（也没有 AI）能在里面找到自己要的东西，连作者自己都不行。 这一章讨论三件事：该做一个还是多个 API、怎么给它起名、要不要让它像网站一样可以「浏览」。

本章目标

  • 会通过识别相互独立的操作集合，判断该拆成几个 API
  • 会给 API 起一个说明其用途的名字，并把它放进基础路径
  • 了解用 OPTIONS 方法、Link 头和超媒体格式实现运行时发现
  • 知道什么时候值得（以及不值得）做超媒体 API

API 层面的好用

除了使用好用的零件，一个好用、可互操作的 API 还要：

  • 有清晰、聚焦的目的。它不试图满足所有可能的需求，所以不会让开发者不知所措。
  • 有一个有意义的名字。
  • （可选）帮助消费者在运行时发现可用的操作和资源之间的关系。

一个 API 还是多个

租车公司的信息系统涵盖财务、人事、云基础设施和租车业务。把所有操作塞进一个叫「API」的内部 API，开发者会被淹没。 按领域拆成四个？可能还不够细：「租车 API」听起来清楚，实际上包含了租赁管理、客户管理、车队管理几个子领域，每个都可以是目的更明确的独立 API。

ⓘ 这也是架构问题

如何把信息系统划分成块，本身是一门学问，通常由架构师或技术负责人主导。作为 API 设计者，我们会在较小的尺度上遇到这个问题 —— 本节从 API 设计的角度给出一些方法，但请和你的架构师一起决定。安全（第 12 章）和组织/系统约束（第 14 章）也会影响拆分。

什么时候讨论

在优化完数据、操作和流程之后。因为优化过程中会冒出新的资源和操作，过早划分依据的是不完整的信息。 如果拿不准，可以先放在一个 API 里，等领域看得更清楚了再拆。代价很小：消费者改一下调用的配置或代码（第 15 章）。

💡 API 是接口，不是应用

一个应用完全可以对外暴露多个 API。拆 API 不等于拆服务。

识别相互独立的操作集合

把所有操作画出来，按第 10 章优化后的操作流把它们连起来，再结合领域专家的知识，独立的集合就会显现。以银行 API 为例：

子 API 之间可以有联系

回想第 10 章优化转账流程之前：我们用「列出账户」来获取付款方。那时很容易觉得账户信息和转账都「和账户有关」，应该放在一起。 优化之后，转账有了自己的「列出付款方」。账户信息里的账户和转账里的付款方是两个不同的资源，但指向同一个业务概念，并共享一个可互操作的标识符 —— IBAN。

于是两个 API 既独立又能配合：消费者可以只用转账 API 完成转账，也可以拿着从账户信息 API（或别的任何地方）得到的 IBAN 来转账。IBAN 从哪来并不重要。

📚 两个可以借力的东西
  • 限界上下文（Bounded Context）：领域驱动设计（DDD）里的概念，把一个大的领域模型拆成若干相互独立、但可以共享某些概念的小模型。和这里做的事是一回事。
  • 现成的业务模型：你的架构师可能已经把业务划分好了；行业里也有标准模型（保险业的 ACORD、银行业的 BIAN、零售业的 ARTS）。可以直接参考 —— 不过这类企业级模型准确归准确，未必好用，也未必适合公开 API。

用名字说清 API 的目的

名字划定了 API 的边界，也是潜在用户了解它的第一个线索。和数据的名字一样，API 的名字在设计过程中可以变： 一开始取自需求，等粒度讨论清楚后再定稿。

名字类型评价
「API」「Web Service」泛泛的✗ 没说它做什么，也没法和别的 API 区分
「新银行架构」项目或内部背景✗ 说的是「为什么建它」而不是「它做什么」。项目会结束，API 还在；而且它不会永远「新」
「粉红毛绒独角兽」没有含义✗ 通常不行（公开 API 的品牌名另当别论）
「在线转账」有含义，但带了场景⚠ 「在线」会限制人们对它的想象 —— 批处理程序也能用它
「银行」领域⚠ 如果它其实只提供账户信息，这个名字就太大了
「账户」「转账」「开户申请」领域 / 业务概念 / 用例✓ 朴素、简单、名副其实

起名的技巧沿用第 8 章：简单、有层次、简短。

把名字放进基础路径

银行 API 拆成三个之后，路径变成 /account/accounts、/transfer/beneficiaries/{beneficiaryId}、/account-application/partial-account-applications。 第一段就是 API 的名字。在 OpenAPI 里，这个前缀不写进 paths，而是通过 servers 定义： 

openapi: 3.1.0
info:
  title: Account          # API 的名字
  version: "1.0"
servers:
  - url: /account         # 基础路径：是 paths 下所有路径的前缀
paths:
  /accounts:              # 实际路径是 /account/accounts
    get:
      summary: List accounts

让 API 可以被「浏览」

浏览网站时，我们从不需要猜 URL 或猜能做什么。银行网站上一笔转账的页面里，有指向付款账户的超链接；如果这笔转账还能取消，页面上就有一个「取消」按钮。 API 也能提供类似的能力，让消费者在运行时发现「接下来能做什么」和「相关的东西在哪」，而不是靠文档和猜测。

ⓘ 超媒体 API、REST 与 HATEOAS

超媒体 API（hypermedia API）指消费者可以借助超媒体元数据和对 HTTP 的通用理解，动态地与 API 交互。 它在 Roy Fielding 定义 REST 的论文里被称为「超媒体作为应用状态的引擎」（Hypermedia As The Engine Of Application State），常被缩写成那个念不出来的词：HATEOAS。 它属于 REST 的「统一接口」约束 —— 但现实中很少有 API 真的这么做。值得了解，因为在某些场合它确实有用。

用 OPTIONS 列出资源上可用的操作

一笔转账（/transfers/{transferId}）可以被读取、修改、取消。但取决于它的状态，后两者不一定可行。 OPTIONS 方法让消费者不必取回资源，就能知道当前有哪些方法可用 —— 答案在 Allow 响应头里： 

OPTIONS /transfers/54321 HTTP/1.1

HTTP/1.1 200 OK
Allow: GET, DELETE

这笔转账可以读、可以取消，但不能修改（没有 PUT）。

用 Link 头提供各种链接

Link 响应头（RFC 8288，Web Linking）是一个逗号分隔的链接列表。每个链接由尖括号里的 URL、rel（与当前资源的关系）和可选的 type（目标的媒体类型）组成。 

GET /accounts/12345/transactions HTTP/1.1

HTTP/1.1 200 OK
Link: </accounts/12345/transactions>;rel="alternate";type="text/csv",
      </accounts/12345/transactions>;rel="alternate";type="application/pdf",
      </accounts/12345/transactions?page=2>;rel="next"


GET /transfers/54321 HTTP/1.1

HTTP/1.1 200 OK
Link: </accounts/11111>;rel="source",
      </beneficiaries/22222>;rel="destination"
rel含义
alternate同一个资源的另一种表示（配合 type 说明格式）
next / prev分页：下一页 / 上一页
source、destination……任何有业务含义的关系

超媒体数据格式

也可以把链接放进响应体。要有效果，就必须用标准格式 —— 最流行的是 HAL，此外还有 JSON:API、Siren、JSON-LD。对比同一笔转账的三种表示：

这些格式各有自己的媒体类型。借助第 9 章的内容协商，可以同时提供普通 JSON 和超媒体格式： 消费者想要 HAL 就发 Accept: application/hal+json，不发就得到普通 JSON。

实现与使用

服务端：同一个转账资源，支持 OPTIONS、Link 头，以及通过内容协商返回 HAL。

from fastapi import FastAPI, Header, HTTPException, Response
from fastapi.responses import JSONResponse

app = FastAPI()

def allowed_methods(transfer: dict) -> list[str]:
    methods = ["GET", "OPTIONS"]
    if transfer["status"] == "pending":          # 只有待执行的转账才能改、能取消
        methods += ["PUT", "DELETE"]
    return methods

@app.options("/transfers/{transfer_id}")
def transfer_options(transfer_id: str):
    transfer = store.get(transfer_id) or _not_found()
    return Response(status_code=200, headers={"Allow": ", ".join(allowed_methods(transfer))})

@app.get("/transfers/{transfer_id}")
def read_transfer(transfer_id: str, accept: str = Header("application/json")):
    transfer = store.get(transfer_id) or _not_found()

    data = {
        "id": transfer["id"],
        "source": transfer["source"],            # 关键业务数据始终在正文里
        "destination": transfer["destination"],
        "amount": transfer["amount"],
        "cancellable": "DELETE" in allowed_methods(transfer),   # 不要只藏在元数据里
    }
    links = {
        "self": f"/transfers/{transfer['id']}",
        "source": f"/accounts/{transfer['source']}",
        "destination": f"/beneficiaries/{transfer['destination']}",
    }
    link_header = ", ".join(f'<{href}>;rel="{rel}"' for rel, href in links.items() if rel != "self")

    if "application/hal+json" in accept:         # 内容协商：要 HAL 就给 HAL
        data["_links"] = {rel: {"href": href} for rel, href in links.items()}
        return JSONResponse(data, media_type="application/hal+json", headers={"Link": link_header})

    return JSONResponse(data, headers={"Link": link_header})    # 默认：普通 JSON

import { Hono } from "hono";

const app = new Hono();

type Transfer = { id: string; source: string; destination: string; amount: number; status: string };

function allowedMethods(transfer: Transfer): string[] {
  const methods = ["GET", "OPTIONS"];
  if (transfer.status === "pending") methods.push("PUT", "DELETE");   // 只有待执行的才能改、能取消
  return methods;
}

app.options("/transfers/:id", (c) => {
  const transfer = store.get(c.req.param("id"));
  if (!transfer) return c.json({ message: "Transfer not found" }, 404);
  return c.body(null, 200, { Allow: allowedMethods(transfer).join(", ") });
});

app.get("/transfers/:id", (c) => {
  const transfer = store.get(c.req.param("id"));
  if (!transfer) return c.json({ message: "Transfer not found" }, 404);

  const data = {
    id: transfer.id,
    source: transfer.source,                     // 关键业务数据始终在正文里
    destination: transfer.destination,
    amount: transfer.amount,
    cancellable: allowedMethods(transfer).includes("DELETE"),         // 不要只藏在元数据里
  };
  const links: Record<string, string> = {
    self: `/transfers/${transfer.id}`,
    source: `/accounts/${transfer.source}`,
    destination: `/beneficiaries/${transfer.destination}`,
  };
  c.header("Link", Object.entries(links)
    .filter(([rel]) => rel !== "self")
    .map(([rel, href]) => `<${href}>;rel="${rel}"`).join(", "));

  if (c.req.header("Accept")?.includes("application/hal+json")) {     // 内容协商：要 HAL 就给 HAL
    const _links = Object.fromEntries(Object.entries(links).map(([rel, href]) => [rel, { href }]));
    c.header("Content-Type", "application/hal+json");
    return c.body(JSON.stringify({ ...data, _links }));
  }
  return c.json(data);                           // 默认：普通 JSON
});

// 依赖：spring-boot-starter-hateoas（原生支持 HAL）
@RestController
@RequestMapping("/transfers/{id}")
public class TransferController {

    record TransferData(String id, String source, String destination, BigDecimal amount,
                        boolean cancellable) {}       // cancellable：关键信息不要只藏在元数据里

    private Set<HttpMethod> allowedMethods(Transfer transfer) {
        Set<HttpMethod> methods = new LinkedHashSet<>(List.of(HttpMethod.GET, HttpMethod.OPTIONS));
        if (transfer.isPending()) {                   // 只有待执行的转账才能改、能取消
            methods.addAll(List.of(HttpMethod.PUT, HttpMethod.DELETE));
        }
        return methods;
    }

    @RequestMapping(method = RequestMethod.OPTIONS)
    public ResponseEntity<Void> options(@PathVariable String id) {
        return ResponseEntity.ok().allow(allowedMethods(store.find(id)).toArray(HttpMethod[]::new)).build();
    }

    // 默认：普通 JSON
    @GetMapping(produces = MediaType.APPLICATION_JSON_VALUE)
    public TransferData read(@PathVariable String id) {
        Transfer t = store.find(id);
        return new TransferData(t.id(), t.source(), t.destination(), t.amount(),
                                allowedMethods(t).contains(HttpMethod.DELETE));
    }

    // 内容协商：Accept: application/hal+json 时走这个方法，Spring HATEOAS 负责生成 _links
    @GetMapping(produces = MediaTypes.HAL_JSON_VALUE)
    public EntityModel<TransferData> readAsHal(@PathVariable String id) {
        Transfer t = store.find(id);
        return EntityModel.of(read(id),
            Link.of("/transfers/" + t.id()).withSelfRel(),
            Link.of("/accounts/" + t.source()).withRel("source"),
            Link.of("/beneficiaries/" + t.destination()).withRel("destination"));
    }
}

客户端：不拼路径，而是跟着链接走；不猜能不能取消，而是先问。

import httpx
api = httpx.Client(base_url="https://api.bank.com/transfer")

# 1. 要 HAL 格式
transfer = api.get("/transfers/54321", headers={"Accept": "application/hal+json"}).json()

# 2. 跟着链接去取付款账户 —— 不需要知道路径怎么拼
source = api.get(transfer["_links"]["source"]["href"]).json()

# 3. 运行时询问：现在能取消吗？
allow = api.options(transfer["_links"]["self"]["href"]).headers["Allow"]
if "DELETE" in allow:
    api.delete(transfer["_links"]["self"]["href"])

# httpx 还能直接解析 Link 响应头（分页很方便）
page = api.get("/transfers")
while page is not None:
    handle(page.json())
    next_link = page.links.get("next")            # 解析自 Link: <…>;rel="next"
    page = api.get(next_link["url"]) if next_link else None

const base = "https://api.bank.com/transfer";

type HalLinks = { _links: Record<string, { href: string }> };
type Transfer = { id: string; source: string; amount: number; cancellable: boolean } & HalLinks;

// 1. 要 HAL 格式
const transfer: Transfer = await (
  await fetch(`${base}/transfers/54321`, { headers: { Accept: "application/hal+json" } })
).json();

// 2. 跟着链接去取付款账户 —— 不需要知道路径怎么拼
const source = await (await fetch(base + transfer._links.source.href)).json();

// 3. 运行时询问：现在能取消吗？
const options = await fetch(base + transfer._links.self.href, { method: "OPTIONS" });
if (options.headers.get("Allow")?.includes("DELETE")) {
  await fetch(base + transfer._links.self.href, { method: "DELETE" });
}

// 解析 Link 响应头里的 rel="next"（分页）
function nextUrl(response: Response): string | undefined {
  const match = response.headers.get("Link")?.match(/<([^>]+)>\s*;\s*rel="next"/);
  return match?.[1];
}

关键业务数据不能只藏在元数据里

注意上面服务端代码里的 cancellable 和 source。即使有了 OPTIONS、Link 和 _links， API 也必须在忽略这些浏览功能的情况下照样可用：

信息可以放在元数据里也必须在普通数据里吗
这笔转账能否取消Allow 头、Siren 的 actions是 —— 关键信息，加一个 cancellable 标志
付款账户是哪个HAL 的 _links.source是 —— source 标识符是消费者和用户都需要的基本数据
交易列表还支持 CSV、PDFLink 头的 alternate否 —— 把它塞进 JSON 正文，等于自创了一种没人会用的超媒体格式

要不要做

超媒体写在 REST 的基因里，功能也强大，但它从未流行起来。和任何技术一样：真正需要时才用。

值得考虑的场合
  • 开发者明确想用这些能力
  • 有动态的、通用的客户端（配合支持超媒体格式的库，很快就能搭出一个通用的消费端）
  • 有 AI 代理在调用：它可以依据运行时返回的数据决定下一步，而不是靠猜
  • 预期 API 会拆分或调整路径：消费者用的是返回的链接而不是自己拼的路径，改动对他们透明
不必费心的场合
  • 以上都不成立
  • 你或消费者的技术栈里没有合适的客户端/服务端库

拿不准也没关系：浏览能力可以以后通过内容协商加上，不影响现有消费者。

💡 一致性本身就是一种可发现性

正确使用 HTTP、保持数据、操作和流程的一致与标准，消费者（包括 AI）就已经能「猜」出大部分东西了。超媒体是锦上添花，一致性才是地基。

本章小结

  • 好用、可互操作的 API 使用好用的数据、操作和流程，并且目的清晰、聚焦；还可以帮助消费者在运行时发现可用的操作和关系。
  • 单个 API 也许能满足需求，但可能难以理解。优化完流程后，评估需要一个还是多个 API。
  • 通过识别相互独立的操作集合及其关联来决定如何拆分。子领域之间不总是泾渭分明，它们可以通过可互操作的标识符相联系。
  • API 的名字划定边界、说明用途。聚焦于领域、业务概念或用例；避免泛泛的、与项目或背景相关的、没有含义的名字。
  • 可以把 API 名字放进基础路径（OpenAPI 的 servers）。
  • 用 OPTIONS 方法让消费者不必取回资源就知道哪些方法可用。
  • 用 Link 头在 GET 响应中提供分页、格式和资源链接。
  • 用标准的超媒体格式（如 HAL、Siren）提供可互操作的导航元数据，并通过内容协商与普通 JSON 并存。
  • 关键的业务数据不能只存在于超媒体元数据里。
  • 只在真正需要时才提供浏览能力 —— 典型场景是有动态的或 AI 驱动的消费端。

动手练习

  1. 一所大学识别出了这些操作：课程的搜索/创建/读取/更新/取消；学生选课、退课、查看选课名单；设置和列出考试；学生的增改删查；录入成绩、查询成绩；员工请假的新增/修改/查询；列出员工。它们适合放在一个 API 里吗？
    参考答案 不适合。按流程连接后至少有两个完全不相干的集合：教务和人事（员工、请假）—— 后者和教学没有任何流程上的联系，应独立成一个 API。 教务部分还可以再看：课程管理（课程 CRUD）、学生管理（学生 CRUD）、选课（选课/退课/名单）、考试与成绩。它们通过可互操作的 courseId、studentId 相关联，可以拆成几个 API，也可以先合为一个「教务 API」，等规模变大再拆。 顺带一提，原设计里「列出员工请假」写成了 POST，应为 GET。
  2. PAX 公司发起了重建内部系统的「ReGenesis」计划，刚重构完的「Zeus」应用可以：计算订单运费、生成运单、发货、追踪物流。给它的私有 API 起名，评估「Zeus API」「Logistics API」「ReGenesis Shipment API」。
    参考答案 Zeus API：应用的内部代号，没有含义，外人不知道它做什么。 ReGenesis Shipment API：带了项目名，项目结束后名字就过时了；不过 Shipment 部分是对的。 Logistics API：有含义，但范围太大 —— 物流还包括仓储、库存、退货等，而它只管发货。 更好的名字：Shipment API（或 Order Shipment API），准确描述了它提供的能力。
  3. 挑一个你用过的公开 API，看看它的响应头里有没有 Link（GitHub 的列表接口就有）。用本章的客户端代码把所有页面翻一遍。
