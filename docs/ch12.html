第 12 章

设计安全的 API

从这一章起进入第三层：约束。前面设计出的 API 做对了事，也好用，但如果不安全，一切归零。 安全不能留到最后交给安全专家「补上」—— 购物网站的用户打开浏览器开发者工具，就能在商品接口的响应里看到进货价； 改一下 URL 里的订单号，就能看到别人的订单。这些都是设计阶段就该堵住的洞。

本章目标

  • 理解一次 API 调用中安全发生在哪三个层面，以及设计能预防哪些问题
  • 只暴露必要的数据和操作（最小化 API 表面）
  • 让操作的行为取决于「谁在调用」，并把这些规则写进 OpenAPI
  • 保证数据完整性：幂等、防重放、条件更新
  • 避免协议和架构层面的泄露：URL 里不放敏感数据
  • 用作用域（scope）划分访问权限，并在 OpenAPI 里描述
  • 安全地报错：401、403、404、500 各在什么时候用

API 安全概览

任何 API 都要保护，包括不对互联网开放的内部 API：网络一旦被攻破，内部 API 就暴露无遗； 安全措施不足还可能导致有人把生产环境的 API 当成开发环境的来调，直接弄坏系统。

什么时候、怎么做

安全贯穿设计的每一步，但为了讨论高效，在 API 做对了事、也打磨得好用之后集中审视一遍，这时面对的是完整的设计。 之后每次修改都要从安全角度再看。设计对安全的贡献归纳为四点：

  1. 不暴露提供者视角（第 2 章）—— 聚焦用户需求本身就是安全的支柱；
  2. 最小化 API 表面；
  3. 保证数据完整性；
  4. 让实现者拿到所需的全部信息 —— 很多安全漏洞的根源，就是设计时没说清楚、实现时只能猜。

只暴露必要的数据和操作

什么是敏感数据和敏感操作

敏感数据一旦泄露，会给组织或相关个人带来安全威胁或损失。敏感操作则是操纵敏感数据、或触及关键业务/技术流程的操作。以银行 API 为例：

  • 银行卡号和有效期：泄露即可能被盗刷；
  • 户主的姓名、电话、地址：这类个人身份信息（PII）可能被用于诈骗和身份盗用，并且受 GDPR 等法规约束；
  • 各项银行服务的内部成本：商业机密；
  • 「审批异常转账」：只有特定的银行员工才能执行。
⚠ 你不能自己判断什么是敏感的

去问首席信息安全官（CISO）、数据保护官（DPO）、法务或其他有资质的专家。组织里往往已经有敏感数据清单，设计之前先拿到它。把一份完整的 OpenAPI 文档交给安全方面的同事审阅也很有帮助。

四种手段

① 质疑它是否该存在

遇到敏感的数据或操作，第一反应应该是：它真的需要在这里吗？账户数据里要带银行卡列表吗？「审批异常转账」要暴露在互联网上吗？ 不敏感的也要问 —— 最安全的数据是不存在的数据。如果没有任何用例需要「读取户主资料」，这个操作就不该出现。

② 修改数据，降低敏感度

③ 拆分操作，分离关注点

如果「审批异常转账」是通过「更新转账」把状态改掉来完成的，那么一个操作里就混了敏感动作（审批）和不敏感动作（改执行日期、改金额）。 拆出独立的「审批异常转账」操作：关注点分开了，敏感动作更显眼，访问控制也更简单。

④ 把敏感操作放进专门的 API

更进一步：把「审批异常转账」移到独立的转账管理 API，从根本上降低把它错误授权给普通消费者的风险。 但新 API 必须自成一体（第 11 章）—— 审批之前得先能列出待审批的转账。回到能力画布，找出审批用例需要的所有操作。 两个 API 可能有同名但略有不同的操作：管理版的「列出转账」会多返回发起人的身份、IP、设备信息，而且不需要「列出付款方和收款方」。

让操作的行为取决于上下文

表面最小化了，泄露仍然可能发生在运行时：Alice 不该能访问 Bob 的账户 —— 除非 Alice 是负责 Bob 的银行顾问。 路径、方法和数据模型本身表达不出这类规则。如果不明确写出来，实现者只能猜。

把「谁能看什么、做什么」写进 OpenAPI

GET /accounts 返回账户列表。哪些账户？不说清楚的话，实现很可能返回所有账户。 对做全局财务核查的内部应用这也许没问题，对手机银行 App 则是灾难性的数据泄露。

💡 description 支持 Markdown

OpenAPI 里所有的 description 都支持 Markdown。| 是 YAML 的多行文本写法。充分利用操作、响应、属性三个层面的描述，把安全规则写全。

同样的规则适用于所有操作的所有输入：

  • GET /accounts/{accountId}：只返回给拥有它的户主，或负责该户主的顾问；
  • POST /transfers 请求体里的付款账户：如果调用者是户主，要检查他确实拥有这个账户；如果是顾问，要检查账户属于他负责的客户；
  • 角色和权限：有些顾问可以办理超过 10 万美元的对外转账，有些不行 —— 写在操作的描述里；
  • 属性级的差异：户主能看到交易的商户地址，顾问不能 —— 在 merchant 属性的描述里写「仅返回给户主」。
⚠ 不透明不等于安全

即使标识符是无法猜测的 UUID（ff0d991d-6fcf-4349-…），这些检查也必须做。 输入数据永远要和令牌里的安全上下文核对 —— 后者是实现唯一可以信任的输入。

用设计收窄访问范围

顾问替某位客户办转账时，「列出付款方」如果返回他负责的所有客户的账户，就很容易选错人。 把客户 ID 放进路径：GET /owners/{ownerId}/sources，只返回这一位客户的。 户主自己用的 App 则可以用一个魔法标识符 me：GET /owners/me/sources。 这算不上强安全措施，但能减少代价高昂的失误。

实现：按安全上下文过滤和检查

from dataclasses import dataclass
from fastapi import Depends, FastAPI, HTTPException

app = FastAPI()

@dataclass
class SecurityContext:            # 由令牌解析而来 —— 唯一可以信任的输入
    user_id: str
    profile: str                  # "owner" | "advisor"
    scopes: set[str]

def require(*accepted: str):
    """作用域检查（通常在 API 网关上做，这里为演示写在实现里）"""
    def check(ctx: SecurityContext = Depends(current_context)) -> SecurityContext:
        if not ctx.scopes & set(accepted):
            raise HTTPException(403, f"Missing {' or '.join(accepted)} scope")
        return ctx
    return check

@app.get("/accounts")
def list_accounts(ctx: SecurityContext = Depends(require("account:read", "account:all"))):
    if ctx.profile == "owner":
        return accounts.owned_by(ctx.user_id)             # 户主：只有自己的
    return accounts.of_owners_managed_by(ctx.user_id)     # 顾问：只有自己负责的客户的

@app.get("/accounts/{account_id}")
def read_account(account_id: str,
                 ctx: SecurityContext = Depends(require("account:read", "account:all"))):
    account = accounts.find(account_id)
    if account is None:
        raise HTTPException(404, f"Account {account_id} doesn't exist")

    if ctx.profile == "owner" and ctx.user_id not in account.owner_ids:
        # 户主无法通过申请权限来解决 → 404，不透露账户存在
        raise HTTPException(404, f"Account {account_id} doesn't exist")

    if ctx.profile == "advisor" and not advisors.manages(ctx.user_id, account):
        # 顾问可以去申请权限 → 403
        raise HTTPException(403, f"Missing permission to access account {account_id}")

    return account

import { Hono } from "hono";
import { createMiddleware } from "hono/factory";

// 由令牌解析而来 —— 唯一可以信任的输入
type SecurityContext = { userId: string; profile: "owner" | "advisor"; scopes: string[] };
const app = new Hono<{ Variables: { ctx: SecurityContext } }>();

/** 作用域检查（通常在 API 网关上做，这里为演示写在实现里） */
const requireScope = (...accepted: string[]) =>
  createMiddleware<{ Variables: { ctx: SecurityContext } }>(async (c, next) => {
    if (!c.get("ctx").scopes.some((s) => accepted.includes(s))) {
      return c.json({ message: `Missing ${accepted.join(" or ")} scope` }, 403);
    }
    await next();
  });

const canRead = requireScope("account:read", "account:all");

app.get("/accounts", canRead, async (c) => {
  const ctx = c.get("ctx");
  return c.json(
    ctx.profile === "owner"
      ? await accounts.ownedBy(ctx.userId)                 // 户主：只有自己的
      : await accounts.ofOwnersManagedBy(ctx.userId),      // 顾问：只有自己负责的客户的
  );
});

app.get("/accounts/:accountId", canRead, async (c) => {
  const ctx = c.get("ctx");
  const accountId = c.req.param("accountId");
  const account = await accounts.find(accountId);
  const notFound = () => c.json({ message: `Account ${accountId} doesn't exist` }, 404);

  if (!account) return notFound();

  if (ctx.profile === "owner" && !account.ownerIds.includes(ctx.userId)) {
    return notFound();        // 户主无法通过申请权限来解决 → 404，不透露账户存在
  }
  if (ctx.profile === "advisor" && !(await advisors.manages(ctx.userId, account))) {
    return c.json({ message: `Missing permission to access account ${accountId}` }, 403);  // 可申请权限 → 403
  }
  return c.json(account);
});

@RestController
@RequestMapping("/accounts")
public class AccountController {

    // 作用域检查（通常在 API 网关上做；这里用 Spring Security 的注解演示）
    @GetMapping
    @PreAuthorize("hasAnyAuthority('SCOPE_account:read', 'SCOPE_account:all')")
    public List<Account> listAccounts(@AuthenticationPrincipal BankUser user) {
        // user 来自令牌 —— 唯一可以信任的输入
        return user.isOwner()
            ? accounts.ownedBy(user.id())                  // 户主：只有自己的
            : accounts.ofOwnersManagedBy(user.id());       // 顾问：只有自己负责的客户的
    }

    @GetMapping("/{accountId}")
    @PreAuthorize("hasAnyAuthority('SCOPE_account:read', 'SCOPE_account:all')")
    public Account readAccount(@PathVariable String accountId,
                               @AuthenticationPrincipal BankUser user) {
        Account account = accounts.find(accountId)
            .orElseThrow(() -> notFound(accountId));

        if (user.isOwner() && !account.ownerIds().contains(user.id())) {
            throw notFound(accountId);   // 户主无法通过申请权限来解决 → 404，不透露账户存在
        }
        if (user.isAdvisor() && !advisors.manages(user.id(), account)) {
            throw new ResponseStatusException(HttpStatus.FORBIDDEN,      // 可申请权限 → 403
                "Missing permission to access account " + accountId);
        }
        return account;
    }

    private ResponseStatusException notFound(String accountId) {
        return new ResponseStatusException(HttpStatus.NOT_FOUND,
            "Account " + accountId + " doesn't exist");
    }
}

保证数据完整性

消费者和用户都只做了被允许的事，数据仍然可能被弄坏。两种常见情形：

  • 请求重放。转账请求发出后没收到响应（网络抖动、500）。服务端可能其实已经处理了；消费者重试一次，钱就转了两次。
  • 基于过期数据的更新。见下图。

安全与幂等

方法安全
不改变服务端状态		幂等
重复执行，服务端状态相同		能放心重试吗
GET✓✓可以
DELETE✗✓可以：第一次删掉了，之后可能返回 404，但服务端状态不再变化
PUT✗✓幂等，但不保证完整性 —— 数据可能已被别人改过（见上图）
POST✗✗不行：重放 POST /transfers 会转好几次钱
PATCH✗✗不行

前提是实现确实遵守了这些语义。这也是第 4 章说「方法描述的是接口，但实现必须符合其特性」的原因。

防止请求重放：幂等键

让消费者为每个请求生成一个唯一标识符（通常是 UUID），放在请求头里。IETF 的一份草案建议叫 Idempotency-Key。 服务端发现同一个键已经处理过，就不再重复执行，返回 409 Conflict。这样消费者就可以放心地自动重试。

还可以加业务层面的检查：手机 App 的用户看到报错后手动重试，每次都是新的幂等键。 如果服务端在一分钟内收到金额、付款方、收款方完全相同的转账，也返回 409； 用户确实想再转一笔的话，带上 Confirm-Duplicate: true 请求头强制执行。

条件更新：ETag 与 If-Match

HTTP 有一套标准的条件请求机制：「仅当条件成立时才执行这个请求」。用它来保证更新是基于最新数据的：

要让所有更新都安全，可以在 OpenAPI 里把所有 PUT/PATCH 的 If-Match 请求头标为 required。这是典型的应该写进团队设计指南的规则（第 16 章）。

import hashlib, json
from fastapi import FastAPI, Header, HTTPException, Response

app = FastAPI()

def etag_of(resource: dict) -> str:
    digest = hashlib.sha256(json.dumps(resource, sort_keys=True).encode()).hexdigest()
    return f'"{digest[:16]}"'

@app.get("/owners/{owner_id}")
def read_owner(owner_id: str, response: Response):
    owner = owners.get(owner_id)
    response.headers["ETag"] = etag_of(owner)          # 返回数据的「版本」
    return owner

@app.put("/owners/{owner_id}")
def update_owner(owner_id: str, body: dict, response: Response,
                 if_match: str = Header(...)):          # 必填：没有 If-Match 就不让更新
    current = owners.get(owner_id)
    if if_match != etag_of(current):                    # 读取之后数据被别人改过了
        raise HTTPException(412, "The owner has been modified since you read it; "
                                 "read it again and retry")
    updated = owners.replace(owner_id, body)
    response.headers["ETag"] = etag_of(updated)
    return updated


@app.post("/transfers", status_code=201)
def create_transfer(body: dict, idempotency_key: str = Header(...)):
    # 同一个键只处理一次：消费者可以放心地自动重试
    if idempotency.seen(idempotency_key):
        raise HTTPException(409, "A request with this Idempotency-Key has already been processed")
    idempotency.remember(idempotency_key)
    return transfers.create(body)

import { Hono } from "hono";
import { createHash } from "node:crypto";

const app = new Hono();

const etagOf = (resource: unknown) =>
  `"${createHash("sha256").update(JSON.stringify(resource)).digest("hex").slice(0, 16)}"`;

app.get("/owners/:ownerId", (c) => {
  const owner = owners.get(c.req.param("ownerId"));
  c.header("ETag", etagOf(owner));                      // 返回数据的「版本」
  return c.json(owner);
});

app.put("/owners/:ownerId", async (c) => {
  const ifMatch = c.req.header("If-Match");
  if (!ifMatch) {                                       // 必填：没有 If-Match 就不让更新
    return c.json({ message: "If-Match header is required" }, 428);   // 428 Precondition Required
  }
  const ownerId = c.req.param("ownerId");
  if (ifMatch !== etagOf(owners.get(ownerId))) {        // 读取之后数据被别人改过了
    return c.json(
      { message: "The owner has been modified since you read it; read it again and retry" }, 412);
  }
  const updated = owners.replace(ownerId, await c.req.json());
  c.header("ETag", etagOf(updated));
  return c.json(updated);
});

app.post("/transfers", async (c) => {
  const key = c.req.header("Idempotency-Key");
  if (!key) return c.json({ message: "Idempotency-Key header is required" }, 400);
  // 同一个键只处理一次：消费者可以放心地自动重试
  if (idempotency.seen(key)) {
    return c.json({ message: "A request with this Idempotency-Key has already been processed" }, 409);
  }
  idempotency.remember(key);
  return c.json(transfers.create(await c.req.json()), 201);
});

@RestController
public class OwnerController {

    private String etagOf(Owner owner) {
        return "\"" + Integer.toHexString(owner.hashCode()) + "\"";   // 也可以用版本号或修改时间
    }

    @GetMapping("/owners/{ownerId}")
    public ResponseEntity<Owner> readOwner(@PathVariable String ownerId) {
        Owner owner = owners.get(ownerId);
        return ResponseEntity.ok().eTag(etagOf(owner)).body(owner);   // 返回数据的「版本」
    }

    @PutMapping("/owners/{ownerId}")
    public ResponseEntity<Owner> updateOwner(
            @PathVariable String ownerId,
            @RequestHeader("If-Match") String ifMatch,                // 必填：没有就不让更新
            @RequestBody OwnerReplacement body) {
        if (!ifMatch.equals(etagOf(owners.get(ownerId)))) {           // 读取之后数据被别人改过了
            throw new ResponseStatusException(HttpStatus.PRECONDITION_FAILED,
                "The owner has been modified since you read it; read it again and retry");
        }
        Owner updated = owners.replace(ownerId, body);
        return ResponseEntity.ok().eTag(etagOf(updated)).body(updated);
    }

    @PostMapping("/transfers")
    public ResponseEntity<Transfer> createTransfer(
            @RequestHeader("Idempotency-Key") String idempotencyKey,
            @RequestBody TransferCreation body) {
        // 同一个键只处理一次：消费者可以放心地自动重试
        if (!idempotency.rememberIfAbsent(idempotencyKey)) {
            throw new ResponseStatusException(HttpStatus.CONFLICT,
                "A request with this Idempotency-Key has already been processed");
        }
        Transfer created = transfers.create(body);
        return ResponseEntity.created(URI.create("/transfers/" + created.id())).body(created);
    }
}

避免协议与架构层面的泄露

HTTPS 保护了什么，没保护什么

由此得出三条规则：

  1. URL 里永远不放敏感数据（路径参数和查询参数都不行）；
  2. 必要时加密数据，让任何中间节点都读不了；
  3. 必要时签名数据，让任何中间节点都改不了。

敏感的搜索条件：POST /resources/search

合作方需要按姓名搜索户主。GET /holders?name=Bob 会让姓名进入所有日志。通行的解决办法是把搜索条件挪进请求体： 

POST /holders/search HTTP/1.1
Content-Type: application/json

{ "name": "Bob" }

为什么不是 POST /holders？它已经被「创建户主」占用了。/search 是一个动作资源（第 4 章说过它是合法的）， 于是路径模式变成了「资源列表 + 可选的标识符或动作资源」。

敏感的资源标识符

第 8 章建议用可互操作的标识符。但如果它本身是敏感的呢？所有系统都认识社会保障号，可它绝不能出现在 GET /holders/{socialSecurityNumber} 这样的 URL 里。 折中办法：路径里用我们内部的 holderId（至少在内部可互操作）；同时提供 POST /holders/search 让外部用社保号查出 holderId，之后的所有操作都用它。

加密与签名

安全专家可能认为 HTTPS 还不够，要求对请求或响应数据加密（只有授权方能读）或签名（确认来源、防止篡改，但数据仍可读）。作为设计者，要向他们问清三件事，并写进文档：

  • 加密/签名的是全部数据，还是只有敏感的部分？
  • 是否因消费者而异？
  • 消费者如何获取或提供加解密、签名所需的材料？

用作用域限制消费者的访问

表面已经最小化，但一个被授权使用这个 API 的应用仍然能调用它的全部操作。 按照最小权限原则，应该只给它需要的那部分。作用域（scope）就是用来划分这个「部分」的。 （它主要与 OAuth 和 OpenID Connect 相关，类似于其他安全框架里的角色或属性。）

作用域 vs 用户权限

为什么作用域的设计很重要

  • 没有作用域：用户授权 SpendAdvize 使用银行 API 后，它就能调用包括「转账」在内的所有操作。
  • 粒度不当：如果只有一个涵盖所有写操作的 write，那么 SpendAdvize 为了把交易标记成「已核对」而申请 write 时，顺带也拿到了转账的权限。
  • 名字和描述看不懂：作用域不只是给提供者配置用的。消费方的开发者要挑选它，最终用户在第三方应用的授权页面上要读它（「MyBk App 想要：转账」）并决定是否同意。

六种设计思路

思路例子优点缺点
按操作transfer:list、transfer:create最精确数量多，配置繁琐，让用户眼花缭乱
按资源/概念transfer:all → /transfers 和 /transfers/{id} 上的所有操作简单易懂可能凑不成一个完整的用例（缺「列出付款方」）；可能混入敏感度不同的操作
按用例money_transfer → 完成转账所需的全部操作对消费者最实用
按读/写account:read、account:write把会改数据的操作隔离出来全局的 read/write 太粗
按用户/消费者owner:all、owner:transfer:write贴合「谁需要什么」太宽的话看不出到底授予了什么
行为调节transaction:sensitive_data同一个操作，有它才返回商户名称和地址由实现处理，改起来比改网关配置麻烦

这些思路可以在同一个 API 里混用、组合，同一个操作也可以被多个作用域覆盖。组合后自然形成一个命名模式： 

{用户或消费者 | 通配}:{资源或用例 | 通配}:{动作 | 通配}

owner:transfer:write        户主可用的、转账相关的写操作（不含「审批异常转账」）
owner:account:read          户主可用的、账户相关的读操作
third_party_server_application:account_application:all
💡 怎么选

细粒度的最精确，但会让配置变得复杂。往粗了合并时要警惕两件事：别把敏感度不同的操作并进同一个作用域；别造出庞大而含糊、第三方和用户都看不明白的作用域。 限制访问的作用域通常只是网关上的配置，调整起来容易；调节行为的作用域要改实现。上线后再改作用域会影响已有的消费者（第 15 章）。

在 OpenAPI 里描述作用域

先在 components.securitySchemes 里定义，再在每个操作的 security 里使用：

components:
  securitySchemes:
    OperationBased:                  # 安全方案的名字，自己起
      type: oauth2                   # 类型和流程请问安全专家；暂时不知道可以先这么写
      flows:
        implicit:
          authorizationUrl: "https://auth.bankingcompany.com/authorize"   # 不知道就先填个假的
          scopes:                    # 注意：是对象，不是列表
            "beneficiary:create": Add a beneficiary       # 作用域名: 描述
            "beneficiary:list": List beneficiaries
            "transfer:create": Transfer money
    ResourceOrUseCaseBased:          # 可以定义多个安全方案来给作用域分组
      type: oauth2
      flows:
        implicit:
          authorizationUrl: "https://auth.bankingcompany.com/authorize"
          scopes:
            "beneficiary:all": Create, list, read, modify, and delete beneficiaries
            "transfer:all": All operations needed to perform and manage transfers

paths:
  /beneficiaries:
    post:
      summary: Add a beneficiary
      security:                      # 满足列表中任意一项即可访问
        - OperationBased:
            - "beneficiary:create"
        - ResourceOrUseCaseBased:
            - "beneficiary:all"
      responses:
        "201":
          description: Added

名字里有冒号时要加引号，否则 YAML 会解析出错。

401、403 还是 404

500 不能泄露实现细节

✗ 泄露了数据库类型和服务器地址
HTTP/1.1 500 Internal Server Error
Content-Type: text/plain

Error [08001] Connection to server
192.168.12.34 failed
✓ 只给消费者有用的信息
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json

{
  "status": 500,
  "type": "https://api.bank.com/unexpected-error",
  "title": "An unexpected error occurred",
  "detail": "An unexpected error occurred (reference 12345)",
  "instance": "/unexpected-errors/12345"
}

左边的 08001 是 PostgreSQL 的错误码，再加一个内网 IP —— 攻击者求之不得。 右边用了 Problem Details 的 instance 属性给出这一次错误的引用：它不必是一个真能访问的 URL，只要能在服务端日志里查到就行。 把引用号也写进 detail，方便用户报给客服。 

import logging, uuid
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()
log = logging.getLogger("api")

@app.exception_handler(Exception)
async def unexpected_error(request: Request, exc: Exception):
    reference = uuid.uuid4().hex[:8]
    # 细节只进服务端日志
    log.error("Unexpected error %s on %s %s", reference, request.method, request.url.path,
              exc_info=exc)
    # 响应里只有通用信息 + 一个可以拿来查日志的引用号
    return JSONResponse(
        status_code=500,
        media_type="application/problem+json",
        content={
            "status": 500,
            "type": "https://api.bank.com/unexpected-error",
            "title": "An unexpected error occurred",
            "detail": f"An unexpected error occurred (reference {reference})",
            "instance": f"/unexpected-errors/{reference}",
        },
    )

import { Hono } from "hono";

const app = new Hono();

app.onError((err, c) => {
  const reference = crypto.randomUUID().slice(0, 8);
  // 细节只进服务端日志
  console.error(`Unexpected error ${reference} on ${c.req.method} ${c.req.path}`, err);
  // 响应里只有通用信息 + 一个可以拿来查日志的引用号
  return c.body(
    JSON.stringify({
      status: 500,
      type: "https://api.bank.com/unexpected-error",
      title: "An unexpected error occurred",
      detail: `An unexpected error occurred (reference ${reference})`,
      instance: `/unexpected-errors/${reference}`,
    }),
    500,
    { "Content-Type": "application/problem+json" },
  );
});

@RestControllerAdvice
public class UnexpectedErrorHandler {

    private static final Logger log = LoggerFactory.getLogger(UnexpectedErrorHandler.class);

    @ExceptionHandler(Exception.class)
    public ProblemDetail handle(Exception exception, HttpServletRequest request) {
        String reference = UUID.randomUUID().toString().substring(0, 8);
        // 细节只进服务端日志
        log.error("Unexpected error {} on {} {}", reference, request.getMethod(),
                  request.getRequestURI(), exception);
        // 响应里只有通用信息 + 一个可以拿来查日志的引用号
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR,
            "An unexpected error occurred (reference " + reference + ")");
        problem.setType(URI.create("https://api.bank.com/unexpected-error"));
        problem.setTitle("An unexpected error occurred");
        problem.setInstance(URI.create("/unexpected-errors/" + reference));
        return problem;       // Spring 会用 application/problem+json 返回
    }
}

在 OpenAPI 里给实现者写清楚

把 HTTP 状态的原因短语（「Forbidden」）直接当作响应描述，是通往错误实现的捷径。 实现者常常搞不清 401 和 403 的界线（「无效令牌包不包括权限不对的令牌？」）。写出每个状态码出现的确切条件： 

paths:
  /accounts/{accountId}:
    get:
      responses:
        "401":
          description: |
            The access token is missing, expired, or invalid (non-existing, typo).
            Scope-related errors are handled with 403.
        "403":
          description: |
            The consumer is missing a scope, or the identified user is a bank
            advisor who doesn't have access to the account.
        "404":
          description: |
            The account doesn't exist, or the identified user is an account
            owner who doesn't have access to it.
⚠ 文档里的描述 ≠ API 返回的错误信息

OpenAPI 里的 description 是写给实现者看的，可以比实际返回给消费者的错误信息（「Missing permission to access account 12345」）详细得多。 别把前者原样返回给调用方。

用 JSON Schema 锁死错误数据

很多 OpenAPI 文档对错误响应不定义 schema，或者所有错误共用一个宽松的 schema —— 实现想返回什么就返回什么，敏感信息就可能漏出来。 可以用 const（唯一允许的值）和 pattern（正则）把 500 的响应精确地规定下来： 

components:
  schemas:
    UnexpectedError:
      type: object
      required: [status, type, title, detail, instance]
      additionalProperties: false            # 不允许出现其他属性
      properties:
        status:
          const: 500
        type:
          const: "https://api.bank.com/unexpected-error"
        title:
          const: An unexpected error occurred
        detail:
          type: string
          pattern: "^An unexpected error occurred \\(reference [0-9a-f]+\\)$"
          examples:
            - An unexpected error occurred (reference 12345)
        instance:
          type: string
          pattern: "^/unexpected-errors/[0-9a-f]+$"

然后在所有操作的 500 响应里引用 #/components/schemas/UnexpectedError。只要实现遵守这份契约，就没有泄露的空间。

本章小结

  • 任何 API 都要保护，包括不对外的私有 API：只有相关的操作和数据能被授权的消费者和用户访问。
  • 设计对安全的贡献：最小化 API 表面、不暴露提供者视角、保证数据完整性、给实现者提供所需的全部信息。
  • 向有资质的专家确认哪些数据和操作是敏感的、如何保护；把完整的 OpenAPI 文档交给他们审阅。
  • 质疑每一个数据和操作的必要性；删除或替换敏感元素；拆分操作；把敏感操作放进专门的 API。
  • 在 OpenAPI 的描述里写明消费者和用户各自能看什么、做什么；调整设计，只返回需要的数据。
  • GET 和 DELETE 可以安全重试；用幂等键防止 POST 被重放；用条件请求（If-Match: <ETag>）防止更新覆盖别人的修改。
  • URL 里不放敏感数据：用 POST /resources/search 把敏感的搜索条件移到请求体，并借此用敏感但可互操作的数据换取不敏感的资源 ID。
  • 与安全专家讨论加密和签名，据此调整设计并写进文档。
  • 作用域要设计得让提供者、消费者和最终用户都容易做出正确的选择；可按操作、资源、用例、读写、用户或消费者来划分，也可以用来调节操作的行为。
  • 在 OpenAPI 的 components.securitySchemes 里定义作用域，在每个操作的 security 里使用。
  • 令牌问题返回 401；可通过申请解决的作用域或权限问题返回 403；无法解决的返回 404。
  • 用描述和 JSON Schema 确保 500 的响应不泄露实现细节。

动手练习

  1. 健身 App 的用户资料包含 id、phone、name、email、birthDate、fitnessLevel；训练记录包含日期、类型、时长、卡路里和带时间戳的 GPS 坐标序列。产品方想让任何用户都能读取任何人的资料和训练。有安全问题吗？
    参考答案 有。电话、邮箱、生日是 PII；GPS 轨迹能暴露一个人的住址和日常作息，非常危险。 对策：为「公开分享」设计不同的资源和模型（如公开资料只有昵称和健身等级；公开训练去掉 GPS 轨迹或只保留总距离，日期可以模糊化）； 让用户自己选择分享什么；完整的数据只返回给本人，并在 OpenAPI 描述里写明；必要时用行为调节型作用域。
  2. 某公司的 API 用 GET /identifiers?id=123-456-789&country=BRA 判断一个字符串是否符合某国某种证件号的格式。有安全问题吗？
    参考答案 被检查的字符串很可能是真实的证件号，它出现在 URL 里就会进入各处的日志。 改为 POST /identifiers/search（或 POST /identifier-checks），把 id 和 country 放进请求体。
  3. 医院里「病历」「治疗」「排班」三个应用共用一个医疗 API。GET /patients/{patientId}/conditions 的数据只能被病历和治疗应用上、正在治疗该患者的医生访问。这能用作用域解决，还是要靠实现检查？
    参考答案 两者都要。作用域解决「哪些应用能调」：定义如 patient:condition:read，只授予病历和治疗应用，不给排班应用。 实现检查解决「哪个用户能看哪个患者」：根据令牌里的医生身份，核对他是否正在治疗 patientId 对应的患者（不是则返回 403 或 404）。并把这条规则写进操作的描述。
  4. 图书馆 API 的作用域：/books 上的 GET、POST 都要 books；/books/{bookId} 上的 GET、PUT、DELETE 都要 book；members/member 同理；借书要 borrowed books。有什么问题？
    参考答案 读和写没有分开：一个只需要搜索图书的应用（比如公开的馆藏查询）拿到 books 就也能新增图书，拿到 book 就也能删书。 按「集合/单个」划分没有业务意义，也让人难以理解；borrowed books 里有空格，命名也不一致。 改进：book:read（搜索+读取）、book:write（增改删）、member:read、member:write、borrowing:create，或按用户再细分（librarian:…、member:…）。
