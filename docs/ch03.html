第 3 章

从 REST 视角观察操作

上一章我们得到了一组用自然语言描述的操作，比如「搜索商品」。现在要把它们变成编程接口。 但别急着写 GET /products —— 先补上 HTTP 和 REST 的基础，然后换一副「REST 眼镜」重新审视这些操作： 它们操纵的是什么资源？对资源做了什么动作？需要什么输入，给出什么输出？

本章目标

  • 看懂一次 HTTP 请求/响应由哪几部分组成
  • 分清「REST API」和「只是用了 HTTP 的 Web API」
  • 知道设计接口的三个小步骤：观察 → 用 HTTP 表示 → 数据建模
  • 会从操作描述里找出资源、资源之间的关系、动作
  • 会把多个步骤的输入、成功、失败合并成与场景无关的输入列表和输出列表

HTTP 基础

HTTP（超文本传输协议）是一个同步的「请求—响应」协议，它让客户端通过一组标准化的方法与资源交互。 资源可以是任何东西：一个 HTML 页面、一段视频、一份 PDF。最常用的两个方法是 GET（取）和 POST（送）。

任何编程语言都能说 HTTP。下面三段代码做的事和在终端里敲 curl https://apihandyman.io/blog 完全一样：

import requests

page = requests.get("https://apihandyman.io/blog")
print(page.status_code)  # 200
print(page.text)         # <html> ...

const page = await fetch("https://apihandyman.io/blog");
console.log(page.status);        // 200
console.log(await page.text());  // <html> ...

var client = HttpClient.newHttpClient();
var request = HttpRequest.newBuilder(URI.create("https://apihandyman.io/blog")).GET().build();
var page = client.send(request, HttpResponse.BodyHandlers.ofString());

System.out.println(page.statusCode());  // 200
System.out.println(page.body());        // <html> ...

REST API 基础

目前可以把 REST API 理解为：充分使用 HTTP 并且尊重其语义的 Web API（它其实不止于此，第 4 章末尾再讲）。 调用一个 REST API 和加载一个网页在 HTTP 层面一模一样，区别只有两点：

  • 资源不再是 HTML、CSS 这类「网页资源」，而是一个业务概念，比如「商品」；
  • 返回的不是 HTML，而是结构化数据（通常是 JSON，第 5 章讲）。
GET /products HTTP/1.1
Host: api.shp.ng

HTTP/1.1 200 OK
Content-Type: application/json

[
  { "id": 12345, "name": "Cowboy Bebop", "type": "BD" },
  { "id": 12346, "name": "Macross",      "type": "BD" }
]
ⓘ 像不像面向对象？

HTTP 的「资源 + 方法」模型很像 OOP 里的「对象 + 方法」。 区别在于：对象可以随便定义方法，而 HTTP 只有有限的几个标准方法。这个限制正是它的力量所在 —— 后面会体会到。

不遵守 HTTP 语义的 Web API

所有 Web API 都用 HTTP，但不是都尊重 HTTP 的语义。对比一下「删除一个不存在的商品 123」：

这种差别不是洁癖。看看消费者的代码：遵守语义时，HTTP 客户端库、缓存、网关、监控都能自动理解发生了什么； 不遵守时，每个调用点都要自己拆开响应体猜。 

import httpx
api = httpx.Client(base_url="https://api.shp.ng")

# ✓ REST：状态码就是答案，任何 HTTP 工具都看得懂
r = api.delete("/products/123")
if r.status_code == 404:
    print("商品不存在")
r.raise_for_status()          # 其他错误统一抛异常

# ✗ 非标准：永远是 200，只能去响应体里翻
r = api.get("/deleteProduct/123")
body = r.json()
if "error" in body:           # 字段叫 error？err？message？每个接口都可能不一样
    print("好像失败了：", body["error"])

const base = "https://api.shp.ng";

// ✓ REST：状态码就是答案，任何 HTTP 工具都看得懂
const r1 = await fetch(`${base}/products/123`, { method: "DELETE" });
if (r1.status === 404) console.log("商品不存在");
else if (!r1.ok) throw new Error(`HTTP ${r1.status}`);

// ✗ 非标准：永远是 200，只能去响应体里翻
const r2 = await fetch(`${base}/deleteProduct/123`);
const body = await r2.json();
if ("error" in body) {        // 字段叫 error？err？message？每个接口都可能不一样
  console.log("好像失败了：", body.error);
}

RestClient api = RestClient.create("https://api.shp.ng");

// ✓ REST：状态码就是答案，框架自动把 4xx 变成对应的异常
try {
    api.delete().uri("/products/123").retrieve().toBodilessEntity();
} catch (HttpClientErrorException.NotFound e) {
    System.out.println("商品不存在");
}

// ✗ 非标准：永远是 200，只能去响应体里翻
Map<String, Object> body = api.get().uri("/deleteProduct/123")
    .retrieve().body(new ParameterizedTypeReference<>() {});
if (body.containsKey("error")) {   // 字段叫 error？err？message？每个接口都可能不一样
    System.out.println("好像失败了：" + body.get("error"));
}

设计 REST 接口的三个小步骤

⚠ 为什么识别能力时不直接想 HTTP

有经验的人一眼就能把「搜索目录」翻译成 GET /products，但这种本能会带偏思路。 例如给图书馆设计 API，如果满脑子 HTTP，很容易只想到 GET /books、GET /books/{bookId}， 接着顺手加个 DELETE /books/{bookId} —— 可「删除一本书」在图书馆里有意义吗？ 一本书的多个副本怎么办？「借书」是个动作而不是名词，又该怎么表示？ 先不带 HTTP 滤镜把能力找全，才能既满足需求，又有足够的信息来回答这些问题。

准备工作：按操作重排画布

本章用上一章「在线购物」例子里的一个子集，它恰好覆盖了五种最典型的操作： 搜索、创建、读取、更新、删除 —— 后四个常被合称 CRUD（Create / Read / Update / Delete，Read 也涵盖搜索）。

画布原本按用例组织，同一个操作散落在多个步骤里。用电子表格的透视表（把「操作」列放最前面），或者直接按操作筛选，得到下面的视图：

识别资源与关系

什么是资源

在 REST API 里，资源首先是一个与领域相关的业务概念，用一个名词或简短的领域术语来称呼。判断标准：

  • 它能独立存在，可以被单独操纵；
  • 它不同于它的属性 —— 属性是组成它的小块数据，不能独立存在。

「商品」是资源；商品的「名称」是属性。有些东西介于两者之间：「价格」通常是商品的属性，但如果业务需要追踪价格的历史变化，它也可能需要被当作资源。 资源大致相当于面向对象里的一个类。

怎么找：看主要动词作用在谁身上

操作描述里的主要动词的宾语通常就是资源，再用输入、成功、失败来印证。 「修改商品」→ 动词「修改」作用于「商品」；输入、成功、失败也都只提到商品 → 资源是商品。

拿不准时，把描述缩短或扩写：

操作描述改写资源
把商品加入目录缩短 →「加入目录」。成功与否讲的也是「是否进了目录」目录
从目录移除商品缩短 →「移除商品」。输入和结果都只关心商品商品
搜索商品扩写 →「在目录中搜索匹配条件的商品」→ 再缩短 →「在目录中搜索」目录
获取商品详情「获取」作用于「商品详情」商品
修改商品「修改」作用于「商品」商品
★ 一条好用的规律

读取 / 更新 / 删除某个元素时，资源是元素本身。
创建（加入）/ 列出 / 搜索元素时，资源是元素的容器。

ⓘ 嵌套资源

如果怎么改写都定不下来，可能遇到了嵌套（层级）资源。 「把新商品加入某商家的目录」可以缩成「加入商家的目录」，但缩不成「加入目录」—— 资源是「商家的目录」。

识别关系

借助领域知识和画布上的信息找出资源之间的关系。大多数关系最后都能表述成「X 属于 Y」或「Y 包含 X」。 这和设计类或数据库表很像，可以用你熟悉的方法 —— 但别被现有代码或表结构牵着走（第 2 章的「暴露提供者内部」）。

识别动作

动作就是操作描述里的那个主要动词 —— 找资源时已经顺便找到了。

操作资源动作
添加商品到目录目录添加
（在目录中）搜索商品目录搜索
获取商品详情商品获取
修改商品商品修改
从目录移除商品商品移除
⚠ 别抢跑

保留描述里的原始动词，不要现在就换成 CRUD 动词或 HTTP 方法。 一旦学会把动作映射到 HTTP 方法（下一章），你会很想直接写「POST」「GET」—— 忍住。有些动作并不能干净地对应到某个方法，过早替换会丢信息。

列出动作的输入

一个操作的输入 = 所有用到它的步骤的输入，合并后用与场景无关的方式重新描述（和提炼操作时同一个思路）。

  • 「选中的商品」和「找到的商品」本质都是「指明某一件商品」→ 合并为商品引用。
  • 「修改后的信息」写得更明确些 → 修改后的商品信息。
  • 「把商品加入目录」的输入「商品」改叫商品信息，避免和「商品」这个资源混淆。
  • 「搜索商品」两个步骤的「筛选条件」和「特征」都是搜索条件 → 合并为筛选条件。
💡 资源本身什么时候是输入

操作的资源通常不算输入。但如果它有多个实例，就需要一个引用来指明是哪一个。 比如系统里有多个目录，「添加到目录」就得加上「目录引用」—— 并且你刚刚发现了一个新用例「管理目录」需要回头分析。 本例与领域专家确认后，决定只有一个目录。

此时不需要细节，「商品信息」里有哪些字段留到第 5 章；分页、筛选相关的参数漏了也没关系，第 13 章会系统处理。

列出动作的输出

每个动作有一张输出列表，把成功和失败都放进去。每一项包含：描述、类型（成功 / 错误）、数据（可以没有）。 同样要合并各步骤并去掉场景色彩。

解决矛盾：成功还是失败由操作本身决定

一个操作的输出算成功还是错误，必须独立于用例和消费者，只取决于操作的性质、输入输出数据和领域本身。 同理，读取一件库存为零的商品，对想买它的顾客是坏消息，对想确认它已下架的管理员是好消息 —— 但操作的输出在两种情况下都是「成功，返回商品信息」。

⚠ 别把苹果和橘子混在一起

如果一个操作返回了性质不同的东西（尤其在列表里），往往说明操作或数据识别错了。 返回「书」和「牙刷」？可以统一为「商品」。返回「商品」和「供应商」？多半应该拆成两个操作。 （不过，商品详情里带一份供应商摘要是合理的。）

把这张表写成代码

既然资源像类、动作像方法，那这张操作表其实就是一组接口签名。 下面把它翻译成三种语言 —— 这不是 API 的实现，只是帮你用程序员熟悉的方式再看一遍「资源 / 动作 / 输入 / 输出」： 

from dataclasses import dataclass
from typing import Protocol

@dataclass
class ProductInfo: ...        # 商品信息：里面有什么字段，第 5 章再定
@dataclass
class Filters: ...            # 筛选条件
ProductRef = str              # 商品引用

class ProductNotFound(Exception): ...     # 错误输出
class WrongProductInfo(Exception): ...    # 错误输出


class Catalog(Protocol):
    """资源：目录（容器）"""

    def add(self, info: ProductInfo) -> None:
        """动作：添加。成功：商品已加入目录；错误：WrongProductInfo"""

    def search(self, filters: Filters) -> list[ProductInfo]:
        """动作：搜索。找到或没找到都是成功 —— 没找到就返回空列表，不抛异常"""


class Product(Protocol):
    """资源：商品（元素），由 ProductRef 指明是哪一个"""

    def get(self, ref: ProductRef) -> ProductInfo:
        """动作：获取。错误：ProductNotFound"""

    def modify(self, ref: ProductRef, modified: ProductInfo) -> None:
        """动作：修改。错误：ProductNotFound"""

    def remove(self, ref: ProductRef) -> None:
        """动作：移除。错误：ProductNotFound"""

type ProductInfo = { /* 商品信息：里面有什么字段，第 5 章再定 */ };
type Filters = { /* 筛选条件 */ };
type ProductRef = string;      // 商品引用

// 输出 = 成功或错误，各带一段描述和可选的数据
type Output<Data = undefined> =
  | { type: "success"; description: string; data: Data }
  | { type: "error"; description: string };

/** 资源：目录（容器） */
interface Catalog {
  /** 动作：添加。成功：商品已加入目录；错误：商品信息有误 */
  add(info: ProductInfo): Output;

  /** 动作：搜索。找到或没找到都是成功 —— 没找到时 data 是空数组 */
  search(filters: Filters): Output<ProductInfo[]>;
}

/** 资源：商品（元素），由 ProductRef 指明是哪一个 */
interface Product {
  /** 动作：获取。错误：商品不存在 */
  get(ref: ProductRef): Output<ProductInfo>;

  /** 动作：修改。错误：商品不存在 */
  modify(ref: ProductRef, modified: ProductInfo): Output;

  /** 动作：移除。错误：商品不存在 */
  remove(ref: ProductRef): Output;
}

record ProductInfo() {}       // 商品信息：里面有什么字段，第 5 章再定
record Filters() {}           // 筛选条件
record ProductRef(String value) {}   // 商品引用

class ProductNotFoundException extends RuntimeException {}    // 错误输出
class WrongProductInfoException extends RuntimeException {}   // 错误输出

/** 资源：目录（容器） */
interface Catalog {
    /** 动作：添加。成功：商品已加入目录；错误：WrongProductInfoException */
    void add(ProductInfo info);

    /** 动作：搜索。找到或没找到都是成功 —— 没找到就返回空列表，不抛异常 */
    List<ProductInfo> search(Filters filters);
}

/** 资源：商品（元素），由 ProductRef 指明是哪一个 */
interface Product {
    /** 动作：获取。错误：ProductNotFoundException */
    ProductInfo get(ProductRef ref);

    /** 动作：修改。错误：ProductNotFoundException */
    void modify(ProductRef ref, ProductInfo modified);

    /** 动作：移除。错误：ProductNotFoundException */
    void remove(ProductRef ref);
}

下一章要做的事情，就是把这些「方法签名」换成 HTTP 的表达方式： 类名变成路径，方法名变成有限的几个 HTTP 方法，返回值和异常变成状态码。

本章小结

  • HTTP 是同步的请求—响应协议，通过标准化的方法与资源交互；资源可以是任何东西。
  • REST API 充分使用 HTTP 并尊重其语义。
  • 设计 REST 接口分三步：从 REST 视角观察操作 → 用 HTTP 表示 → 数据建模。
  • 五种典型操作：搜索，以及创建、读取、更新、删除（CRUD）。
  • 资源是能独立存在的业务概念，区别于它的属性。
  • 一个操作只用一个资源；资源是操作描述中主要动词的作用对象。
  • 创建/添加、列出/搜索时资源是容器；读取/更新/删除时资源是容器里的单个元素。
  • 动作就是那个主要动词，保留原词，别急着换成 HTTP 方法。
  • 输入列表合并各步骤的输入并去场景化；操作的资源本身不算输入，除非它有多个实例。
  • 输出列表合并各步骤的成功与失败，每项有描述、类型、可选数据；类型要从与场景无关的角度判断。

动手练习

  1. 在线课程平台，教师可以：①开设一门新课程（含大纲、难度、主题列表）；②按主题或难度查找课程；③查看某门课程的信息；④修改课程的难度、大纲或主题。为每个操作找出资源、关系和动作。
    参考答案 资源有两个：课程目录（容器）和课程（元素），关系是「课程目录包含多门课程」。 ① 课程目录 / 开设（添加）；② 课程目录 / 查找；③ 课程 / 查看；④ 课程 / 修改。 大纲、难度、主题在这里是课程的属性，不是独立资源（除非业务上需要单独管理主题）。
  2. 航空出行 API：「搜索航班」在两个步骤中的输入分别是（机场、目的地、航班、出发日期）和（日期、航空公司、航班）；「预订航班」的输入是（航班、日期、乘客、航班）。每个操作的资源和真正的输入是什么？
